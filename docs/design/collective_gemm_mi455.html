MI455X Helios 上的 Collective GEMM 设计

适用平台：MI455X（gfx1250），Helios 机柜，UALink（UALoE）scale-up 域，跨 compute tray
状态：设计稿；阶段 0（fabric 对称内存）已实现，跨 tray 复测待完成（见 分阶段计划）
测试机器：ctheliosr-rck-g02-e15-01 / -02，2 个 tray × 4 张 GPU，2026-11-23
摘要
  • 两台 tray 的 8 张 GPU 在硬件上是同一个扁平的 scale-up 域。tray 内和跨 tray 的带宽（单对约 1.3–1.4 TB/s）、延迟（远端 load 约 3.1–3.2 µs）几乎一样，不需要分层（hierarchical）算法。
  • 现有实现跨不了 tray，原因在内存映射层。SymmetricMemory 用 legacy HIP IPC，只能在同一个 OS 实例内使用。改用 VMM + fabric handle 之后，跨 tray 的 load/store、原子操作、release/acquire flag 都已实测可用。这部分已经实现，所有使用对称内存的模块不改代码就能跨 tray。
  • 在 MI455 上，数据搬运应以 SDMA 为主，CU 只做 flag、reduce 和小消息。CU 每个只能向远端推 8–10 GB/s，打满链路需要 128–256 个 CU，和 GEMM 并发时 GEMM 慢 20–47%。SDMA 单个 engine 就有 1.55 TB/s，而且不占 CU，和 GEMM 并发时 GEMM 的变化在 ±2% 以内。
  • 架构分四层，通用性优先：L0 对称内存（IPC / fabric）→ L1 通信原语（put + signal，SDMA 或 CU 两种引擎）→ L2 融合算子（GEMM 只多一个"按 flag 放行 tile"的钩子）→ L3 模型算子（只描述数据布局，不再为每个模型手写融合 kernel）。

1. 背景与问题

Primus-Turbo 现有的融合通信 GEMM 在 primus_turbo/flydsl/fused_collective_gemm/，包括 GemmA2A、A2AGemm、AgGemm、GemmRS 四个 kernel，服务于 Ulysses 和 MLA latent 投影。它们的共同做法是：

  • 通过 SymmetricMemory 拿到每个 rank 的 heap 指针（peer_ptrs），由 GEMM kernel 里的一部分 block 直接对远端 heap 做 load/store（push 或 pull），并用 system-scope 的 flag 和 tile 级的流水做同步。
  • 对称内存用 hipMalloc + hipIpcGetMemHandle / hipIpcOpenMemHandle 做 rendezvous。
  • kernel 针对 MI355X（gfx950）调优：写死了 WARP=64、NUM_XCDS=8、缓存策略位 SYS_NT=0x13，测试也明确只在 gfx950 上运行。

在 Helios 上，一个训练任务会跨多个 compute tray，每个 tray 是一个独立的 OS 实例，只能看到本 tray 的 4 张 GPU。由此带来三个问题：

  1. 能不能跨 tray？legacy IPC handle 只在同一个内核实例内有效，打不开另一台机器上的 handle。
  2. 该用什么搬数据？MI355X 上"CU 直接 load/store 远端内存"是合理选择，在 MI455 上是否仍然成立，需要实测。
  3. 怎么兼顾通用性？现有四个 kernel 是按模型特化的。要支持新的架构、新的拓扑规模和更多算子，逐个移植的成本很高。

1.1 适用范围

本设计只覆盖 scale-up 域，也就是同一个 UALink vpod 里的 GPU。它们之间可以直接 load/store 对方的显存。跨 vpod、跨机柜的 scale-out（经后端 RDMA 网卡）不在范围内：

  • 原语不同：fabric handle 只能在 vpod 内导入，出了 vpod 就没有 peer_ptrs。L1 和 L2 依赖的"直接写对端地址、spin 对端写来的 flag"都不成立；scale-out 要用 RDMA write、atomic 和 completion。
  • 需求上也不需要：collective GEMM 服务的 TP、SP/Ulysses、MLA 投影本来就应该放在 scale-up 域内。Helios 的 scale-up 域最大是整个机柜 72 卡。跨机柜的 DP、PP 和大部分 EP 由 RCCL 或 DeepEP 的 internode 路径负责，一般不需要和 GEMM 做 tile 级融合。
  • 扩展路径：L1 的 put(dst_rank, dst_offset, src, nbytes, signal) 语义上就是"RDMA write + 远端 flag"。以后需要时，可以加一个与 SDMA、CU 并列的 RDMA 引擎；L0 要相应地支持内存注册和 rkey 交换。L2、L3 基本不变。这不在当前计划内。

  • 正确性：tray 内和跨 tray 各 256 MB，逐字比对 0 mismatch。3.5 节用到的 torch peer copy 在 rocprofv3 trace 里只有 memory copy 记录、没有 copy kernel，确认走的是 copy engine。

CU 这一列测的是"两个独立 kernel 并发"的情况，persistent GEMM 被抢走 CU 后会出现 wave 量化和尾部效应，所以是偏悲观的上界。但即使在融合 kernel 里精确地只划出 N 个 CU，直接代价也至少是 N/256 的算力，再加上 L2 和 HBM 的争用；而按 3.2 节的数据，要搬 1 TB/s，N 得在 128 左右。

4. 关键结论

  1. 拓扑是扁平的。8 张卡之间的带宽和延迟几乎一致，算法只需要按"一个 scale-up 域里有 n 个 rank"来设计，不用区分 tray 内和跨 tray。
  2. 能不能跨 tray，只取决于内存映射方式。fabric handle 映射之后，kernel 层的指针语义、原子操作、内存序都和 tray 内一样。
  3. 大块数据用 SDMA，CU 用于计算。SDMA 在带宽（1.55 对 1.37 TB/s）、CU 占用（0 对 128–256 个）和对 GEMM 的干扰（±2% 对 +20–47%）三项上全面胜出。CU 只在需要计算（reduce）、消息很小（SDMA 每次 7 µs 的固定开销占主导）或者要求 tile 级细粒度同步时使用。
  4. 流量要分散。同时直连所有 peer，避免一对一和 ring。
  5. 跨 rank 优先 push。远端 load 要等约 3 µs 的往返，而写是 posted 的；跨 rank 的数据路径应尽量写到对端，读只发生在本地。

6. 分层架构

L0 对称内存 已实现

每个 rank 分配一块大小相同的 heap，每个 rank 都持有所有 heap 的设备指针。上层只依赖指针语义，不关心底层映射方式。

IPC 后端（_IpcHeap）

  • hipMalloc 或 hipExtMallocWithFlags(Uncached)
  • hipIpcGetMemHandle → all-gather → hipIpcOpenMemHandle
  • 只在同一个 OS 实例内有效；行为与改动前完全一致

fabric 后端（_FabricHeap）

  • hipMemCreate（Pinned 或 Uncached，requestedHandleType = Fabric），按推荐粒度对齐
  • hipMemExportToShareableHandle → all-gather 64 字节 handle → hipMemImportFromShareableHandle
  • hipMemAddressReserve / hipMemMap / hipMemSetAccess，只对本进程的设备开放访问
  • 可跨同一 scale-up 域内的任意 OS 实例

后端选择（resolve_symm_mem_backend，所有 rank 共同参与）：显式参数 backend= 优先，其次是 PRIMUS_TURBO_SYMM_MEM_BACKEND，默认 auto。auto 时，所有 rank 的内核 boot_id 相同就用 IPC，否则用 fabric。boot_id 正好对应 legacy IPC 的有效边界：容器共享宿主机内核，所以同一台机器上的多个容器算同一个 OS 实例。选择过程用一次 all-gather 汇总各 rank 的 OS 实例、请求的后端和 fabric 支持情况，任何不一致都会让所有 rank 一起报错，不会出现部分 rank 卡在后续集合通信里。

附带收益：VMM 可以先预留一大段虚拟地址，按需映射物理内存，以后能让 workspace 原地扩容，不用像现在这样"先分配新的、再释放旧的"。

L1 通信原语 阶段 1

只有一个核心原语：把一段本地数据写到某个 rank 的对称内存，写完后在对端置一个 flag。一次调用是 stream 上的一个会话，epoch 由 begin 分配，put 时不用再传：

epoch = comm.begin()                    # 不在 stream 上放任何东西
comm.put(dst_rank, dst_offset, src_ptr, nbytes, flag, engine=None)   # 次数、目的地、切分都由调用方决定
comm.release()                          # 可选：此前的 put 从 stream 的这个位置起开始搬（读到的是这里之前产生的数据）
comm.wait_flag(src_rank, flag)          # 可选：stream 等某个 peer 的某个 flag（按块开始计算）
comm.wait(num_flags)                    # stream 等待：本 rank 的 put 已落地，各 peer 的 flag 0..num_flags-1 已到
comm.flags()                            # [world, max_chunks]，融合 kernel 可以自己轮询，代替 wait

all_gather(inp, num_chunks)       # 每个 peer 的块切成 num_chunks 次 put，第 c 块用 flag c
all_to_all(inp, num_chunks)       # 按目的地切片后 put
reduce_scatter(inp, num_chunks)   # A2A：把属于别人的 partial 推到对方；拥有者本地按固定 rank 顺序归约

flag 按"源 rank"分块：接收方每个 bank 为每个源 rank 留 max_chunks 个 flag，只由该源写，所以只要同一次调用里每个 (dst_rank, flag) 只 put 一次，每个 flag 就只有一个写者。默认 engine 分配：发给第 k 个下游 peer 的第 i 次 put 用 engines[(k − 1 + i·(n − 1)) mod E]，peer 和 chunk 同时错开。

  • SDMA 引擎：每个 peer 分配独立的 engine（16 个 engine 足够覆盖 7 个 peer，peer 更多时共享），各 rank 的 peer 顺序错开。按 chunk 发起。单个 engine 上，chunk 约 11 MB 才能达到 50% 的链路带宽（图 3）；更小的 chunk 要靠多个 engine 并行来重叠每次约 7 µs 的固定开销，这一点在阶段 1 验证。
  • CU 引擎：用于小消息、flag，以及没有可用 SDMA 的环境。可以嵌进融合 kernel 里运行。
  • RS 改写为 A2A + 本地归约：跨 rank 只有写；归约只读本地 HBM（单 CU 约 50 GB/s，远高于远端的 8–10 GB/s），结果确定。代价是多占 n 份 staging 显存。

L2 融合算子 阶段 2

GEMM 是 persistent kernel，只增加一个能力：每个 m-tile 在计算前，等待它依赖的 chunk 的 flag；tile 的调度顺序按 chunk 的到达顺序排，本地 chunk 先算。

算子数据流谁在搬
AG-GEMM每个 rank 把自己的 A 按 chunk 推给所有 peer 的 recv bank，每个 chunk 置一个 flag；GEMM 按 flag 放行 tile，直接从 bank 读 ASDMA
GEMM-RSGEMM 把 partial 写进本地 staging，每算完一个 chunk 置 flag；flag 触发 SDMA，把这块 partial 推到拥有者的 staging 槽位；拥有者等齐 n 份后在本地归约SDMA 搬，CU 归约
A2A-GEMM与 AG-GEMM 相同，只是按目的地切片，GEMM 按到达顺序遍历 K 段SDMA
GEMM-A2A与 GEMM-RS 相同，但不需要归约，按列块分发到各 rankSDMA

"flag 触发 SDMA"用 HSA copy 的依赖信号实现：put 时 host 就把拷贝提交给 SDMA，拷贝依赖一个闸门信号；GPU kernel 在 stream 上把闸门清零，SDMA 随即开始，不经过 host 轮询。e15-01 上已验证（GEMM-RS 每算完一块就 release 一次）。

当前实现（GEMM 无关的版本，comm_method="sdma"）：pytorch/kernels/async_tp/sdma_impl.py，接在 fused_all_gather_matmul / fused_all_gather_scaled_matmul / fused_matmul_reduce_scatter 后面。GEMM 仍是 hipBLASLt，按块在调用方的 stream 上执行，stream 在每块之前 wait_flag：

  • AG-GEMM：先把本 rank 的 A（以及行 scale）按 num_splits 块 put 给所有 peer，release 后先算本地分块；之后按发送顺序（rank r 第 k 步收到 r − k 的数据）逐块 wait_flag 再算。GEMM 直接从 bank 读 A；bank 默认不走 cache，实测 GEMM 只慢 0–4.6%。
  • GEMM-RS：按目的 rank、按块计算 partial 写入本地 staging，每块算完立刻 put 并 release；本 rank 的行最后算；wait 后按 rank 顺序以 fp32 归约，结果确定。
  • tile 级的"按 flag 放行"仍是下一步：需要 gfx1250 的 persistent GEMM（FlyDSL）读 flags()。

L3 模型算子 阶段 3

Ulysses 的 QKV / O 投影、MLA latent 投影等，都改写成 L2 之上的布局描述：每个 rank 的哪些行（或列块）发给谁，在对端落在什么偏移。新增一个模型算子只需要写描述，不需要写 kernel。对外接口沿用 async_tp.py 里已有的 fused_all_gather_matmul / fused_matmul_reduce_scatter，名字与 PyTorch 一致；Ulysses 和 MLA 的现有接口保持不变。

7. 搬运引擎的选择

场景引擎原因
每个 peer 的数据量 ≥ 约 4 MB（训练里的 AG / A2A / RS 大多如此）SDMA带宽最高、不占 CU、不干扰 GEMM
每个 peer 的数据量很小（推理 decode、小 batch）CUSDMA 每次约 7 µs 的固定开销占主导
需要边搬边算（归约、量化、加 residual）SDMA 搬 + CU 在本地算远端只写；计算只碰本地 HBM
flag、少量控制数据CU（或 SDMA 在数据之后补写）延迟最低
MI355X 等 SDMA 单 engine 较弱的平台CU由 autotune 根据实测决定阈值

8. 同步协议

  • 沿用现有的 epoch + 双 bank 协议（fused_collective_gemm/workspace.py）：每次调用从 state[0] 读 epoch，使用 epoch & 1 号 bank，flag 的值就是 epoch，等待方 spin 到 flag ≥ epoch。两个 bank 交替使用，不需要额外的确认或 barrier，也能进 CUDA graph。
  • SDMA 的顺序保证：同一个 chunk 的数据和 flag 必须"先数据、后 flag"可见。原计划用 hsa_amd_memory_async_batch_copy 的 signal-after-copy（拷贝后由 SDMA 原子写任意地址），但在 e15-01（gfx1250）上实测不可用：容器的 ROCm 7 和宿主机的 ROCm 10.2 运行库都接受这个参数，拷贝也完成了，目标地址却始终没被写（host 内存、device 内存都试过）；宿主机运行库上，之后同一队列的 SDMA 工作也不再完成。现在的实现这样串起来：
    1. 数据拷贝用 hsa_amd_memory_async_copy_on_engine 发到指定 engine，依赖一个 HSA 信号（闸门）。
    2. flag 是同一个 engine 上的第二个拷贝：8 字节，源是本 slot 的 epoch 字，目的地是对端的 flag，依赖数据拷贝的完成信号。HSA 只在拷贝的数据可见后才递减完成信号，所以 flag 一定在数据之后。
    3. stream 上一个单 wave 的 kernel 先写 epoch 字，再以 system scope release 把闸门清零。release 会写回 L2，所以 SDMA 读到的是 stream 上游已经产生的数据。这一步就是"GPU 触发 SDMA"，不经过 host。release() 可以调用多次，每次打开一个新的闸门，对应 GEMM-RS 里"算完一块发一块"。
    4. wait / wait_flag 在同一个带超时的 kernel 里先开闸，再等：本 rank 发出的 flag 拷贝都已完成，以及对应 peer 的 flag 已到达。
    e15-01 上 GPU 侧一次调用（开闸 → 数据 → flag → 等待）约 23–28 µs；host 侧提交约 48 µs（4 卡 all-gather：每个拷贝约 2.5 µs 的 HSA 调用，加一次约 12 µs 的 Triton launch），背靠背的小消息 microbenchmark 因此受 host 限制，训练中 host 通常领先 GPU。这条路径由 host 按次提交 SDMA 工作，所以 epoch 是 host 侧的计数器，不能进 CUDA graph。
  • 延迟预算：flag 单程约 2.5–3 µs，按 chunk 粒度同步完全可以接受；不建议按单个 tile 跨 rank 同步。
  • 所有 spin 等待必须有超时：DeepEP V2 的经验是，在 gfx1250 上驱动抢占或销毁一个仍在 spin 的队列时，MES 可能进入不可恢复的状态。本次测试中 e15-02 驱动卡死，很可能就是这类情况。spin 超时后应该 trap，而不是一直等待。

9. 与现有代码的关系

现有部分处理
SymmetricMemory（pytorch/core/symm_mem.py）保留接口，增加 fabric 后端（已完成）。mega、DeepEP intranode、fused_collective_gemm、async_tp 都通过它拿对称内存，因此在内存层面自动支持跨 tray。
fused_collective_gemm 的四个 kernelgfx950 上保持不变。不直接移植到 gfx1250，原因有三：写死 wave64 / 8 XCD；SYS_NT=0x13 在 gfx1250 上会被解释成 TH_LU + SCOPE_DEV，语义不对；通信完全依赖 CU，在 MI455 上代价过高。它们的协议设计（epoch / bank、按到达顺序调度 tile、确定性归约）会被 L1 和 L2 吸收。
async_tp（AG-GEMM / GEMM-RS，按 chunk 切分）接口保留，作为 L3 对外的 TP 入口。它内部用 hipMemcpyAsync 写 peer，在跨 tray 的 fabric 内存上只有 268 GB/s，需要换成 L1 的 SDMA 路径。
DeepEP V2（MI455X）它的 ArchTraits（wave32、拆分的等待计数器、缓存策略位、watchdog）是 gfx1250 上 CU 引擎的现成参考，L1 的 CU 引擎应复用。

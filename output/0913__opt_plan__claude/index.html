三个悬案，两个已结

① 220.6 vs 131.7 TFLOP/s 之谜 —— 是限频。 实测 b=2 是 129.4 TFLOP/s，b=4 是 127.8——batch 根本不影响 TFLOP/s， 这条假设死了。剩下的 1.70× 差距正好等于 VR 限频比。所以 c1325c7e 是在没限频的卡上测的。 重启没有解除限频，MAX_CLK 仍是 1100 MHz。

② JIRA 那个 enable_gqa 报错 —— 根因是缺 tensorboard。 patch runner 把依赖缺失吞掉当成"patch 没应用"，于是修调用点的补丁没生效。 装上之后 12/12 补丁全部应用成功。这是第三个与 JIRA 叙述不同的根因。

③ 端到端 tps —— 跑通了，但这台机器上测不出 attention。 turbo 245 tps vs flex 244 tps，两条路径差 0.4%—— 说明打开 turbo 不是回归，但也说明端到端瓶颈根本不在 attention。 根因见下。（另：这台机器此前从没跑通过一个 step， 三次历史运行 step 计数都是 0，所以本地原本就没有可回归的基线。）

端到端的真正瓶颈：这个镜像没有能用的 BLAS

排除法三步。先排除显存：开 activation checkpointing 后显存从 379.5 GiB 砍到 174.8 GiB，tps 反而从 245 变成 215（重算换显存，符号正确）——显存不是原因。

再测 GEMM（空闲卡，rocm-smi 确认无其它进程，bf16）： 8192³ 只有 27.4 TFLOP/s，几个真实训练形状都在 24–26 之间。

判定依据：同一张卡、同一次会话里，我们调优后的 attention 内核跑到 215 TFLOP/s，Phase 1 的 Triton GEMM 上限是 1002.7 TFLOP/s。 一个稠密 GEMM 比 flash-attention 慢 8 倍，这个方向本身就是反的—— attention 每个 FLOP 干的活更多，本该更慢。rocBLAS 离上限差约 37×。 而 hipBLASLt 的 gfx1250 库在镜像里根本不存在。

这一次性解释了全部现象：14 TFLOPS、133.7 秒/step、GPU 100% 占用却不做有用矩阵运算、 flex 和 turbo 只差 0.4%。也说明 JIRA 的 GEMM 数字和 19,795 tps 不可能来自这个镜像。 端到端验证需要一个 BLAS 能用的镜像——这是平台问题，和限频一起升级。

正确性门抓到了一个"又快又错"的配置

某个配置返回 out 53.67 dB ✓、dq 52.24 dB ✓、dk −inf ✗、dv −inf ✗—— 输出和 dq 完全正常，dk/dv 被毁掉。只看输出的检查会直接放过它。 这正是第 09 节所说"关键不是阈值，是覆盖面"的现实例证。 它不是必现的（75 次定向重复 0 次复现），所以是竞态而非配置错误，目前仍未定论。

顺序错了，而且这个错误是有代价的

计划里白纸黑字写着 Round 0 是 Phase 1 的第一步，还写着它是"整个计划里性价比最高的一次探针"。 实际执行时它被放到了最后。这是个错误，代价是一整段工作用在了错的轴上。

如果第一天就做了对照实验，那两个整数照样会被找到（它们是可迁移的）， 但花在 turbo 调度旋钮上的那些轮次——waves_per_eu 扫描、跳掩码改写、 收紧 lo 边界、折叠 log_p_scale、寄存器溢出排查—— 本该花在真正区分两个后端的那一件事上（见下）。那些实验的结果无一例外是"持平或更差"。

这条经验值得写进流程：在确认"这是该调的实现"之前，不要开始调它。 一次对照实验只要一个会话，却能把下游全部重新定标。

为什么 aiter 的反向更快：块尺寸是不对称的

这不是调度差异，是切块方式的差异——而 turbo 目前表达不了这种切法。

turbo 反向aiter 反向
dkdv 的块FIXED_BLOCK_M = FIXED_BLOCK_N = 64BLOCK_M1=32，BLOCK_N1=128
dq 的块同样这两个常量BLOCK_M2=128，BLOCK_N2=32
形状对称，模块级硬编码常量不对称，且成对：N1==M2、M1==N2
其他—waves_per_eu=1、BLK_SLICE_FACTOR=2

aiter 的反向两半互为转置：dkdv 那一半用短的 query 块（32）配长的 key 块（128）， dq 那一半反过来，长 query（128）配短 key（32）。 两半各自都在自己需要的那根轴上拿到了长块。而 turbo 两半共用一个 64×64 的对称块， 结果是两半都不合身。 那个成对关系（N1==M2、M1==N2）正是第 09 节那个"改 BLOCK_N1 就把 dq 算错"陷阱的同一根绳子——两半共用一个启动网格。

turbo 不能简单地把 64 改成 128：那个数字是一份跨内核的接口约定

dkdv 的 BLOCK_M 不是旋钮，是 ABI。它被四段代码同时绑住： attn_fwd 把 LSE 写在偏移 m*BLOCK_M*2； _bwd_preprocess_use_o 把 delta 写在同一个块的 +BLOCK_M 处； host 侧的 _lse_delta_views 按这个布局把两份视图还原出来； _bwd_kernel_dkdv 读 2*start_m + tl.arange(0, 2*BLOCK_M) 再用两次 tl.gather 拆开。

单独改这个常量不会崩——它会把 lse 行和 delta 行接在一起返回， 产出平滑地错掉的 dk/dv。只有四张量 SQNR 门能抓到。 把这套 ABI 解耦，就是目前正在做的工作，也是一切"照着 aiter 的形状试"的前提。

解耦成功之后能拿到多少？纯算术，不是实测：turbo 的前向（4.152 ms） 加上 aiter 的反向耗时（27.888 ms）＝ 32.04 ms／ 240.2 TFLOP/s 推导， 离 flex 和调优后的 aiter 都只差约 3%。 这就是这块奖品的诚实大小：追平，不是赢。

更正：316.1 TFLOP/s／24.347 ms 没能复现

第 06 节那张图里"aiter Triton +2 整数 = 24.35 ms"、以及第 07 节的 316.1 TFLOP/s， 来自更早一次 op-evolve 测量，一直被当作 aiter 的既定水平在用。 它复现不了。本次实测是 31.207 ms／ 246.6 TFLOP/s。

差距全部在反向：前向当时约 3.272 ms，今天 3.260——精确复现； 反向当时 21.075 ms，今天 27.947， 差 6.872 ms，正好等于总时间的差（6.860 ms）。

机制：上游 aiter 自己把反向重新调过了。那个旧数字来自另一个 aiter 版本。 两条证据：aiter 的前向 num_stages 1→2 至今精确复现 （6.676 → 3.260，2.05×）；而 aiter 的反向 num_warps 4→2 在今天的 aiter main 上已经完全没用了（27.888 → 27.947，是噪声）。 这个旋钮在旧版本上确实是真收益，上游后来把反向换到了一个已经把它吃掉的配置上。

处理办法：把 24.347 ms／316.1 TFLOP/s 从所有目标和对比里撤掉。 aiter 在这张卡、这个时钟下的当前水平是 31.207 ms／246.6 TFLOP/s， 任何由 316.1 推出来的阶梯数字都要重算。

这件事改变了什么，没改变什么

改变的：

  • 冠军配置照样落地。它比出厂默认快 1.64×，只改两个整数、不碰一行内核代码， 2,300 次调用逐位确定，端到端也不是回归。它只是不再是终点线。
  • 停止在 turbo 的调度旋钮上继续投轮次。已经榨干了： waves_per_eu 只有 0 能用（2 和 4 直接掉到 54.9／104.4 ms）， 反向 num_stages>1 更差，三次源码改写的结果是 −9%／持平／持平，全部回滚。 "dkdv 寄存器溢出"这个头号假设也被推翻——num_warps 2／4／8 的溢出计数都是 0，只有 1 才溢出（512）。所以 dkdv 卡的是每个 program 的效率，不是寄存器。
  • 下一个工作项是 LSE/delta 的 ABI 解耦。反向后面所有事都排在它后面。
  • 目标阶梯要重新定标：turbo 反向的近期现实目标是 aiter 的 27.9 ms， 不是 flex 的 23.8 ms。顺便记一笔：flex 的反向仍然是这张卡上最快的， 比 aiter 还快 1.17×，目前没人能解释为什么。
  • "在 gfx1250 上直接派发到 aiter 的 Triton 后端"现在是一个正经选项， 应该和"继续自研"放在一起算账。turbo 后端真正的价值一直是 "一条在 gfx1250 上前向反向都正确、而且我们能改的代码路径"—— 这个价值不因输掉对照实验而消失，但它不是一条性能论据。

没改变的：

  • 端到端那个结果的含义一个字都没变。turbo 245 tps vs flex 244 tps 只说明打开 turbo 不是回归，仅此而已。在这个镜像上，整条注意力路径是 36.4 ms × 32 = 1.16 s，占 133.7 s 一个 step 的不到 1%； 瓶颈是没有能用的 BLAS（rocBLAS bf16 27.4 TFLOP/s 对 1002.7 的上限）。 端到端在这台机器上根本察觉不到 turbo 输掉了这次对照实验，两个方向都察觉不到。
  • 限频仍然压倒一切。上面每一个数字都是 1100 MHz 下测的， 而 2026-09-04 同一张卡能跑 1699–1703 MHz。这条平台工单的价值高于本节任何内核结论。
  • 已被否掉的仍然否掉：sequence_parallel=False 是静默算错（只算 1/128 的梯度）、 XCD 重映射会更慢、FlyDSL 装不上且拒绝 G=4、AITER 的 CK fmha 是 CDNA 专用。
01

先把 attention 是什么讲清楚

如果你没写过 GPU kernel，下面这三句话足够读懂全文。

大模型每一层都要做一次注意力（attention）：让序列里每个词去"看"它前面所有的词， 算出该关注谁。序列长度是 8192，所以这是一个 8192 × 8192 的关系矩阵。 因为词只能看前面的（叫 causal，因果掩码），实际只用算一半。

朴素做法要把这个巨大矩阵完整存进显存，装不下。 Flash Attention 的办法是切成小块（tile），算一块丢一块，只保留累加结果。 所以"优化 flash attention"很大程度上就是选对块的大小、选对每块用多少线程、让搬数据和算数据重叠起来。 本文后面反复出现的 BLOCK_M / BLOCK_N / num_warps / num_stages 就是这四件事的旋钮。

训练比推理多一步：算完还要反向传播求梯度。反向的计算量大约是前向的 2.5 倍， 实测在这张卡上占了注意力总时间的 73–76% 实测。 所以这场优化的主战场是反向，不是前向。后面所有轮次安排都围绕这一点。

02

JIRA 里需要更正的三件事

原始 JIRA 的方向是对的——瓶颈确实在注意力。但具体归因有三处和代码、日志对不上， 而这三处恰好决定了我们该做什么。

更正一：patch 并没有"被跳过"，它是被应用之后崩了

JIRA 说 turbo_attention 补丁在 MI455X 上"Skipped（条件不满足）"。 但那个补丁的启用条件只检查两个配置开关，完全没有架构判断、没有 aiter 检测、没有 head_dim 检测 （attention_patches.py:22-31）。在默认配置下它在 MI455X 上是被正常应用的， 然后在第一个训练 step 死于 ModuleNotFoundError: No module named 'aiter' 实测。日志里那行 "⊘ Skipped" 来自后来有人手工加的 use_turbo_attention: false——那是规避手段，不是原因。

这条更正的后果很实际：JIRA 的第一条请求"在 gfx1250 上启用 AITER fmha"走不通。 aiter 的 fmha 反向落到 CK 库，而 CK 是 CDNA 专用的；在 gfx1250 上前向能过、 反向会在训练中途报 invalid argument for fmha_bwd。这不是配置问题，是库里就没有这个架构的内核。

更正二：今天打开 turbo_attention，是性能倒退 1.85 倍

同一形状、同一份 benchmark 日志里 实测：flex 走完一次前向+反向是 31.508 ms，而 turbo 的 Triton 后端要 58.424 ms。 新加的 gfx1250 Triton 后端（提交 c1325c7e）的价值是"终于有了一条在 gfx1250 上 前向反向都正确、而且我们能改的代码路径"，不是性能。它现在是我们的落地点，不是起点。

更正三：那 245 ms 的 elementwise，换内核不会让它消失

JIRA 把 245 ms 的 elementwise（"dtype cast ×492"）算进注意力的差距里。但算术不支持： benchmark 里 flex 一次前向+反向的全部 elementwise 开销是 0.399 / 31.857 ms = 1.25%， 折算到一个 step 约 12.8 ms，不是 245 ms，差了 19 倍 推导。

它实际上是模型层里没被融合的 RoPE 位置编码（xq.float() / view_as_complex / type_as）加上 layout 转置——因为 MI455X 的复现配置里设了 compile.enable: false。预计其中 45–85 ms 能靠一个原生 BSHD 布局的后端顺手省掉， 剩下 160–200 ms 需要打开 torch.compile 或写一个融合 RoPE，那是另一张单子。 注意：原始 trace 文件不在仓库里，"492" 这个数字在磁盘上搜不到，所以这个拆分是推导，不是实测。

硬件现实：这张卡被限频了

这是整份计划里最重要、也最容易被忽略的一条，它决定了目标该定在哪。

同事的前期探测（op-evolve Phase 1）实测发现：这张卡的 amdgpu 在每次启动时都会打印 GPU is throttled, expect performance decrease. VR.，时钟表被截断到只剩两档 500 MHz 和 1100 MHz。同一张卡在 2026-09-04 还能跑到 1699–1703 MHz， 现在最高 1100 MHz——差约 1.65 倍 实测。

功耗只用到 49%，GFX 活动率却是 100%——说明这张卡跑注意力时是被时钟卡住的，不是被功耗卡住的。 这有一个直接推论：延迟隐藏类的优化（让搬数据和计算重叠）在这里应当按面值计分， 不需要像在 CDNA 上那样打折扣。

于是：JIRA 的 30k tps 目标在当前时钟下数学上不可达

30,000 tps 意味着注意力路径要从 755 ms 压到 192 ms，等效 246.29 TFLOP ÷ 0.192 s = 1282.8 TFLOP/s 推导。 而实测算力上限是 1002.7 TFLOP/s——目标是上限的 128%。 一个注意力内核不可能超过同一块硅片同一时钟下稠密矩阵乘法的上限。

即使限频解除（推断上限 ~1580–1690 TFLOP/s），仍需要 76–81% 的峰值利用率， 而 MI355X 在同样负载上也只做到 31%。所以我们重新标定了目标，见下一节。

05

选哪个后端：证据摆在这里

之前有同事建议"先用 FlyDSL，不行再考虑 Triton"。方向上可以理解——FlyDSL 是团队的战略后端， 在 gfx950 上有全仓库最高的实测天花板。但对这块芯片 + 这个模型， 有三个各自独立、任何一个都足以否决的硬阻断：

  1. FlyDSL 的注意力内核在非 gfx950 上是 build 时直接 raise 的，不是回退。 它用了 ds_read_tr16_b64——一条 CDNA4 专属的 LDS 转置读指令，gfx1250 上没有对应物。 反向的七个 builder 每一个都断言 gfx950。
  2. gfx1250 构建时根本不安装 flydsl（setup.py:529-535， 注释写着 "flydsl 0.2.4 does not support gfx1250"）。
  3. 就算能跑，它也会拒绝我们这个模型。_gqa_group_ok 要求 GQA 分组数 G = Hq/Hkv 是 [8,256] 区间的 2 的幂；Llama-3.1-8B 是 32/8 = G=4。 FlyDSL 在任何架构上都会拒绝这个 shape，MI355X 上也一样。

另外从 gfx950 移植到 gfx1250 不是"移植"而是"重写"：wave64→wave32、MFMA→WMMA、 AccVGPR 消失、buffer_load_lds→TDM、160KB→320KB LDS。 FlyDSL 前向的全部价值是一套为 wave64 MFMA 手工排的 14-cluster 调度，一行都不转移。 而它在新架构上的失败模式是全仓库最差的：TDM gather 有记录在案的硬挂（需要重启机器）。

07

为什么我们相信还有很大空间

因为这些内核的配置从来没有被搜索过一次。这不是猜测，是读代码读出来的：

  • turbo 的 Triton 内核：FIXED_BLOCK_M = FIXED_BLOCK_N = 64 是模块级 Python 常量， 不是可调参数。
  • 前向的 "autotune" 列表里只有一个配置：num_stages=1, num_warps=4。 反向同样只有一个。_bwd_preprocess_use_o 连 autotune 装饰器都没有。 也就是说 @triton.autotune 在这里只是个编译缓存，从没搜索过。
  • aiter 那边更直接：gfx1250-MHA-DEFAULT.json 与 gfx950-MHA-DEFAULT.json md5 逐字节相同——它就是一份拷贝。

这些配置全部原样继承自 CDNA 目标（wave64 / MFMA / 64KB LDS）。 而 gfx1250 是 wave32 / WMMA / 320KB LDS / 256 CU。 在这里 num_warps=4 是 128 条通道而不是 256 条； num_stages=1 意味着完全没有软件流水—— 而这块芯片的招牌特性恰恰是异步数据搬运引擎（TDM）。

最有力的先验：两个整数换来 1.401 倍

同事在 aiter 的 Triton 内核上只改了两个整数——前向 num_stages 1→2， 反向 num_warps 4→2——耗时从 34.111 ms 降到 24.347 ms，其中前向单独一项就是 2.06 倍 （6.665 → 3.234 ms），而且 out/dq/dk/dv 四个张量的 SQNR 精确到小数点后四位都没变， 峰值显存还少了 33% 实测。

两个不同的 Triton 注意力内核，都在出厂时带着从别的架构拷来的配置， 都在头两个旋钮上留了 1.4–2 倍。这是我们能拿到的校准最好的先验。

但这段里的 24.347 ms／316.1 TFLOP/s 已被证伪：今天重测是 31.207 ms／ 246.6 TFLOP/s，差额全在反向（21.075 → 27.947 ms），因为上游 aiter 已经把反向重调过。 前向那一项（2.05×）仍然精确复现，所以"出厂配置留了大倍数"这个先验本身仍然成立。见第 00B 节。

08

执行计划

分四个阶段。Phase 0 完全不需要 GPU——这台机器上可能有别人在用， 而且这张卡目前状态存疑，所以先把所有离线能做的做完。

Phase 0

不需要 GPU 的准备工作

现在就能开始

0.1 修三个真实的派发 bug。这些不修，任何内核成果都到不了训练 step：

  • DenseAttnFwdAiterBackend.can_handle 对任何 4 维 bf16/fp16 张量无条件返回 True， 而回退扫描按字典插入序进行，AITER 永远排在 TRITON 前面—— 所以 gfx1250 上那个唯一能用的 Triton 后端，默认永远不会被选中。
  • _flydsl_common_ok 用 compute_capability >= (9,5) 判断， 而 gfx1250 报 (12,5)，这道门是通的。 目前只是靠 Llama-3.1-8B 的 G=4 偶然挡住；任何 G∈{8,16,…} 的模型今天就会在 gfx1250 上 派发到 FlyDSL 然后在 gfx950 的 JIT 里硬崩。
  • dense_backward 传 dq/dk/dv=None，于是按 fp32 分配——bf16 输入拿回 fp32 梯度。 能抓到它的测试被 tests/conftest.py 在 gfx1250 上整体 skip 掉了， 所以这条路径至今没有任何 CI 覆盖。

0.2 把种子代码 vendor 进来，搭测试台。复用 op-evolve Phase 1 已有的 E2_correct.py（可用的 fp32 参考实现）和计时脚本。 丢掉 mha_fused_bwd.py——它的 dk SQNR 是 −0.22 dB，误差能量超过信号能量， 而且更慢。

0.3 写好自动调优 job 的配置。基线用 aiter 出厂配置，对照组用 flex 且 每一轮当场重测（不用存档值——这张卡的时钟状态正是存疑的东西）。

0.4 平台线并行推进：把 VR 限频问题升级给平台/BMC 负责人。

0.5 FlyDSL 限时调研（≤3 天，只读）：产出一份"可借鉴／不可借鉴"清单，不产出内核。

09

已经踩过的坑，测试台必须内建防线

下面每一条都是同事实际踩过、有日志为证的。它们不是"注意事项"，是必须写进代码的断言。

最危险的一条：有些配置"又快又错"

反向内核的启动网格由 BLOCK_N1 决定，但这个同一个网格同时喂给了 dq 那一半 （它按 BLOCK_M2 切分）。把 BLOCK_N1 从 128 提到 256，网格就减半， dq 只覆盖了一半的 query 行：

配置耗时dq SQNRdkdv判定
基线（gfx950 拷贝）27.744 ms52.2552.3152.73正确
BLOCK_N1=256 单独改21.110 ms9.5952.3152.73错，但看起来快 1.31×
BLOCK_M2=64,BLOCK_N2=6421.773 ms9.5952.3152.73错，从另一侧
BLOCK_N1=256 + BLOCK_M2=256 成对21.639 ms52.2552.3152.73真的快 1.28×

注意 dk 和 dv 全程完好，只有 dq 坏了。 一个只看输出、或者只看 dk/dv 的正确性检查会奖励这个错误配置。 仓库现有 benchmark 的 max-abs 检查对所有后端都返回同一个 8.011e-03， 而且根本不看梯度——它抓不到任何一个。

防线：正确性检查必须对 out / dq / dk / dv 四个张量分别算 SQNR， 对 fp32 参考，阈值 50 dB（bf16 的地板约 55.6 dB，正确实现落在 52–54 dB）。 关键不是阈值，是覆盖面。

其余四条防线

  • 配置缓存：aiter 的 _get_config 是 @lru_cache 的—— 覆盖配置不调 cache_clear() 会静默无效。 症状是一整轮 sweep 里所有配置返回同一个时间（同事真的遇到过：27.45–27.49 ms 一路平到底）。 每次计时前必须清缓存并断言取回的配置就是设置的配置。
  • 禁止 PC sampling——在包装层硬禁，不靠人自觉。三次尝试三次 GPU fault， 其中一次把驱动搞到 wait for reset ack，需要重启机器。 而且健康检查不能调用 rocm-smi（它自己会卡在 D-state）， 改用 dmesg 抓 MES( / GPU Hang。
  • 每个候选独立进程，rc=139 当作重试并记录次数—— flex 的反向有约 2/12 的概率 page fault 直接杀进程，而对照组每轮都要重测。
  • 赢在边界要自动扩范围：一个 sweep 的赢家落在参数范围端点，说明没收敛。

还要防"基准测试过拟合"

aiter 的配置缓存是按激活张量做 key 的，而真实训练每次 Q/K/V/dO 都是新的， 命中率是 0。这意味着微基准上的收益可能完全不转移到训练。 所以每个被接受的轮次都要附一条"真实训练可转移性检查"，并且 Phase 3 的端到端验证不可跳过。

10

另一件事：这张卡的观测能力很差

这会影响我们的方法选择。rocprofv3 在这个镜像里对 gfx1250 只列出 51 个硬件计数器、0 个派生指标（gfx950 有 630 个）。 其中实际请求的 27 个里只有 8 个返回非零， 而 TCC、TCP、TA、TD、EA、LDS、GL2C 这些访存相关的块完全不存在。

后果很直接："这个内核是算力受限还是访存受限"这个分析在这张卡上做不了， 因为没有任何一级缓存或显存的字节计数器。所以我们的策略是 多做便宜的 A/B 实测，少做昂贵的 profiling 分析—— 反正已知的收益形态就是"改两个整数"，那正好适合 A/B。

一个会骗人的陷阱

如果把一个不存在的计数器和一个有效的混在一起请求，rocprofv3 会 返回 0、生成格式完全正确的 CSV，只是那个缺失的计数器整列不见了—— 不是补零，是根本没有。唯一能发现它的办法是对结果列名做集合相等检查。

值得一试：宿主机的 ROCm 7.15 为 gfx1250 定义了 233 个计数器。 在 Phase 1 顺手跑一次 GL2C_EA_RDREQ_64B——如果新版 SDK 让访存计数器可用， 深度分析的价值会大幅回升，轮次安排要相应调整。

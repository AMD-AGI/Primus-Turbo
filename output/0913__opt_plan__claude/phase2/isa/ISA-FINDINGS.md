# 离线 ISA 分析：不用 GPU 得到的四个结果

卡 wedged 期间做的。`docker exec` 已经失效，但 `docker cp` 还能用，而**今天跑过的每一个内核的
编译产物都躺在容器的 Triton 缓存里**（220 MB，211 个条目，43 个融合反向变体）。
编译产物包含 `.source`/`.ttir`/`.ttgir`/`.llir`/`.amdgcn`/`.hsaco` —— 也就是说，
**今天所有测量的机器码都可以事后离线解剖，不需要卡是活的。**

紧凑证据保存在 `bwd-isa-census.jsonl`（43 行，每行一个编译变体）。

---

## 1. E2 已死：`tl.trans` 消除不值得做，省下一整项 GPU 工作

TODO 里 T3/E2 写着「先花 15 分钟 dump ISA 看后端是否发 `ds_load_tr16_b128`，
**这一个检查决定它值 2% 还是 10%**」。

检查做完了，答案是**两者都不是，是 0%**。冠军内核的 ISA 里：

```
ds_load_tr16_b128   32      <- 后端已经在用 gfx1250 的转置加载
ds_load_tr16_b64     0
ds_read_b128         0      <- 一条普通 LDS 读都没有
ds_read_b64          0
```

四次 `tl.trans` 已经被后端**免费折叠进 LDS 转置加载**了。源码层面手工消除它们，
消除的是一个已经不存在的开销。**E2 关闭，不要在明天的 4 卡机上花时间。**

## 2. 冠军内核在 spill —— 而且 VGPR 溢出的税比 spill 本身更贵

冠军（`BLOCK_M1=32 N1=256 M2=256 N2=32 BSF=1 warps=4`）：

```
vgpr_count          1024     <- 硬上限，顶满
scratch_store       113      \  spill
scratch_load        245      /
s_set_vgpr_msb     1834      <- 占全部 11,665 行的 15.7%
v_wmma_f32_16x16x32_bf16  448
```

`s_set_vgpr_msb` 是 gfx1250 用超过 256 个 VGPR 时的**存储体选择指令**，纯开销，不算数。
**它的条数是 WMMA 的 4.1 倍。** 每发一条有用的矩阵指令，就要发四条纯粹用来切寄存器组的。
这比 358 条 spill 访存更值得关注，而且此前完全没被注意到。

## 3. 一条干净的结构性规律：spill 是二值的，不是渐变的

43 个变体里：

| VGPR | spill |
|---|---|
| 352…951（21 个变体） | **全部恰好为 0** |
| 1024（顶满，14 个变体） | **全部 spill**，从 28 到 1814 条不等 |

没有中间态。编译器要么装得下，要么顶满然后开始往 scratch 倒。
这意味着 **VGPR 是否等于 1024 本身就是一个可以离线读出的、二值的健康指标**。

## 4. `waves_per_eu=0` 是一个从未测过的真旋钮，代价为零

缓存里有同一个配置的两次编译。一开始看起来像编译器不确定性，
但逐字段比对后**不是**——`.source` / `.ttir` / `.ttgir` 逐字节相同，
`.llir` **只差一行函数属性**，JSON 只差一个字段：

```
waves_per_eu:  A=0（不设，交给编译器）   B=1（当前出厂值）
```

这一行属性产生了 **10,831 行不同的机器码**：

| | waves_per_eu=0 | waves_per_eu=1（现用） |
|---|---:|---:|
| 总指令数 | **8,793** | 8,983 |
| `s_set_vgpr_msb` | **1,689** | 1,853 |
| spill st/ld | 167 / 293 | 164 / 287 |

不设比设死少 2.1% 指令、少 8.9% 存储体切换，代价是多 3 条 spill 存储。
**净向好但不是定论**，需要一次 GPU A/B。零代码改动（配置字典里删一个键）。
这也是 T4 那 1.85 ms 差的一个可信机制候选——量级同阶。

## 对明天 4 卡机的直接影响：先离线筛，再上卡

最有价值的不是上面任何一条，而是**方法**：

Triton 编译**不需要 GPU**（只需要 LLVM 后端）。所以候选配置可以先编译、
离线读出 `vgpr / spill / s_set_vgpr_msb / wmma / 总指令数`，
**只把不顶满 1024 VGPR 的候选送上卡去测**。

今天那些以 1600–1900 条 spill 收场的配置（`M1_16_N1_128`、`BSF=4`、`N1_512`…），
每一个都烧掉了真实的 GPU 分钟数才被判死，而它们在**编译期就能看出来**。
10 小时的 4 卡预算下，这个前置筛子值的钱可能比任何单个旋钮都多。

# 离线预筛工具：`tools/gfx1250/isa_screen.py`（已验证，有明确的适用边界）

上面第 5 节说「先离线筛，再上卡」。这一节把它做成了工具，**并且验证了它——结果不是满分。**

## 能跑起来的关键

`docker exec` 对 wedged 容器失效，但**可以用同一个镜像起一个全新的、不挂 `/dev/kfd`
和 `/dev/dri` 的 CPU-only 容器**。Triton 3.6 在里面可以为 gfx1250 编译，
只是 `JITFunction.warmup()` 不可用（`0 active drivers`），所以必须手搭 `ASTSource`。

## 手搭 ASTSource 必须复刻运行时的特化，否则筛子会骗人

初版没有复刻，结果与缓存真值差 4 倍：

| | 手搭初版 | 加 divisibility | **加 divisibility + 折叠单位 stride** | 缓存真值 |
|---|---:|---:|---:|---:|
| 总指令 | 47,067 | 44,050 | **11,557** | 9,565 |
| `ds_load_tr16_b128` | 128 | 128 | **32** | 32 |
| spill | 259 | 252 | **328** | 358 |
| wmma | 448 | 448 | 448 | 448 |

两件事各自必需：指针与非单位 stride 标 16 字节整除，**以及**把最内层的单位 stride
折成常量。少任何一个，编译出来的都是另一个内核。
（顺带一提：`Sink`/`Alibi`/`cu_seqlens`/`Descale` 这些实参为 `None` 的指针做不做特化，
影响 11,558 → 11,557，可以忽略——它们已经被 constexpr 开关挡掉了。）

## 验证：23 个有真值的配置，逐个比对

绝对指令数仍差 ~20%，**没有对齐，也不打算对齐**——筛子的用途是判定，不是预测。
按用途验收：

| 判定 | 一致 |
|---|---|
| 「顶满 1024 VGPR」 | 20 / 23 |
| 「是否 spill」 | 19 / 23 |
| **「是否灾难性 spill（> 1000 条）」** | **22 / 23** |

**三处不一致全部落在 `M1=64 N1=128` 一族，且方向是偏悲观**
（预测 vgpr 1024 + spill 133，真值 880 + spill 0）。
偏悲观对筛子是**危险方向**：拿它做硬性拒绝会误杀一族真正装得下的配置。

## 所以它该怎么用

**只当灾难探测器，阈值 1000 条 spill，不当细粒度排序器。**
今天以 2400–3800 条 spill 收场的六个配置（`M1_16_N1_128`、`M1_16_N1_256_BSF2`、
`BSF=4`、`N1_512`、`M1_128_N1_256`、`w=2`），**六个全部被正确预测**，
而它们每一个都烧掉过真实 GPU 分钟。少于 1000 条的区间它不可靠，那部分仍要上卡测。

用法：

```bash
docker run --rm -v /home/lihuzhan/code:/home/lihuzhan/code \
  -w /home/lihuzhan/code/2026_0903__turbo/Primus-Turbo fa-tune:deps \
  python tools/gfx1250/isa_screen.py --grid default --out screen.jsonl

# 重新验证（任何时候改了工具都要重跑）
  python tools/gfx1250/isa_screen.py --validate .../bwd-isa-census.jsonl
```

# 64 配置全网格离线筛选结果（`screen-default.jsonl`）

## 更正：`waves_per_eu` 的影响远小于我上面说的

上一节我写「一行属性产生 10,831 行不同的机器码」。**这个说法误导了——包括误导了我自己。**
diff 的行数主要由指令重排贡献，不等于差异的量级。

网格里有 32 对「`waves_per_eu=1` vs 不设」的同配置对照：

| | 中位数 | 最大 |
|---|---:|---:|
| 总指令数变化 | **0.00%** | 1.32% |
| `s_set_vgpr_msb` 变化 | **0** | 139 |

**一半的配置对上这个旋钮一条指令都不差。** 缓存里那对 2.1% 的差是分布的尾巴，不是典型值。
**T1b 降级**：仍然可以顺手测（零成本），但不要再当成「有希望的免费收益」。
解析器的修复仍然是必要的——这个设置此前**根本无法从调优 harness 到达**。

（这条更正本身也是筛子的价值：一个需要 GPU 的实验被一次离线编译降级了。）

## 主结果：16/64 在碰到卡之前就被判死

16 个配置 spill 超过 1000 条，按上一节验证过的阈值（22/23 准确）判为灾难，**不上卡**。
48 个进入基准测试。按今天每个配置约数分钟的测量成本，这是明天预算里实打实的一块。

## `num_warps=8` 有 ISA 支持——这是 T1，应当第一个测

在**冠军自己的 tile 家族**（32/256 bsf=1）内比较：

| num_warps | num_stages | vgpr | spill | `s_set_vgpr_msb` |
|---:|---:|---:|---:|---:|
| **4** | 1 | **1024（顶满）** | 328 | **2,299** |
| 4 | 2 | 1024 | 659 | 3,425 |
| **8** | 1 | **512** | 426 | **715** |
| 8 | 2 | 512 | 650 | 1,450 |

`num_warps=8` 把 VGPR 从硬上限降到 512，**存储体选择指令少 3.2 倍**，代价是 spill 从 328 升到 426。
这正是 T1 预测的方向，现在有了编译期证据。`num_stages=2` 在两种 warps 下都明显更差，
与「已知悬崖」一致。

## 一个必须记住的读表限制

**不要跨 tile 家族比较 `wmma` 条数。** 表里 32/128 的配置 wmma 只有 96–224，
32/256 的有 448——那是因为 tile 变小后每个 workgroup 干的活变少、workgroup 数量变多，
**不是**它算得少。筛子只在同一 tile 家族内部（比 warps / stages / wpe）有排序意义。

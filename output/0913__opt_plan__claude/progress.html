02

优化历程：三次假设被推翻

这条路上真正有价值的不是找到的配置，而是被实测推翻的假设—— 每一次推翻都把方向修正了一次。

第一步：配置调优（59.6 → 36.4，1.66×）

内核的 @triton.autotune 列表里只有一个配置，而且是从 CDNA （wave64 / MFMA / 64KB LDS）原样继承的——gfx1250 是 wave32 / WMMA / 320KB LDS。 num_warps=4 在这里是 128 条通道不是 256，num_stages=1 意味着 完全没有软件流水，而这块芯片的招牌特性就是异步数据搬运。

两个整数：前向 num_stages 1→2（单项 2.4–2.6×）、 反向 num_warps 4→2（1.54×）。数值精度逐位不变。

第二步：假设「非对称 tile」—— 被推翻

aiter 的反向用非对称 tile（32×128），turbo 用对称的 64×64，而且 turbo 的 BLOCK_M 被一个跨内核的 ABI 绑死了。于是做了解耦，让 tile 可自由设置。 结果：

tile反向 ms对比 64×64
64×6432.447基准
32×6435.545+10%
128×6443.719+35%
32×128（aiter 的）51.563+59%
32×256125.998+288%

64×64 本来就是最优，而 aiter 自己的 tile 在 turbo 内核里慢 59%。 假设被彻底推翻。

第三步：profiler 定位真因 —— 内核融合

实现结构反向
turbo两个内核：dkdv 18.96 + dq 11.2630.6 ms
aiter一个融合内核27.7 ms

核心洞察：tile 偏好是内核结构的属性，不是形状的属性

同一个方向（把 K 轴 tile 放大到 256），在 turbo 的非融合内核里是灾难 （126 ms），在 aiter 的融合内核里是胜负手（反向 1.26×）。 两个方向都被实测证明了。

所以结论不是「换个参数」，而是必须换结构——这也是最终决定 vendor 融合内核的依据，是 1.75× 的实测差距，不是论证。

第四步：找到真正的杠杆（和预期的不一样）

原本预期杠杆是 BLOCK_M1（因为 flex 和 aiter 的配置只差这一项）。 M1 几乎无关。真正的两个杠杆是：

杠杆改动反向收益
BLOCK_N1 / BLOCK_M2（K 轴 tile）128 → 2561.26×
BLK_SLICE_FACTOR2 → 11.20×

合起来反向 27.85 → 18.42 ms，1.51×。

03

方法论：抓到的两次「静默失效」

这一节是整个过程里最该被记住的部分——两次差点把错误结论写进报告。

一、又快又错的配置

某个配置返回 out 53.67 dB ✓、dq 52.24 dB ✓、dk −inf ✗、dv −inf ✗—— 输出和 dq 完全正常，dk/dv 被毁掉。只看输出的检查会直接放过它。

同类陷阱还有：反向的启动 grid 由 BLOCK_N1 决定，而同一个 grid 也喂给按 BLOCK_M2 切分的 dq 那一半。破坏配对会让 dq 只覆盖部分 query 行—— 测出来更快。现在这个配对在调度前就被断言拦下。

规则：正确性门必须分别覆盖四个张量。关键不是阈值，是覆盖面。

二、覆盖没生效，而我自己的断言放过了它

一轮 sweep 的六个配置结果只差 0.6%——这正是「覆盖没生效」的特征。 原因：配置函数在一个模块里，但调用方在导入时做了 from … import _get_config，把名字绑进了自己的模块。 patch 源模块后，_get_config() 老老实实返回新值，launch 用的还是旧值。

我的断言验证的是「配置源返回了我要的值」，而不是「内核确实用这个值跑了」。 两者在任何持有独立引用的地方就会分叉。

定案靠的是内核名字——aiter 把 tile 尺寸编进了 kernel name： bwd_kernel_causal_BLOCK_M1_32_BLOCK_N1_256_…。 规则：在 launch 处验证，不在源头验证。 那一轮的十二次测量作废重跑，重跑后才出现了真正的突破。

05

下一步规划

  1. 接 dispatcher（带 shape gate）。用上表的交叉点做门控，补 gfx1250 测试。 这是让成果真正生效的一步——目前还要靠环境变量。
  2. 再跑一次 bake-off。vendor 之后必须重测，不能假设移植保持了性能。 已做 树内 316.1 已验证。
  3. 补前向的 0.9 ms。turbo 4.15 vs aiter 3.26，两个都是 Triton 前向。 配置已扫遍（num_stages 2/3/4、num_warps 1/2/4/8、PRE_LOAD_V 都不动）， 说明是结构差异，可能也要 vendor 前向。
  4. 查 vendored 与纯 aiter 的 1.8 ms 差（反向 20.2 vs 18.4）。 怀疑是 packed LSE 的 gather 开销——Primus-Turbo 的前向写的是 [B,Hq,2*Sq] 交错布局，融合内核要的是稠密 [B,Hq,Sq]。
  5. HipKittens udna1 路线。仓库里已经有完整的 gfx1250 移植 （3rdparty/hipkittens/include/udna1/，72 个头文件，WMMA 16×16×32、TDM 描述符、 split wait counter 都接好了），只差 attention 内核。这是 Triton 撞到天花板后的现成地基。

两个不是代码能解决的阻塞项

① VR 限频，值约 1.65×。重启没有解除， MAX_CLK 仍是 1100 MHz（这张卡 9/04 还能跑 1699 MHz）。 本页所有绝对数字都在限频态下。

② 缺失的 gfx1250 BLAS，值约 37×。 稠密 GEMM 只有 27.4 TFLOP/s，而同一张卡同一次会话里注意力内核跑到 316—— 稠密 GEMM 比 flash-attention 慢 8 倍，方向是反的。 hipBLASLt 的 gfx1250 库在镜像里根本不存在。这导致端到端测不出 attention （attention 只占一个 step 的 1%），两个后端的 tps 差 0.4%。

# 阶段 2 · 前向 —— KV 块宽度扫描（2026-09-23）

计划里 S1 的头号候选是「`n_block` 64 → 128 →（评估 256）」，理由是
`MIN_KV_BLK_BYTES = 64 KB` 已经把 LDS 地板抬好、提到 256 一个字节额外 LDS 都不要，
而 **ASM 的 tile 恰恰就是 `128x256`**。

**用一个 10 分钟的同会话实验把它打死了**，而不是先花 58 分钟建作业再发现方向不对。

## 结果

同会话、轮转交错、每 rep 256 MiB L2 flush、n=20、先验 SQNR 后计时。

| 臂 | median | TF/s | SQNR | vs 出货 |
|---|--:|--:|--:|--:|
| aiter ASM（bar） | **1.576 ms** | 1416.9 | 53.62 dB | — |
| FlyDSL n_block=64（出货） | 2.400 ms | 930.7 | 51.63 dB | 1.000× |
| FlyDSL n_block=128 | 7.741 ms | 288.5 | 51.66 dB | **0.310×** |
| FlyDSL n_block=256 | 23.753 ms | 94.0 | 51.69 dB | **0.101×** |

**128 慢 3.2 倍，256 慢 9.9 倍。** 死因不是 LDS——LDS 确实一字节没涨，计划那半是对的——
是 **VGPR**。LDS 已经把占用率钉死在 1 WG/CU，8 wave/WG 摊到 4 个 SIMD 就是 2 wave/SIMD，
而 n_block=128 下每 wave 约 584 个 VGPR，2 × 584 = 1168 > 1024，直接溢出到 scratch。

## 第一次跑出来的是个空实验，不算数

第一版 harness 报出三个臂**时间与 SQNR 完全相同**、后两次「构建」耗时 **0.0 s**。
那不是「n_block 无所谓」，那是 **n_block 根本没传进去**：

- `n_block: int = DEFAULT_N_BLOCK` 是**关键字默认值，在 def 时就绑定**，事后改模块常量无效；
- `build_fmha_fwd_prefill_a16w16_m32x8` 上面有 `@functools.cache`，而 `_ensure_bshd_kernel`
  每次传的参数完全相同 → 直接返回同一个 kernel。

改成直接改 `__wrapped__.__kwdefaults__` 并 `cache_clear()`，才出现了真实的构建耗时
（0.1 / 4.1 / 8.2 s）和真实各异的 SQNR（51.63 / 51.66 / 51.69）。
harness 现在带两道绊线：构建耗时 < 0.5 s 报 SUSPICIOUS，所有变体是同一对象则直接中止。

> 规矩：**一个「无差别」的结果，先怀疑实验没生效，再怀疑机制没效果。**
> 三个不同 tile 尺寸给出小数点后两位完全相同的 SQNR，是不可能的巧合。

## 但它指出了正确的形状

| | Q tile | KV tile |
|---|--:|--:|
| aiter ASM bar | **128** | **256** |
| FlyDSL 出货 | 256 | 64 |

bar 不是「KV 块更大」，是**用减半的 Q tile 换来 4 倍的 KV 块**。
单独放大 KV 必然撞寄存器墙，因为 Q 那边的 O 累加器一分不让。

所以下一个实验是**联动**：`WMMA_ROW_PER_WAVE` 2 → 1（`BLOCK_M` 256 → 128，O 与 S 累加器同时减半）
与 `n_block` 一起扫，逼近 bar 的长宽比。

---

## 第二轮：联动 `(BLOCK_M, n_block)` —— 出货点是局部最优

`WMMA_ROW_PER_WAVE` 2 → 1 让 `BLOCK_M` 256 → 128，O 与 S 累加器同时减半。

| 臂 | BLOCK_M | n_block | median | TF/s | vs 出货 |
|---|--:|--:|--:|--:|--:|
| aiter ASM（bar） | 128 | 256 | **1.574 ms** | 1418.8 | — |
| **出货 R=2 n=64** | 256 | 64 | **2.364 ms** | 944.8 | **1.000×** |
| R=2 n=32 | 256 | 32 | 2.666 ms | 837.6 | 0.887× |
| R=1 n=64 | 128 | 64 | 3.143 ms | 710.7 | 0.752× |
| R=1 n=128 | 128 | 128 | 3.292 ms | 678.3 | 0.718× |
| R=1 n=256 | 128 | 256 | 24.799 ms | 90.1 | 0.095× |

**五个点把出货点围死了：它是这一族里的局部最优。**

但机制被证实了。**Q tile 一减半，KV 64 → 128 的代价从 3.2× 掉到 4.7%**
（R=1 时 3.143 → 3.292），正是寄存器压力那条解释所预言的。
只是砍 Q 本身要付 25%，比放宽 KV 赚回来的多——**换不划算，不是换不了**。

结论：**前向 1.51× 的差距不在 tile 形状上。** bar 和我们做同样的数学
（分块 causal 只多 0.78%），tile 长宽比这一族已经穷尽。
剩下的结构差异只有一条：**bar 是 4 个 wave、每个吃满 1024 个 VGPR、填充路径零 `buffer_load` 全 TDM**，
而我们是 8 个 wave、每个约 392 个 VGPR。

⚠ 下一组扫描带一个必须写在前面的**混淆**：所有 V2/V3 manager 在 `num_waves != 8` 时硬抛
`NotImplementedError`（`fmha_b16_buffer_managers.py:1015,1166,1252,1588,1748`），
所以 4 波臂**必须同时**退回 V1 loader 和 v1 O writer——一次改三样。
因此扫描里带了 8 波 + V1/v1 的对照臂，把 loader 的影响和波数的影响分开。

---

## 第三轮：波数 —— 在 aiter 这份代码里走不通

| 臂 | 结果 |
|---|---|
| `W8 R2 n64` TDM + O=v3（出货） | 2.392 ms |
| `W8 R2 n64` TDM + O=**v1** | **2.344 ms（快 2.01%）** |
| `W8 R2 n64` **V1 loader** + O=v1 | **编译失败** |
| `W4 R4 n64` V1 + v1 | **编译失败** |
| `W4 R4 n128` V1 + v1 | **编译失败** |
| `W4 R2 n64` V1 + v1 | **编译失败** |

失败全是同一条：

```
DSLCompileError: 'fly.ptr.load' op operand #0 must be ... but got '!llvm.ptr<3>'
```

**V1 loader 在 flydsl 0.3.2 下已经不能编译了**（它把 LDS 指针 `addrspace(3)` 喂给
`fly.ptr.load`，0.3.2 不再接受）。而 V2/V3 manager 在 `num_waves != 8` 时硬抛。
两边一夹，**4 波在 aiter 这份前向里无路可走**。

这是**路障，不是关于波数的结论**——不能记成「4 波更慢」。
对我们自己的前向 kernel 也不构成阻碍：那条「4 波 + 全 TDM」的路本来就要自己写，
bar 已经证明它能跑到 1401.5 TF/s。

## 一个顺手捡到的东西：`O_VARIANT`

出货是 `v3`，但文件自己的注释（`:147-150`）写着 **v1 是 "fastest so far"**。
20 次迭代下 v1 快 2.01%——**贴着噪声**（两臂 sd 1.5–1.6%，同码跨会话漂移过 1.5%），
所以单独用 101 次迭代重测，不拿 20 次的差值下结论。

## `O_VARIANT` 确认：v1 比出货的 v3 快 1.90%

101 次迭代、8 秒预热、其余参数完全相同：

| 臂 | median | TF/s | sd |
|---|--:|--:|--:|
| aiter ASM（bar） | 1.557 ms | 1434.0 | 1.39% |
| `O_VARIANT=v3`（出货） | 2.356 ms | 947.8 | 1.21% |
| `O_VARIANT=v1` | **2.313 ms** | **965.8** | 1.17% |

**1.90%**，与 20 次那轮的 2.01% 在两个独立会话里一致。

但两个臂的构建都只花了 0.0–0.1 s，**我自己的绊线响了**，所以没有直接采信，
而是用已经验证过的 `--pmc` 独立读了两个 kernel 的描述符：

```
O_VARIANT=v3   VGPR=224  SGPR=128  LDS=327680  scratch=0  wg=256  grid=1048576
O_VARIANT=v1   VGPR=232  SGPR=128  LDS=327680  scratch=0  wg=256  grid=1048576
```

VGPR 224 vs 232 —— **确实是两个不同的 kernel**，0.0 s 只是编译得快。结论成立。

### 顺带修掉一条失效的绊线

harness 里那条「所有变体是同一对象则中止」的检查**根本不可能触发**：
`_ensure_bshd_kernel` 每次都定义一个**新的** `_launch` 闭包，`id()` 必然不同，
无论底下的 kernel 是不是缓存命中。已改为追踪 `build()` **返回的对象**——
那个在缓存命中时才是真正共享的。

## 前向最重要的一个数，现在两边都实测了

| | wave/WG | 驻留 | LDS | VGPR/wave | **VGPR/SIMD** |
|---|--:|--:|--:|--:|--:|
| FlyDSL 前向 | 8 | 2 wave/SIMD | 327680 | **224** | **448 / 1024** |
| ASM bar | 4 | 1 wave/SIMD | 327680 | **1024** | **1024 / 1024** |

两边都独占整个 CU 的 LDS，`scratch=0`（都没溢出）。
但 **bar 在寄存器里存着 2.3 倍的状态**。

而 tile 一族已经证明：靠放大累加器去吃掉这些寄存器**换不划算**。
所以剩下的方向是 bar 实际在做的那件事——**2 路展开的 KV 循环、每 wave 每阶段 256 条 WMMA**，
即**深展开 / 软件流水**，而不是更大的 tile。

另有一个从未在前向试过、但在后向**两次都为正**的杠杆：
grid 是 1048576 work-item / 256 = **4096 个 WG**，而驻留只有 1 WG/CU、256 个 CU，
所以要跑 16 个批次；causal 下每个 WG 的工作量正比于它的 q 序号（1..32 个 tile），
**尾巴很贵**。后向 round 12 靠纯派发顺序拿过 14%，前向零接触。

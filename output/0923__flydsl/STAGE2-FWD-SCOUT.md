## fwd-kernel

I read aiter's gfx1250 FlyDSL forward prefill kernel (/home/lihuzhan/code/aiter-src/aiter/ops/flydsl/kernels/fmha_gfx1250/fmha_fwd_prefill_a16w16_m32x8.py, 2233 lines) and its companion fmha_b16_buffer_managers.py (1914 lines), plus flydsl's rocdl/gpu MLIR bindings under /home/lihuzhan/.local/flydsl032/. Everything below is STATIC READING — nothing was compiled or run, so every register count is a hand count of the traced IR, not a measured .vgpr_count. Four things stand out. (1) n_block is a real builder parameter with choices (32,64,128,256) but it is UNREACHABLE from the host API: neither _ensure_thd_kernel nor _ensure_bshd_kernel forwards it, so every launch gets DEFAULT_N_BLOCK=64. (2) The LDS budget is dominated by a 64 KiB-per-block floor (MIN_KV_BLK_BYTES); at n_block=64, d=128, bf16 the K and V tiles actually occupy 17,408 B and 18,432 B inside 65,536 B blocks — 73% of the KV slot is reserved headroom, and raising n_block from 64 to 128 costs ZERO additional LDS bytes. 256 costs +24 KiB and still fits. (3) The VGPR cost is where n_block is paid for: the K and V ds_load bursts are each 2*n_block VGPRs per wave, so per-wave live pressure goes ~392 -> ~584 -> ~968 at n=64/128/256, and 2 waves/SIMD (the waves_per_eu=2 hint) survives only at 64. (4) _named_barrier_pair is a literal no-op (`del warp_idx`); the LO/HI warp split today only reorders each wave's own load/prefetch around the full-workgroup gpu.barrier() in _drain_barrier. The bindings needed for a real implementation exist (rocdl.s_barrier_init / s_barrier_signal_var / s_barrier_wait, gpu.initialize_named_barrier), but s_barrier_wait takes a compile-time I16 id attribute, so a runtime `warp_idx & 3` barrier index cannot be expressed directly.

## flydsl-tdm

PART 1. flydsl 0.3.2's TDM surface lives at /home/lihuzhan/.local/flydsl032/flydsl/expr/rocdl/tdm_ops.py (1266 L) and exports 20 names: a 2D path (make_tensor_descriptor_2d -> tensor_load_2d / tensor_store_2d), a gather path (make_tensor_gather_descriptor / make_tensor_gather_dgroup0 -> tensor_load_gather / tensor_store_gather), six address-advance helpers plus add_addr_with_carry, two pure compile-time helpers, and l2_prefetch_tile. Loads lower to rocdl.tensor_load_to_lds, stores to rocdl.tensor_store_from_lds, and the sole sync is tensor_wait(n) -> s_wait_tensorcnt. There is a SECOND, higher-level surface — fx.rocdl.make_tdm_atom / fx.copy_atom_call in expr/rocdl/cdna5.py, rank 1-5 — and that is the one the shipping gfx1250 attention kernel actually uses. Guards are thin: the only hard assertion on the 2D path is that padIntervalInDwords be a power of two; tile extents are masked into 16-bit fields with no check, tensor_shape is a DEAD parameter (OOB comes only from oob_outer_bound), and the inner stride must be 1 because the descriptor carries only the outer stride. The concrete question — replacing a hot-loop buffer_load of a [BLOCK_KV, 128] bf16 tile into LDS with a TDM 2D load — does not need inventing: aiter's fmha_gfx1250 buffer managers already do exactly that for K and V (_tdm_load_views, fmha_b16_buffer_managers.py:939-994), across all 8 waves, into a row-major PADDED LDS block with pad_interval=128 / pad_amount=8, HW OOB on the seq axis, drained by tensor_wait(0). PART 2. Confirmed: Primus-Turbo/primus_turbo/flydsl/attention/flash_attn_fwd.py:72 tests `not gpu_arch.startswith("gfx950")` and raises at :73-75. Relaxing it would not work.

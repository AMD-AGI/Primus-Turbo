两条线的分工，一句话

不是"用 FlyDSL 替代 ASM"，而是"ASM 吃掉当前这一个形状，FlyDSL 补它结构上补不了的部分" —— varlen（gfx1250 的 ASM 根本没有）、GQA 越界写的根治、确定性、以及形状/特性变化时不必等 AMD 发新资产。 详见 §组会问答。

主线一：ASM 路线 0913 – 0916

我们把 AMD 已经发布、但在 Python 侧完全够不着、且在 GQA 下算错的 gfx1250 预编译 ASM attention 内核，做成了 Primus-Turbo 里可派发、可 A/B、正确的一条生产路径。 我们一行汇编都没有改过 —— 价值全部在适配、纠错与工程化上。

1.1 做了哪些适配

① 发射器从零写 —— aiter 根本没有给 gfx1250 任何可调用的入口 （674 行）

aiter 的 C++ host 有五处 gfx1250 特判，但 Python wrapper 没有： can_impl_fmha_v3_bwd 从 get_gfx() == "gfx942" 起判、只放宽到 gfx950， gfx1250 永远选不中这些内核。我们离线从 ELF metadata + 反汇编反推 kernarg 布局，自己写了发射器。

文件行数作用
tools/gfx1250/asm_bwd_abi.py136从 ELF 推出的 kernarg 字段表 + 无 GPU / 无 torch 自检
tools/gfx1250/asm_bwd_launcher.py185手工发射器（bring-up / ABI 自检入口）
…/attention/_asm_bwd_kernargs.py335产品侧 kernarg 打包 + HipModule
…/attention/attention_asm_bwd_impl.py353反向资格门 + adapter
…/attention/attention_asm_fwd_impl.py199前向资格门 + adapter

反向不是一次发射而是三次：bwd_hd128_odo_bf16（delta=rowsum(dO·O)）→ bwd_hd128_bf16_causal_br_a32_pssk（主体，514 条 buffer_atomic_add_f32 累加进 fp32 dq_acc）→ bwd_hd128_dq_convert_bf16（fp32→bf16）。

主要的坑：两种 packing 约定并存 —— dqdkdv 每字段 16 B 对齐、odo 紧凑打包。 那个无 torch、无 GPU 的 ABI 自检当场抓到一张手抄字段表悄悄丢了最后七个字段（含 mask_x/mask_y）。

② 找到并绕过 aiter 这批资产里的一个正确性 bug —— 最实质的一项

主体内核的 grid 是 (kv_tiles, nhead_q, batch)，却按 q head 去索引 kv 尺寸的 dk/dv 缓冲区 —— 越界写。 GQA ratio=4 下，4 个 workgroup 无同步地争同一块 dk/dv tile。

两副面孔，取决于越界落在哪：

256跨页 → 进程 fault（dmesg 零记录，不伤卡）

三个实验钉死它，并排除了"累加 vs 赋值"假设（预置零没有任何改变）：

代价（0917 首次单独计量）：dk/dv 张量 0.125 → 0.500 GiB（4.0× = GQA ratio）， 反向发射峰值增量 1.254 GiB；host 规约 +0.482 ms = 反向的 +5.2%（相当于总时间 −4.1% 的空间）。

不做这一步，这个内核对 Llama-3.1-8B 这类 GQA 模型直接不可用。 已连同完整复现与三实验定位写成 vendor report 提交 aiter。

③ 接进派发层，而不是做成一个脚本
  • 前向：可用时替换为 aiter 预编译 ASM 前向，并留 PRIMUS_TURBO_ATTN_DISABLE_ASM_FWD 硬开关 —— 没有开关就只能靠"让 aiter 不可 import"来做 A/B，那会同时改掉反向，对比作废。
  • 反向：PRIMUS_TURBO_ATTN_ENABLE_ASM_BWD（0915 起默认 OFF，理由见 §1.3）。
  • 补了 non-causal 发射（换 mask=0 的 .co；只有 causal 才半 x-grid）。
  • 修了 enable_gqa 不被接受 —— 这才是 e2e 里 turbo attention 根本没被调用的原因。
  • 资格门 seqlen ≥ 2048：内核自身时间几乎不随工作量变化（0.88 / 0.91 / 1.00 / 1.34 ms， seqlen 1024→8192，即 16× 工作量只换 1.5× 耗时），约 0.85 ms 固定开销，低于 2048 摊不平。 这条我们错过两次：先从单样本外推成 b*hq ≥ 32，后又差点整个拿掉，而那组数据是被污染的。
④ 两个每调用开销  ·  ⑤ 测量纪律
  • 每次反向都重新 hipModuleLoad 三个 .co —— 32 层就是每步 96 次加载。改成进程级加载一次。
  • scratch 按形状缓存，进程级共 1.000 GiB，不随层数增长（此前一个 45× 的外推错误已纠正）。
  • 同会话、回文交错、带时钟见证的 A/B：这张卡会漂（一个计时窗口内 1100 → 967 MHz）。 另外把 e2e 噪声底刻画清楚了：~3.9% 且三峰，而且 seed 根本没被设上 （torchtitan 在 world_size==1 且 debug.seed is None 时直接跳过播种）。两项都已修，A/B 现在播种、交替、n≥9。

llama-3.1-8B，b=4 s=8192，1 GPU，seed 固定

0915−0.28% 0.15× sem，完全不显著 → 默认 OFF。当时 94% 的 step 是 hipBLASLt GEMM，attention 只占 3.3%。
0916（GEMM 缺陷绕开后）+14.40% attention 占比升到 20.8%。同一个内核、同一台机器、同样的算子级 1.74×。
0917 更正+12.72% 全量 74 次运行的正确性筛查发现两臂各有一次 loss: nan （asm1-on nan×6，且是 ON 臂最快的一次；asm3-off nan×1），各自剔除后重算： ON 42,534 / OFF 37,734。效应依然真实且显著，只是小了 1.7 个百分点。
这条已经写进 skill

一个优化的端到端价值，是它与当前瓶颈关系的函数，不是它自己的属性。 同一个内核、同一台机器、算子级一模一样的 1.74×，端到端从 −0.28% 变成 +12.72%， 变的只是它在单步里的占比 —— 而那个占比是被一个与它无关的 GEMM 修法挪动的。

叠加三项修法后的全链（8 层，仅干净运行）：6,128 → 46,374 tps（7.57×），单步 5.35 s → 707 ms。 32 层生产配置 1,984 → 14,050 tps（7.08×），同会话对照 12,340，20 步零 non-finite。

但 ASM 反向默认仍然关闭 —— 理由变了

不再是"测不出收益"（那个前提已被推翻），而是：它的收益依赖的 GEMM 绕路 nkfix.py 是运行时补丁而非产品代码，且该绕路自身有 21% 的 nan 率待解决。 等 GEMM 走上正路（FlyDSL wgrad 是候选），值得重新评估这个默认值。

2.2 反向：三个内核从零写出来（0917，一天）

gfx1250 没有 MFMA，gfx950 的 FlyDSL 反向模板不可移植： llvm.amdgcn.mfma.f32.32x32x16.bf16、ds.read.tr16.b64、permlane32.swap 在 gfx1250 上全部 cannot-select；LDS 转置要换成 ds_load_tr16_b128，寄存器落位不同。 Primus-Turbo 自己的 FlyDSL attention 树里有 6 个 kernel 各自硬断言 gfx950。 所以是逐 kernel 重写，不是改一个 arch 判断。

内核作用首次验证 SQNR
odo_gfx1250.pydelta = rowsum(dO*O)159.24 / 156.49 dB
dkdv_loop_gfx1250.pydV + dK，运行时 q 循环 + causal （真内核）141.9 / 141.0 dB

三个都是一次通过，每个都带 NaN 预填 + 全 isfinite 覆盖检查再算 SQNR。 写之前先用探针把三件事钉死：WMMA fragment 布局（对 torch 验证）、跨 d-tile 的累加链、ds_load_tr16_b128 的语义。 并顺手发现 gfx942 模板的"免费操作数"技巧在 dq 上成立（151.32 dB 实测）、在 dkdv 上不成立 —— 方向不同结论不同。

顺带修掉 main 上两个真实缺陷
  • flydsl 名义可选却被无条件 import —— 缺了它 import primus_turbo.pytorch 整个失败， 连 gfx1250 上唯一能用的 Triton 路径也一起拖下水。已修 attention 与 sparse_mla 两处 （MoE / GEMM / quantization 下还有 10 个文件同样问题，范围明确、独立有价值）。
  • _flydsl_common_ok 用 >= _GFX950 判断，而 gfx1250 报 (12,5) —— 它能通过。 只是碰巧被 GQA 门挡住才没出事。已改为 is_gfx950()。

round 5 的一个诚实注记 —— 会上主动说，不要等人问

记账上的 1.15× 是被 fast 形状抬起来的：接受判据取三形状增益的算术平均， 而 fast 只有 0.35 ms、被发射开销主导，却与 26 ms 的 prod 同权重。

单臂 prod 实测（基线 331.07）：g12 335.94、g17 333.45、合并 336.32 —— round 5 在 prod 上的真实收益约 +1.6%，主要来自 g12。 继续跑之前建议先 op-evolve tune 调形状权重，否则后续轮次可以靠 fast 形状持续"赢"而 prod 停滞。

一条值得沉淀的工具链发现（round 6 的 build failure）

FlyDSL 0.3.2 的 ast_rewriter 会把 kernel 体里的 if 整体改写成 scf.if：两个分支被提成独立函数，在 if 之前不存在的新变量带不出来 → NameError， 而且报的是"明明两个分支都赋了值"的那一行。 在 FlyDSL kernel 体内做任何编译期分支，条件必须裹 const_expr(...) （由 rewriter 自己注入 globals，无需 import）。

2.5 挂卡、AC-cycle 与一条重要发现

round 8（当时在试 g04 的 4-wave 重构）运行中，卡于 14:26 挂死： MES(0,0) failed to respond 从 INVALIDATE_TLBS 一路升级到 RESET/RESUME， 随后 GPU reset begin! + MES 0–7 的 REMOVE_QUEUE 无界级联 —— 属不可恢复档。

没有做任何恢复尝试：不 modprobe -r（上次让整机掉 SSH 两小时）、不 kill -9 （每次都会多留一个不可杀的 D-state 进程，把可恢复推向不可恢复）、不做进一步探测 （挂卡时 rocm-smi / pgrep / docker stop 会自己挂住）。 14:40:38 完成 AC-cycle，重启后全检通过（amdgpu 已加载、KFD 空、零故障签名、 git fsck 通过、4096³ bf16 matmul 5.071 ms 有限结果），round 8 随后手工收口。

闸门本身才是挂卡源 —— 这条值得单独讲

补验 round 8 时 validation.py 在 proxy 阶段以 HSA_STATUS_ERROR_MEMORY_APERTURE_VIOLATION 中止，dispatch 签名 workgroup=[256,1,1] group_seg_size=6144 —— 那是 op/eager/ 里的 hipBLASLt/Tensile GEMM，不是我们任何一个 kernel （k_dkdv 32 线程 / 22,528 B、k_dq 32 / 8,704、k_delta 256 / 0）， 且与 round 3 中止时的签名完全相同。

含义：每轮的固定挂卡风险，有很大一部分来自闸门里的 fp32 参考实现，而不是被测的 kernel。 本轮的绕法是：armAB 对 incumbent 逐位相同（prod 上 134,217,728 个元素零差异）， 正确性由继承得到，比重测 SQNR 更硬（闸门有 2.5 dB 余量，逐位没有余量）； determinism 单独跑（它不需要 eager 参考），200 次通过。

2.6 天花板与剩余方向

一个被证伪的模型，记下来免得再被引用

hint h8 断言"我们钉在 HBM 屋顶上"（107 GB / 6.46 TB/s = 16.56 ms ≈ 当时实测 16.39 ms）。 强形式错了 —— round 6 的 prod 已是 15.52 ms、round 7 是 14.36 ms，都低于那个下界。 107 GB 是 load 指令请求字节的正确计数，但实际到 HBM 的流量低于它（cache 吸收一部分）， 所以并未贴顶，还有延迟/访存并行度余量 —— round 6/7/8 吃的就是这块。 方向仍成立：冗余流量是最大杠杆（aiter 的字节数是我们的 1/5.6），但不要再引用"101% of roof"。

  • k_dkdv 仍把 16 宽的收缩 padding 到 WMMA 的 32，浪费一半 GEMM。
  • 唯一还能指望数量级改善的 g04（多 wave workgroup，BLOCK_KV 32→128） 现在被两条独立的阻塞堵住（hint h13）：
    1. 寄存器 —— 缺 462 个。k_dkdv 因 g21 的预取已到 956–988 / 1024。 历史规律是 VGPR ≤ 951 的 21 个变体零 spill、= 1024 的 14 个全 spill，中间没有过渡态； 而 gfx1250 上 spill 的 build 第一次发射就挂起，代价是一次断电。
    2. 同步。round 8 删掉的正是 4-wave 需要的那两个 barrier。若直接把 block 改成 128， kernel 会静默竞态 —— 而竞态可能通过 SQNR 闸门（causal 跳过区真值本就接近零）、 也可能在固定调度下 200 次逐位稳定，两道现有闸门都不保证能抓到。
    两者都是由各自正确的轮次造成的（g21 +8.3%、g23+g24 +6.3%）。合起来， 它们把 kernel 爬进了一个局部最优：流量分析认为唯一必要的结构性改动，现在装不下了。 要走 g04，可能得先吐回 g21 和/或 g23+g24；这笔账该由下一轮显式定价， 并把交付标准写成"证伪 g04 也算合格"。
  • 精度余量按设计就薄：返回 bf16 梯度把 SQNR 封在 52–53 dB，对 50 dB 闸门只有约 2.5 dB 余量。
  • SQNR 在这个 op 上基本看不出东西 —— 能干活的是逐位比对。 这也是 round 8 在闸门挂掉时仍能交付的原因。

组会问答：有了 aiter，为什么还要做 FlyDSL

这是最可能被问到的一题。下面把两个常见回答先做真伪判定，再给四个更站得住的角度。

成立角度一：aiter ASM 面对 shape 变化不够灵活

成立，而且要升级说法 —— "灵活性不够"听起来像偏好问题，实际是有没有的问题：

  • gfx1250 根本没有 varlen ASM 反向。dispatch 表只有 mode=0， host 对每个 seqstart 指针传 nullptr。这条没有任何绕法。
  • 资产极度稀薄：gfx1250 反向 6 个 .co，gfx950 有 124； 只有 a32、只有 pssk，没有 psskddv、没有 a16。 MI355 在 trace 里实际跑的 bwd_hd128_bf16_causal_br_a16_psskddv，在 gfx1250 上不存在。
  • 连入口都没有：can_impl_fmha_v3_bwd 从 gfx942 起判、只放宽到 gfx950 —— 走 aiter 公开接口在 gfx1250 上根本调不到，我们是自己反推 kernarg 手写发射器才用上的。
  • 小 shape 直接掉出去：seqlen < 2048 时 ASM 反向打不过融合 Triton 反向（比值 0.54–0.87）， 我们不得不设资格门。

一句话版本： "ASM 只覆盖我们当前这一个形状族；形状一变、要 varlen、要新特性，就得等 AMD 发新的 .co， 而我们连编译它的能力都没有。"

不成立角度二：FlyDSL 预估性能可以超过 ASM

会上这么说会被我们自己的测量打脸。同一张卡上， aiter 的 FlyDSL 前向比它自己的 ASM 前向慢 1.51×（2.373 vs 1.569 ms），两边都成熟， 这是现有最好的估计。立项文档里我们自己写的是"持平是现实上限"。 目前 FlyDSL 反向是 ASM 的 0.609×，还差 1.64×。

如果有人追问，反而有一条对你有利但方向不同的数据 —— 同事在 gfx950 上测 FlyDSL vs AITER （dev/kyle/flydsl-attn-gqa4，B=2，D=128，bf16 causal，min of 20）：

补一句量化进展，显得不是空谈：基线 57.2 → 429.4 TF/s（7.50×）， 与 ASM 的差距从 12.6× 收到 1.64×，八轮做到这里，路线图还有明确的下一步。

更强角度三：正确性我们拿不回来 —— 最实质的一条

aiter 这个 gfx1250 ASM 反向在 GQA 下越界写：s=1024 静默把 dk/dv 打到 −0.3 dB 而 dq 仍正确， s=256 直接 fault。llama3.1-8B 正好是 GQA=4。

没有源码，我们只能在外面绕：per-q-head 分配 + host 规约， 代价峰值 +1.254 GiB、反向 +5.2%（总时间 4.1%）。 源码版反向把这 1 GiB 和这次规约整个删掉 —— 这既是性能，也是把一颗静默损坏梯度的雷拆掉。 没有源码就只能一直绕。

成立角度四：确定性 / atomic-free

ASM 反向用 514 条 buffer_atomic_add_f32 往 fp32 dq_acc 里累加， 累加顺序不可复现。我们的 FlyDSL 反向按构造无 atomic、每个输出元素只写一次， 并有 200 次逐位一致的闸门。训练收敛出问题时能逐位复现，是实打实的产品属性 —— 对比：gfx950 的配方里 deterministic=True 要付 22.7%。

成立角度五：ASM 这条路的调优面已经关死  ·  角度六：能力沉淀会外溢
  • 调优面关死：内核 VGPR 用满 1024、LDS 320 KiB、workgroup 1024、wave32 —— 资源饱和。 我们一行汇编都改不了也不该改。ASM 侧后续所有收益都依赖 AMD 发新资产；FlyDSL 是我们能改的那条。
  • 能力外溢：gfx1250 的 FlyDSL 打法（WMMA fragment 布局、ds_load_tr16_b128 转置、 const_expr 编译期分支陷阱、wave32）是可复用资产。同一套东西在 GEMM 上已经兑现： FlyDSL wgrad 8 层 +9.26%、32 层生产配置 +13.9%。attention 这边投入的不只是一个算子。
建议的收口说法

不是"用 FlyDSL 替代 ASM"，是"ASM 吃掉当前这一个形状，FlyDSL 补它结构上补不了的部分"： varlen（ASM 根本没有）、GQA 越界写的根治、确定性、以及形状/特性变化时不必等 AMD。 性能上我们的目标是追平，不是超越；目前 7.50× 基线、差距 1.64×，还在收敛。

同时要诚实地说出成本和最高杠杆项：这条线已花掉单卡八轮、两次需 AC-cycle 的挂卡； 而成本近零、杠杆最高的动作是把 GQA bug 报给 aiter 并申请 gfx1250 的 psskddv / a16 / varlen 变体。 FlyDSL 是他们不发这些资产时的对冲 —— 这么讲，两件事就不是竞争关系了。

会上可能被追问的其它问题

"你们的卡限频，这些数字是不是都不可比？"

方向对，幅度错 —— 限频只值约 13%，不是 2×。 B0 的时钟是 A0 的 2.13–2.24×，而同代码、同形状、同一个 ASM 反向实现只快 1.118× / 1.150× / 1.146×（fwd / bwd / total）。

结论：gfx1250 上的 attention 几乎不受核心时钟限制， 它受限于访存带宽或固定延迟，而 VR 限的是 sclk 不是 HBM。 换算过去：A0 的 11.726 ms 在健康卡上约 10.2 ms。

"和 MI355 比怎么样？"

前向我们是全表最快：比 MI455 的 Flex 快 2.10×、比 MI355 的 AITER 快 2.42× （用满频的 B0 则是 2.35× / 2.70×）。

反向是唯一的战场：即便在满频的 B0 上，我们的 8.835 仍比 MI355 的 AITER 5.381 慢 1.64×。 bwd/fwd 比值：MI355 是 1.42，我们是 6.28 —— 前向优化得太好，反而让反向的落后无处可躲。 另一个参照：理想的 5 次矩阵乘结构下界是 5.48 ms，ASM 反向的 10.160 ms 约是它的 1.85×。

"最快的那档为什么默认是关的？"

理由被修正过两次，现在的理由不是"测不出收益"（那个前提已被推翻，见 §1.3），而是：它的收益依赖的 GEMM 绕路 nkfix.py 是 运行时补丁而非产品代码，且该绕路自身有 21% 的 nan 率待解决。 等 GEMM 走上正路，值得重新评估这个默认值。

"Triton 那条线为什么不继续投？"

三条 Triton 路径全部扫过：vendored 融合反向九个轴全测，256/32/32/4-warps 严格局部最优， 邻居更慢（有的 2×）；两 kernel 反向扫出真实 18%，但仍比 ASM 慢 2.7×；前向 −3.73%，只值 e2e 的 0.15%。

更关键的是结构上界：调度良好的 Triton 在 AMD 上落在 issue-slot wall 的 1.3–1.5×， 即总时间 16.7–18.2 ms。我们现在是 11.726 ms —— Triton 不是"提升空间较小"， 而是结构上就到不了我们已经在的位置。要拿到剩下的空间得重写 kernel，不是调参。

### d.1 GPU wedges and AC power cycles

On both machines, once a card is wedged for good (a wedge), no software means can bring it back: the driver's own reset cannot complete, the container holds unkillable D-state processes, and the reference count of `/dev/kfd` never drops to zero. The only way to recover is for the user to go to the machine in person and cut power to the whole box (an AC power cycle). Wedges are therefore first a scheduling constraint, and only second a technical problem.

#### d.1.2 Wedge classes and how our understanding evolved

1. **09-04..09-13 (A0-throttled): first treated as a platform problem.**
   - Four unrelated workloads all triggered the same kind of wedge: MES unresponsive, reset unable to complete. The four workloads were HipKittens GEMM, grouped-GEMM, the E3 mask outer product, and E4 PC sampling.
   - The conclusions at the time: the card itself is fragile; PC sampling always wedges; reloading the driver is not feasible, because D-state processes do not release `/dev/kfd` and the amdgpu refcount never drops to zero.
   - It was also found that during a wedge, `rocm-smi`, `ps -eo …wchan`, `pgrep` and `docker exec` all hang themselves.
   - Action: filed HARDWARE-ISSUE / PLATFORM-ESCALATION and moved to B0 on 09-14.
2. **09-14..09-17: learned to tell three states apart.**
   - "Degraded" is not "wedged for good". B0 GPU0 had 120 `MES failed to respond` lines but could still run kernels to completion. Only `wait for reset ack`, `ring gfx timeout` and `GPU reset begin` mean unrecoverable.
   - A "process-level fault" is not a "wedge". The `Queues reset on process` on 09-17 did not need an AC.
   - There were many startup wedges during e2e work: on 09-16, 3 of the day's 14 launches wedged (21%), from which it followed that **risk is priced by the number of launches, not by run duration**.
   - Confirmed triggers identified: autotune inside the training step, `converters: []`→inductor, Triton `num_warps=16`, bad candidate #58, starting a new run while KFD leftovers remain, `modprobe -r`, repeated SIGKILL of running kernels, and a "CPU-only" agent going onto the card on its own.
   - Another conclusion: SIGBUS is a symptom, not the cause.
3. **09-21..09-24 (op-evolve bwd job): split into three classes A/B/C by the first dmesg line; the discriminants were falsified one by one.**
   - Four "wedge precursor" discriminants were proposed in turn, and all were overturned by measurement:
     - h15: truncated sub-4GB address + PF 0x5/RW 0x1 + `copy_context_work_handler`. Class B wedges never trigger it at all.
     - h22: `IH ring buffer overflow`. During the 09-24 boot there were 8 overflows and the card stayed alive, while the 08:58 wedge had no overflow at all.
     - MORE_FAULTS / multiple XCDs. 8/8 of the survivable batches had MORE_FAULTS.
     - A fault arrival rate of "6000×". That number is actually the driver's ~97 ms throttling (7436cd29).
   - Conclusion (3fd48059): **there is no usable wedge predictor**; alert only on the wedge itself.
   - Two triggers were actually pinned down in this period: first, the fp32 Tensile reference that the gate ran on the card, solved with refcache; second, running multiple shapes in a single process, which faulted in ~44% of processes; after switching to one shape per process, 6 consecutive runs had 0 faults.
   - In the same period it was also found that `dmesg_restrict=1` had invalidated all earlier "zero faults" checks.
4. **09-28..10-06: the host library and new kernels became the main triggers; the firmware reflash did not make the card any sturdier.**
   - The host hipBLASLt library `~/.local/hipblaslt-gfx1250` is associated with several incidents: on A0 on 09-28, one NaN and one wedge; B0 stuck at step 1; the 10-02 wedge.
   - Running the fp32 reference GEMM on the card still causes faults (B0 GPU2).
   - After the 09-29 reflash the clock recovered and ATT became usable, but on 10-02 a new kernel sent straight to prod still wedged the card. On 10-06, `hipblaslt-bench` wedged it too when its enumeration hit a bad Tensile solution.
   - The rules converged into h85: scale new kernels up step by step from toy→prod; probes that only read ISA/VGPR are always compile-only; use only the hipBLASLt library shipped in the image.
   - Another data point: B0 had ≥12 training launches on 09-27/28 with 0 wedges. Pooling all periods, the startup wedge rate is about ≤5/31≈16% (`1002__e2e/E2E-PLAN.md:377`).

#### d.2.2 What nkfix is and how to install it

- **Problem**: the hipBLASLt in the image ships pure-bf16 tuned libraries only for the TN layout (`Alik_Bljk`) used by the forward Linear. The backward dgrad (`Ailk_Bljk`) and wgrad (`Ailk_Bjlk`) can only look up the sparse GridBased table, whose nearest neighbor lands at N=1, so they end up with the GEMV tile `MT32x16x32` at only 50–80 TF/s. The forward reaches 1.5–1.9 PF/s, an 11–32× gap per call.
- **Approach**: intercept `aten::mm` with `TorchDispatchMode` and change the physical layout of the backward GEMM operands to the forward one, so that they hit `MT256x256x128`:
  - dgrad, when B is contiguous, becomes `mm(A, B.t().contiguous().t())`.
  - wgrad becomes `mm(A.contiguous(), B.t().contiguous().t())`. The wgrad criterion must be checked before the dgrad one.
- **Approaches that did not work**:
  - The zero-copy form `(BᵀAᵀ)ᵀ` still lands on the bad tile, only 0.83–0.95×, because this library has good tiles for the TN layout only.
  - Overriding `aten::mm` with `torch.library` recurses infinitely.
  - Putting it in `sitecustomize` fails because torch is not loaded yet at that point.
- **Numerics**: op-level SQNR is identical to the original call, 55.59–55.63 dB in both cases; over 99.996% of elements differ by at most 1 ulp; bitwise deterministic across 3 repeats.
- **Versions**:
  - A0 v1 (09-15) changes dgrad only.
  - A0 v3 (09-16) adds wgrad; rule 3 is the FlyDSL wgrad, driven by an offline table and off by default.
  - B0 `nkfix_b0.py` (09-28) is a rewrite on top of 1255557f:
    - Persistent scratch, keyed by (device, stream).
    - Chunked along the output dimension, chunk size `NKFIX_CHUNK_BYTES` defaulting to 256 MiB; the K reduction is not split.
    - Transposes use the blocked Triton kernel `transpose_triton.py`, bitwise identical to the torch copy and 5–7× faster.
    - `NKFIX_CHECK=0/1/2` checks for non-finite values; `NKFIX_SHADOW` runs a shadow comparison during real training.
  - The tutorial uses exactly this B0 version.
- **Installation**:
  - Tutorial route: `primus-nkfix-hook.patch` adds 14 lines to `_run_trainer_lifecycle` in Primus's `primus/core/runtime/train_runtime.py`, which import nkfix and call `install()` when `NKFIX_ENABLE=1`.

#### d.2.4 NaN, `HIPBLASLT_TENSILE_LIBPATH` and host-library risks

1. **nkfix and NaN (A0-throttled, 09-16)**
   - Runs with nkfix hit NaN in 8/39 cases, runs without in 0/35 (p=0.004). A separate count: with nkfix, 7 of 40 runs showed only `grad_norm=inf`; without, 3 of 36.
   - All NaNs occurred at step ≤10 and were entangled with that day's MES TLB faults. The root cause was never found.
   - The B0 rewrite: 8 nkfix runs in total, 486 steps (150 unstable steps), 0 NaN. The upper bounds are computed only over the 7 runs at 32 layers among them, 466 steps (138 unstable steps): the 95% upper bound per step is 2.2%/step; per run it is 35%/run, not yet enough to rule out A0's 21%/run; pushing it below 21% would take ~13 clean runs (`0927__b0/gemm/REPORT.md` §0 §4).
   - Hence nkfix stays opt-in; turn on `NKFIX_CHECK=1` for long runs or debugging; any NaN or inf voids that run's speed data in its entirety.
2. **Library path**
   - The default search path is one directory level too high: `library/` contains only a single `gfx1250/` subdirectory, which holds all 402 files, so the result is `INVALID_VALUE`. The 09-23 S0-b directory table did not list this subdirectory, which is why the host library was adopted instead (see d.2.1).
   - `_rocm_sdk_devel/.../library/gfx1250` is an incomplete copy (326 files, no `Kernels.so-000`, no extop/transform) and gives SIGSEGV, exit 139.
   - `/opt/rocm/lib/hipblaslt` is an empty directory; the container's ROCm is not under `/opt/rocm` at all.
   - Falling back to rocBLAS makes e2e 8× slower, and its fp32 Tensile kernel has also caused page faults on the card.
3. **`TORCH_BLAS_PREFER_HIPBLASLT` is silently rewritten, in at least three places**
   - `sitecustomize.py` uses `setdefault("0")`; we added this ourselves on 09-17.
   - `/etc/profile.d/zz-gfx1250.sh` exports it as 0; this only takes effect in a login shell, so `bash -lc` gets caught.
   - `tune_attention.py` sets it to 0 itself before importing torch.
   - Rules: assign only, never `setdefault`; use `bash -c`; confirm by printing `torch.backends.cuda.preferred_blas_library()` inside the process.
   - Also, `runtime.env` in the op-evolve spec does not actually take effect; the setting must go into the op's own code or the exec command line.
4. **Host library `~/.local/hipblaslt-gfx1250` (a copy from host ROCm 10.1.0, 328 files)**
   - Validated only on square matrices.
   - Associated with these incidents: the B0 hang at step 1 (p1a/p1b single-variable control, n=1 per side); GEMM bursts ~20× slower; the A0 09-28 NaN and wedge; the 10-02 wedge. Apart from p1a/p1b, all of this is correlational evidence only.
   - Banned by h85 since 10-02.
   - `skill:env-and-pitfalls` §1b still recommends the host library to this day; it is outdated and needs updating.
5. **fp32 GEMM reference on the card**: causes class-A wedges (refcache) and the B0 GPU2 fault (h50). References for tests and gates are always computed on the CPU or served from refcache; a refcache sha mismatch is an immediate FAIL (see d.5).
6. **`hipblaslt-bench --algo_method all`**: hits bad precompiled solutions and wedges the card; do not use it.

# dkdv 第一次计时：5.8 TFLOP/s，对 ASM 的约 540 TFLOP/s

日期 2026-09-17 · `heliosr-1b114-c07-1` @1100 MHz · `kernels/dkdv_timing.py`

## 数字

D=128、causal、单头。四个 GEMM 按完整方阵计 FLOP；"useful" 是 causal 下真正需要的一半。

| S | median | executed | **useful** | grid |
|--:|--:|--:|--:|---|
| 1024 | 0.443 ms | 2.4 TFLOP/s | 1.2 | 64 wg × 32 thr |
| 2048 | 0.793 ms | 5.4 TFLOP/s | 2.7 | 128 wg × 32 thr |
| 4096 | 1.475 ms | 11.6 TFLOP/s | **5.8** | 256 wg × 32 thr |

**参照**：aiter 预编译的 ASM 反向在生产形状（`b=4 s=8192 hq=32 hkv=8 d=128 causal`）
上是 10.160 ms，换算约 **540 TFLOP/s useful**。

**差距约 93×。**

## 这个数字说明什么、不说明什么

**不说明 FlyDSL 在这张卡上做不快。** 差距几乎全部落在**已知缺失的东西**上，不是内核结构本身：

| 已知损失 | 量级 |
|---|---|
| 一个 workgroup 只有 **一个 wave（32 线程）**，而卡要的是 8 wave / 256 线程 | 最大 ~8× 的占用率 |
| 收缩宽度只有 16 个 query，被零填充到 WMMA 的 32 | 2× |
| **不跳过被 causal 掩掉的 tile** —— 每个 kv 块都遍历全部 query 块 | 已计入 "useful" 那一列 |
| 没有软件流水、没有 TDM 异步拷贝 | 未知，但前向大量使用 TDM |
| 每次迭代重新 stage Q/dO 进 LDS，无 ring buffer | 未知 |
| 没有 bank 冲突 swizzle | 未知 |

所以**这次测量没有决定任何事** —— 它测的是一个刻意不做优化的正确性载体。

**但它确实说明了一件事**：剩下的不是打磨，是**主要工作量**。把 93× 收回来要做的是多 wave 调度、
TDM 流水、causal tile 跳过、更宽的收缩、swizzle —— 也就是 `fmha_gfx1250/` 那 4147 行前向里
绝大部分内容的对应物。"结构模板已存在"从来不等于"性能已存在"。

## 和今天其它证据放在一起

| | |
|---|---|
| FlyDSL 前向 vs ASM 前向 | **慢 1.51×**（`STAGE1-FWD.md`，两边都已高度优化） |
| FlyDSL 反向数据通路 | **正确**（odo 159 / dkdv 150·145 / dq 145 dB，全部一次通过） |
| FlyDSL 反向性能 | **慢约 93×**，且差距全在未做的外围 |
| 版本 | 0.3.2 与 turbo 的 0.2.4 树不能共存 |
| 立项理由 | 只剩结构性的：gfx1250 **没有 varlen ASM 反向**；ASM 反向的 GQA 越界写（峰值 1.254 GiB + 反向 5.2%）；ASM 资产 1/25 |

**诚实的读法**：前向那个 1.51× 是在**两边都优化过**的前提下比出来的，它是这套 gfx1250 FlyDSL
惯用法竞争力的最好估计。如果反向优化到位之后也落在同一量级，那么用它替换 ASM 反向
**不会带来性能收益**。它的价值仍然只在那三条结构性理由上 —— 其中 varlen 是最硬的一条，
因为那是"有没有"而不是"快多少"。

## 建议

**在投入多 wave 调度和 TDM 流水之前，把这个判断摆给决策人。** 那是数个 agent session 的工作，
而它的预期收益按今天的证据是"性能持平、换来源码可控和 varlen 能力"。
这是一个值得由人来做的取舍，不该由我默认继续。

如果决定继续，优先级应当是：**多 wave（占用率）→ causal tile 跳过 → 更宽收缩 → TDM 流水 → swizzle**，
每一步单独计时，因为上表里只有前两项的量级是已知的。

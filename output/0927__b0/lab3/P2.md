## 0. 结论

- **h58 1-wave（BLOCK_KV=32）：P2 这一槽通过，判 GO 进入 P1。** T_a = **4.43 ms**，门槛是 7.97 ms（B0 冠军实测 8.724 − 0.25 − 0.5）。
  串行 GO 要求 T_c ≤ 3.54 ms，而 T_c 至少等于冠军 k_dkdv 的时间（约 5.5 ms），所以串行 GO 实际上不可能。
  可能的走向是：若 T_c ≤ 7.97，进入"再测"（P3，需 T_P3 ≤ 7.72 ms，即原子至少盖住约 60%）；若 T_c > 7.97，则 NO-GO。
- **h58 4-wave（BLOCK_KV=128）：P2 这一半闸门通过。** T_a,128 = **2.46 ms**，门槛 ≤ 3.0 ms，离 5.0 ms 的整路线 NO-GO 线很远。
  另一半条件 x ≤ 7.6% 由 P1 给出。
- 原子的有效载荷吞吐是 **15.6 TB/s**（68.99 GB），为普通 `buffer_store_b32` 的 **0.92 倍**（原子/写 = 1.09×）。
  这个数是 aiter 实证 2.41 TB/s 的 6.5 倍，也高于 FUSED5 §0.4 所说"完全盖住需 ≥ 9.0 TB/s"（按 B0 的计算时间折算约 11 TB/s）。
  但它仍低于"串行也能赢"所需的 ~25 TB/s，所以 1-wave 融合必须靠重叠。
- 整个 session 中 **dmesg 新增 0 行**（开始和结束都是 2750 行），11 个卡上进程全部 RC=0，结束后 KFD 无残留。

## 4. 读法与注意事项

1. **b 点量的是关键路径，不是吞吐。** 无论 KVG 取几，最长的 WG 都是 1024 次迭代（G·nqt2 = 4·256）。
   b（2.46 ms）和 c（2.60 ms）几乎一样，而 a 的每个 slot 分到约 4112 次迭代也只用了 4.43 ms。
   所以 b 被"最长 WG 串行发 1024×128 条原子"卡住，7.09 TB/s 只是 17.45 GB 能达到的**吞吐下界**，2.46 ms 是时间上界。
   真正的 4-wave 形态会把一个 WG 的原子摊给 4 个 wave，应当不会比这更慢。
   另一个可能的因素（未验证）：grid 是 (hkv, bid, bat)，bat 在最外层，所以 bat=3 的最长 WG 要排在 1536 个 WG 之后才被派发，并不是全局 longest-first。
   融合 kernel 用的是同一个 grid，值得在 P3 时顺便看一眼。
2. **占用率越高反而越慢**：f（不钉 LDS，19 VGPR，可以驻留很多 wave）是 8.63 ms，为 a 的 1.95 倍。
   原子流量在 1 wave/SIMD 时已经饱和，再多的 wave 只会增加争用。这对融合 kernel 是好事，因为它本来就是 1 wave/SIMD。
3. **e 点作为"索引算术地板"无效。** 编译器删掉了全部索引计算，只剩 `s_add_f32` 计数循环（`isa/none_lds70656`）。
   keepalive 的 buffer_store（num_records_bytes=4）也没有落地（非零元素为 0，可能与 V# num_records 的 128 B 单位有关）。
   0.014 ms 只说明循环骨架可以忽略；索引算术的成本已经包含在 a 和 d 里。
4. **门槛怎么取。** FUSED5 §6 的 10.0 ms 定义为"冠军 − 0.25 − 0.5"，冠军值要求在同一 session 实测，缺省 10.75 是 A0 的数。
   B0 上同卡实测为 8.724，所以门槛是 **7.97 ms**。4-wave 的 3.0 / 5.0 ms 在原文中是绝对值，这里照原文使用。
   如果按 8.724/10.751 等比缩放，3.0 会变成 2.43，b 点 2.46 刚好压线；但由于 b 是时间上界（第 1 条），结论不变。
   按缺省 10.0 算，1-wave 的判定同样是"P2 通过，看 P1"，只是串行 GO 所需的 T_c 从 3.54 放宽到 5.57 ms。

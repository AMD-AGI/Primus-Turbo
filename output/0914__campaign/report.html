对「四卡满载压低了数字」的担心没有成立。上表全部在四卡满载下测得。 收尾时在安静的 GPU1 上复测：10.235 ms / 752.0 TFLOP/s，与满载下只差 0.6%。

收益来自哪里

waves_per_eu 不设值 4.2%，而昨天的网格并没有测错—— 64 个配置的指令数中位变化确实是 0.00%。收益不在指令数上，而在 你不再约束占用率时后端自己选的那个值；1100 MHz 下没有足够的访存延迟需要隐藏， 所以它在限频态确实一文不值。它是一口窄井而不是一条斜坡： waves_per_eu=2 是 49.7 ms，=3 是 78.7 ms。

in-thread transpose 来自在 GPU1 上无人值守运行的 op-evolve 循环， 它在自己的 harness、自己的进程里测出 5.9%。同一轮还独立重新发现了 waves_per_eu。 两套互不共享的 harness 在同一个旋钮上吻合，比任何一边单独的结果都值钱。

产品代码里的两个真 bug

树内的融合反向此前完全无法在 torch.compile 下运行。 两个互相独立的硬失败，都不是软 graph break：

失败为什么一直没被发现
os.environ 写在启动路径上 AOTAutograd 在编译前向时会追踪反向，于是这个写落进被追踪的图里，posix.putenv 不被支持
num_ctas 直接作为 launch kwarg 传入 dynamo 直接拒绝；而 num_ctas=1 本就是 Triton 的默认值，等于 1 时不传，行为完全不变

两者能存活是因为两道门的盲区正好错开：51 个测试不编译模型， 而端到端配置里的 converters: [] 让 TurboAttention 从未被装上、融合反向从未进入训练路径。 「torch.compile 开着」和「融合反向真的在跑」这两件事，在今天之前从未同时成立过。 已在 ad67a2cc 修复。

两条已判死的路线

路线判定证据
HipKittens udna1RED 红在预测之外。transpose 本身能编译、结构上也是对的—— 行/列寄存器布局在 wave32 下确实是精确对偶，离线穷举 4608 个三元组、0 处违例。 真正的墙是三条编译期事实：reductions.cuh 完全编不过 （permlane32_swap 是 gfx950 独有，7 个调用点）； 三个矩阵入口只有 mma_ABt 存活； swap_layout 在 wave32 下可证明只覆盖一半寄存器，而它在 transpose→mma 路径上是必经的。 GPU gate 给出同样结论：256 个元素错 126 个。
FlyDSLBLOCKED 工具链门是开的——0.2.4 确实暴露了 tdm_ops、s_wait_tensorcnt、 ds_load_tr16_b128，与昨天的记录相反——gfx950 前向翻一行 arch 门后也能一路 build 并 lower 过 MLIR。 但 gfx1250 根本没有 MFMA：mfma.f32.32x32x16.bf16、 ds.read.tr16.b64、permlane32.swap 在 gfx950 全部选中， 在 gfx1250 全部 Cannot select。 调度表是从 MFMA wave64 的 fragment 布局推出来的，所以这属于「重写」而非「替换」。 18–36 工程日的估算确证。

九次调查，九次测量问题

每一次「改动应该有效果却没有」，根因都在测量或编排链路上， 没有一次在被测的改动上。按消耗的时间排序。

  1. 所有端到端跑的都是镜像里的包，不是 checkouteditable 安装通过 .pth 注册了 MetaPathFinder，而 sys.meta_path 的查询先于 sys.path，所以 PYTHONPATH 根本压不过它。而它在每一条日志里都显示正确。
  2. 三张卡闲置数小时，监控看不见活性判断读的是 ledger 文件的 mtime，而网格跑完的队列每轮仍会追加一行完成标记。代理永远显示「新鲜」。是操作者一眼看出来的，不是监控报出来的。
  3. 「四张卡全死了」来自一个 150 秒超时的 matmul。一个冷进程要花约 78 秒在 HIP 初始化和分配上才轮到第一个内核。分阶段测量后，稳态是 0.0011 秒——死的是一张卡，另外三张好好的。
  4. 一个孤儿循环给降级的卡喂了 2 小时 15 分一个 ppid=1 的后台 bash 重生循环。三次清理都只杀掉了它的子进程，而每次「又出现了」都被误判成「kill 的模式没匹配上」。
  5. ASM 路径「从未被走到」依据是日志里没有厂商的加载横幅。而 launcher 导出了 AITER_LOG_LEVEL=ERROR，把它压掉了。缺席从来就不是证据。
  6. 三个探针设计各自弄挂了训练在被追踪的 autograd.Function 里，os.getpid()、open()、以及调用 @torch.compiler.disable 的函数，三者都是致命错误。会改变程序能否运行的诊断不是诊断。
  7. 抢卡会产生假的 SQNR 失败同一配置、同一随机种子：抢卡时 42–48 dB，干净时 53.7–53.9 dB。SQNR 门是唯一的正确性防线，一次假失败就会让你丢掉一个好配置。
  8. 一个扫描空转了 40 轮幂等 tag 里带了轮次号，于是它永远不是「已完成」——网格跑完后队列就只重复那一个候选，还一直看起来很忙。
  9. 四个 shell 陷阱pkill -f 会匹配到调用者自己的命令行（丢了四个 shell）；timeout 5 kill -0 跑的是 /bin/kill 而非 shell 内建，语义不同；kill -0 的 EPERM 被 2>/dev/null 吞掉、读成了「进程不存在」；grep -c 无匹配时既打印 0 又返回退出码 1，于是 || echo 0 产生 "0\n0"。

能避免其中大部分的那条规则：在相信任何「X 是否在工作」的信号之前， 先问「有没有直接测 X 的办法」。通常有，而且通常比搭一套间接监控更快。

一件仍未查明的事

torch.cuda.init() 要 58–172 秒且随并发 GPU 进程数上升， 正常应是几秒。它是测量吞吐的地板——今天每个 run 都先付约 78 秒才轮到第一个内核。 三个实验各排除一个假设：AMD_LOG_LEVEL=3 显示运行时自己的整段日志只跨 141 毫秒，所以不是 ROCm 运行时； ROCR_VISIBLE_DEVICES（在枚举前就滤掉 GPU0）只省 18%，所以不主要是那张死卡； 同一容器连跑三次给出 157/130/172 秒、毫无预热，所以不是冷库加载。 剩下的解释是内核侧 KFD 上下文创建，被其他进程序列化。

剩余空间在哪

反向是 8.840 ms，对重算后的墙 4.31–4.63 ms 仍有 1.9–2.0×， 和昨天是同一个倍数。前向换上预编译 ASM 内核后是 1.396 ms， 已经不再是今早那个杠杆了。所以接下来的实质收益都是结构性的，且全部在反向： ASM 反向探针、op-evolve 的持续搜索，以及——只有前两者都停滞时—— 把下界本身从 7.68 挪到 5.48 TFLOP 发射量的 5-GEMM 重构。

一条需要随身带的警告：plan 里「well-scheduled Triton 落在 issue-slot 墙的 1.3–1.5×」 这个说法，被我们自己的两个 Triton 内核证伪了——它们分别在 2.0× 和 2.2–2.4×。 现在的 10.3 ms 与旧的那句「低于 13 ms 就不是 Triton」只是数字巧合，不是抵达。

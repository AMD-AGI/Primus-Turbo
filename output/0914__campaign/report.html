Where the win came from

waves_per_eu unset is worth 4.2 % and yesterday's grid was not wrong about it — a 64-config sweep really did move the instruction count by a median of 0.00 %. The win simply is not in the instruction count; it is in the occupancy the backend picks when you stop constraining it, and at 1100 MHz there was not enough memory latency to hide for that to matter. It is a narrow well, not a slope: waves_per_eu=2 measures 49.7 ms and =3 measures 78.7 ms.

In-thread transpose lowering came from the op-evolve loop running unattended on GPU1, which measured it at 5.9 % on its own harness in its own process. The same round rediscovered waves_per_eu independently. Two harnesses agreeing on a knob is worth more than either result alone.

Routes closed, with proof

RouteVerdictEvidence
HipKittens udna1redNot where predicted. transpose compiles and is structurally sound — its row/col layouts really are exact duals on wave32, 4608 triples checked, 0 violations. The wall is three compile-time facts: reductions.cuh cannot compile at all (permlane32_swap is gfx950-only, 7 call sites), only mma_ABt of three matrix entry points survives, and swap_layout provably covers half its registers on wave32 while being mandatory on the transpose→mma path. The GPU gate agrees: 126 of 256 elements wrong.
FlyDSLblockedThe toolchain gate is open — 0.2.4 does expose tdm_ops, s_wait_tensorcnt, ds_load_tr16_b128, contrary to yesterday's note — and the gfx950 forward builds and lowers through MLIR for gfx1250 after a one-line flip. But gfx1250 has no MFMA: mfma.f32.32x32x16.bf16, ds.read.tr16.b64 and permlane32.swap all select on gfx950 and all give Cannot select on gfx1250. The schedule table is derived from the MFMA wave64 fragment map, so this is the rewrite class. 18–36 engineer-days confirmed.

Nine investigations, nine measurement bugs

Every time something "should have had an effect and didn't", the cause was in the measurement or orchestration chain — not once in the change under test. Ordered by time cost.

  1. The end-to-end runs measured the image's package, not the checkoutAn editable install registers a MetaPathFinder through a .pth, and sys.meta_path is consulted before sys.path — so PYTHONPATH cannot shadow it. It was correct in every log the whole time.
  2. Three cards idle for hours, invisible to the monitorLiveness read the ledger's mtime, and an exhausted sweep still appends a completion line every cycle. The proxy said fresh forever. The operator noticed; the monitoring did not.
  3. "All four cards are dead"From a matmul with a 150 s timeout. A cold process spends ~78 s in HIP init and allocation before the first kernel. Phase-separated, the steady state is 0.0011 s — one card was dead, three were fine.
  4. An orphaned loop fed a degraded card for 2 h 15 mA background bash respawner with ppid=1. Three cleanups killed only its children; each reappearance was misread as "the kill pattern missed".
  5. The ASM path "never ran"Concluded from an absent vendor log banner. The launcher exports AITER_LOG_LEVEL=ERROR, which suppresses it. Absence was never evidence.
  6. Three probe designs each killed the training runInside a traced autograd.Function, os.getpid(), open() and a @torch.compiler.disabled call are all fatal. A diagnostic that decides whether the program runs is not a diagnostic.
  7. Contention produced false SQNR failuresSame config, same seed: 42–48 dB contended, 53.7–53.9 dB clean. The accuracy gate is the only correctness defence, and a false failure there discards a good config.
  8. A sweep that ran 40 rounds doing nothingThe idempotence tag carried a round number, so it was never "already done" — once the grid was exhausted the queue re-ran that one candidate forever, looking busy.
  9. Shell traps, four of thempkill -f matching the caller's own command line (four separate shells lost); timeout 5 kill -0 running /bin/kill instead of the builtin; kill -0's EPERM swallowed by 2>/dev/null and read as "no such process"; grep -c printing 0 and exiting 1, so || echo 0 yields "0\n0".
The rule that would have prevented most of this: before trusting any "is X working" signal, ask whether X can be measured directly. It usually can, and usually faster than building the proxy. All of this is now in the gpu-kernel-campaign skill.

One thing left unexplained

torch.cuda.init() takes 58–172 s and scales with concurrent GPU processes, where it should take seconds. It sets the floor on measurement throughput — every run today paid ~78 s before its first kernel. Three experiments each killed one hypothesis: AMD_LOG_LEVEL=3 shows the runtime's entire log spanning 141 milliseconds, so it is not the ROCm runtime; ROCR_VISIBLE_DEVICES (which filters before enumeration and never touches GPU0) saves only 18 %, so it is not mainly the dead card; and three consecutive inits in one container give 157/130/172 s with no warming, so it is not cold library loading. What is left is kernel-side KFD context creation, serialised behind other processes.

Where the remaining headroom is

The backward is 8.840 ms against a recomputed wall of 4.31–4.63 ms — still 1.9–2.0× above it, the same multiple as yesterday. The forward, now on the prebuilt ASM kernel at 1.396 ms, is no longer the lever it was this morning. So the next real gains are structural and all live in the backward: the ASM backward probe, op-evolve's continuing search, and — only if both stall — the 5-GEMM restructure that moves the floor itself from 7.68 to 5.48 TFLOP of issued work.

A caution worth carrying: the plan's claim that "well-scheduled Triton lands at 1.3–1.5× of an issue-slot wall" is refuted by our own two Triton kernels, which sit at 2.0× and 2.2–2.4×. Treat 13 ms as a digit coincidence with the old "below 13 ms is not Triton" threshold, not as arrival.

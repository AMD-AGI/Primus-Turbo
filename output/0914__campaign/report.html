一、背景知识：这件事到底在优化什么

如果你已经熟悉 attention 内核，可以直接跳到第三节。 这一节把后面所有数字依赖的概念讲一遍，力求「不查资料也能读懂」。

1.1 Attention 是什么，为什么它贵

大模型每一层都要做一次 注意力（Attention）：让序列里的每个 token 去「看」其它所有 token，按相关度加权取信息。它的数学只有三步：

为什么叫 causal

语言模型只能看过去、不能看未来，所以 S 矩阵的右上三角要被屏蔽掉（掩码）。 这意味着真正要算的只有下三角，实际算力约为全矩阵的一半。 报告里所有 TFLOP/s 都已按 causal 的真实计算量折算，不存在虚高。

本次固定测量形状 b=4 s=8192 hq=32 hkv=8 d=128： batch 4 条、每条 8192 个 token、32 个 query head、8 个 key/value head（GQA，4 个 query 共享一组 kv）、 每个 head 维度 128。一次前向+反向的计算量是 7.697 TFLOP， 一个训练 step 要做 32 次（32 层）。

1.2 反向为什么比前向贵 3 倍以上

训练要算梯度。前向输出 O，反向要从 dO 反推出 dQ / dK / dV 三个梯度。前向 2 趟矩阵乘，反向要 5 到 7 趟：

1.3 软件栈：一次 attention 调用会走到哪里

同一行 Python 代码，底下可能是四种完全不同的实现。说清楚「哪个后端」比说清楚「多少毫秒」更重要—— 本报告每个数字都标了后端。

Triton 是什么

Triton 是一种用 Python 写 GPU 内核的语言：你描述「一个线程块处理哪一小块数据」， 编译器负责生成机器码。好处是能读能改，几十行就能表达一个 FlashAttention； 代价是你只能通过有限的几个旋钮（块大小、warp 数、流水级数）间接影响最终机器码， 而不像汇编那样直接控制每一条指令和每一个寄存器。

aiter 是 AMD 的算子库，里面装的是人工手写并预编译好的 .co 二进制。 快，但是黑盒：形状不匹配就用不了，也没法改。

gfx1250 不是常见的 CDNA 卡，很多经验不能照搬。三条硬约束贯穿全篇：

1.5 怎么判断一个改动「真的有效」

GPU 上最容易犯的错误是测得快但算得不对。本次全程用三道门，缺一不可：

门内容为什么必须有
正确性 对 fp32 参考实现，out / dq / dk / dv 四个张量分别算 SQNR， 每个都必须 ≥ 50 dB 真实抓到过「out 和 dq 完美、dk/dv 全是 −inf」的配置。只看输出、或只看前向，会静默放过它。
回归 pytest tests/pytorch/ops/test_attention.py -m gfx1250 51/51 绿 覆盖非因果、varlen、不同 head 数等我们没在跑的形状。
显著性 生产形状上对当日冠军快 > 2%（实测重复离散 0.78%） 低于 2% 的差异分不清是改动还是噪声。
SQNR 是什么，50 dB 够吗

SQNR = 信号与量化噪声之比，单位 dB，越高越接近参考值。 bf16 只有 8 位尾数，理论上限大约在 50–55 dB 这个量级， 所以 53 dB 基本就是「bf16 能做到的最好」，50 dB 是一条务实的及格线。 低于它意味着误差已经大于数据类型本身的精度损失，说明内核算错了，而不是精度不够。

本次冠军路径的签名是 out 53.62 / dq 52.24 / dk 52.31 / dv 52.71 dB， 和出厂实现的 53.67/52.24/52.31/52.71 落在同一条带上——速度是白拿的，没有拿精度去换。

三、Day 1：从出厂实现到树内融合反向

起点是一个尴尬的事实：Primus-Turbo 自己的 attention 在 gfx1250 上比 PyTorch 官方的 flex 慢 1.89×， 而且 51 个 gfx1250 测试一个都跑不过（用例根本无法导入）。Day 1 做了四件事。

3.1 第一步：让它能跑起来（0/51 → 51/51）

仓库主干在镜像的 torch 2.11 下根本 import 不了：low_precision.py 对几个量化配置类调用 register_opaque_type，而新 torch 要求这些类带 OpaqueBaseMeta 元类。 这是主干与新 torch 的不兼容，不是本次工作引入的，值得上游修复。 修好之后 51 个测试全绿，后面所有测量才有了地基。

num_stages 和 num_warps 是什么

num_stages：软件流水的级数。设成 2 表示「在算当前这块的同时，预取下一块数据」， 用来把显存延迟藏起来。出厂值 1 等于完全不预取——在这块高延迟的卡上代价极大。

num_warps：一个线程块用几个 wave。更少的 wave 意味着每个 wave 能分到更多寄存器。 反向内核寄存器极度紧张，所以 4→2 反而更快。同一时期我们也试了 num_warps=8 （寄存器预算减半、占用率翻倍），实测慢 2.36×——溢出的代价压倒了占用率收益。

① 为什么昨天判死的旋钮今天活了

waves_per_eu 是「每个执行单元至少驻留几个 wave」的下限约束， 设成 0 表示「不约束，让后端自己决定」。Day 1 在限频态测过 64 个配置， 指令数中位变化 0.00%，于是判定它没用——这个观测本身是对的。 它今天值 4.2%，因为收益根本不在指令数上，而在 你不再约束占用率时后端自己选的那个值；1100 MHz 下没有足够的访存延迟需要隐藏， 所以它在限频态确实一文不值。

这是一口窄井，不是一条斜坡。waves_per_eu=0 是 10.2 ms， =2 是 49.7 ms，=3 是 78.7 ms。相邻档差 5–8 倍。 这类旋钮必须逐个实测，不能插值、不能外推。

另外还修了一个 harness bug：waves_per_eu=0 此前被当作非法值拒绝， 这个设置根本无法从测试工具到达内核（已修，_ZERO_MEANS_UNSET）。 也就是说 Day 1 那 64 个配置里，从来没有一个真正测过「不设」。

② 前向：把手写汇编接进来，快 1.82×

AMD 的 aiter 里有为 gfx1250 预编译好的 attention 前向汇编内核。 Day 1 以为它被一个 import jax 挡住了——实测那个 import 根本不存在。 接进来之后前向 2.579 → 1.410 ms（1.82×）。

这一步的设计难点不在性能，在安全。它不是替换后端，而是只换前向那一个内核， 所以必须保证换了之后的反向还读得懂前向留下的中间结果：

一个能静默产生错梯度的耦合

attention 前向会留下一个叫 LSE（log-sum-exp，softmax 的归一化因子）的中间量给反向用。 两种实现的 LSE 布局不一样：

· ASM 内核返回 [B, Hq, Sq] 的普通布局；
· 我们树内的两内核反向要的是 [B, Hq, 2*Sq] 的打包布局（LSE 与 delta 每 BLOCK_M 行交错）。

如果用 ASM 前向配两内核反向，反向会照着错的布局去读，不会崩溃，会返回平滑地错的梯度。 所以门的条件写成：只有在「融合反向也会被选中」时，才允许用 ASM 前向。 两个门被故意耦合在一起，这是整个设计里唯一有风险的地方，已在代码注释里显式写明。

③ in-thread transpose：来自自主优化循环的贡献

TRITON_HIP_USE_IN_THREAD_TRANSPOSE 是 Triton AMD 后端的一个编译期标志 （改了它会让内核缓存失效、必须重编）。它改变编译器实现矩阵转置的下降方式。 反向 9.786 → 8.840 ms（−9.7%）。

这个旋钮不是我找到的，是 GPU1 上无人值守跑着的 op-evolve 找到的—— 详见第七节。它在自己的 harness、自己的进程里独立测出 −5.9%， 同一轮还独立重新发现了 waves_per_eu。 两套互不共享的测量装置在同一个旋钮上吻合，比任何一边单独的结果都值钱。

关于「四卡满载会不会压低数字」的担心，没有成立。 上面所有数字都是在四张卡同时跑东西的情况下测的。收尾时在完全安静的 GPU1 上复测冠军： 10.235 ms / 752.0 TFLOP/s，与满载下只差 0.6%。

满载确实让单次测量的离散度变大——同一配置见过 11.2 和 17.1 ms—— 但中位数没有被系统性压低。「交替 A/B ＋ 取多次中位」这套做法挡住了竞争的影响。 所以这条阶梯不需要重新标定。

六、端到端训练：算子收益怎么变成 tps

算子快 2.75× 不等于训练快 2.75×。attention 只是 step 的一部分， 而且只有当它真的在关键路径上，内核优化才可能被看见。这一节讲清楚这件事， 因为它是 Day 1 完全没拿到、Day 2 才打通的。

6.1 Day 1 的困境：attention 占不到 1%

Day 1 的 e2e 里，一个 step 是 133.7 秒，而 attention 只占 35.7 ms × 32 = 1.14 s——不到 1%。 turbo 和 flex 的端到端差异落在 0.4% 以内， 也就是说任何内核改动既不能被证实也不能被证伪。根因是矩阵乘（GEMM）慢到离谱， 把 attention 完全淹没了。

七、op-evolve：自主优化循环做了什么

op-evolve 是一套让 LLM agent 无人值守做算子优化的框架。 它的核心设计原则是一句话：「成功是退出码，不是意见」—— 框架自己跑验证脚本、自己读退出码、自己和冻结的参照臂比， agent 不能给自己打分。Day 2 把它挂在 GPU1 上跑了一整天。

7.4 它遇到的麻烦

  • rocprofv3 在这块卡上记录到 0 次内核分发，整天没修好。 这意味着全部决策都只能靠「静态读编译产物」＋「端到端计时」， 说得出内核占反向 99.28%、溢出 266 个，说不出时间花在内核内部哪一段。 gfx1250 的性能剖析面本来就几乎是瞎的（51 个计数器、0 个 derived、无访存计数器）。
  • 一个 bug 吃掉 4 次验证和约 2 小时，表现为内部断言 / std::bad_alloc / 裸 SIGSEGV 三种面孔， 还是间歇性的（连过三次验证才首次触发）。真因是 vendored 的树和 op/baseline 装好的树 声明了同名算子，第二个 torch.library 片段析构时把 schema 从第一个的活句柄下面抽走了。 教训：同一个位置上的 segfault、bad_alloc 和内部断言是一个 bug，不是三个； 而「这次过了」不构成对 use-after-free 的反证。

十一、九次调查，九次测量问题

Day 2 有九次「改动应该有效果却没有」的调查。 九次的根因都在测量或编排链路上，没有一次在被测的改动上。 按消耗的时间排序。这一节是给接手同事看的，也是本次最值得沉淀的部分。

  1. 所有端到端跑的都是镜像里的包，不是我们的 checkout editable 安装通过 .pth 注册了一个 MetaPathFinder， 而 Python 查询 sys.meta_path 先于 sys.path， 所以 PYTHONPATH 根本压不过它。最可怕的是它在每一条日志里都显示为正确。 修法：容器内先 pip uninstall -y primus_turbo，再把 checkout 放第一位。
  2. 三张卡闲置数小时，而监控完全看不见 活性判断读的是 ledger 文件的修改时间，而一个已经跑完网格的队列每轮仍会追加一行完成标记。 代理指标永远显示「新鲜」。这是用户一眼看出来的，不是监控报出来的。 由此得出第一条铁律：在相信任何「X 是否在工作」的信号之前，先问有没有办法直接测 X。
  3. 「四张卡全死了」 结论来自一个 150 秒超时的矩阵乘。分阶段测量后真相是：一个冷进程要花约 58 秒 HIP 初始化 + 20 秒分配 才轮到第一个内核，而稳态只要 0.0011 秒。 死的是一张卡，另外三张好好的。
  4. 一个孤儿循环给已降级的卡喂了 2 小时 15 分 一个 ppid=1 的后台 bash 重生循环。三次清理都只杀掉了它的子进程， 而每次「它又出现了」都被误判成「kill 的匹配模式写错了」。
  5. 断定 ASM 路径「从未被走到」，依据是日志里没有厂商横幅 而启动脚本导出了 AITER_LOG_LEVEL=ERROR，把那行横幅压掉了。 缺席从来就不是证据。换成「门自己往文件里写一行」之后才有了不会被吞掉的证据。
  6. 三个探针设计各自弄挂了训练 在一个会被 torch.compile 追踪的 autograd.Function 里， os.getpid()、open()、以及调用带 @torch.compiler.disable 的函数， 三者都是致命错误。会改变「程序能不能运行」的诊断，不是诊断。 最终解法是用 torch.compiler.is_compiling() 把探针整段折掉。
  7. 抢卡会产生假的 SQNR 失败，不只是假的计时 同一配置、同一随机种子：抢卡时 42–48 dB，干净时 53.7–53.9 dB。 SQNR 门是唯一的正确性防线，一次假失败就会让你丢掉一个本来很好的配置。
  8. 一个扫描空转了 40 轮 幂等标签里带了轮次号，于是它永远不可能命中「已完成」—— 网格跑完之后队列就只在重复那一个候选，还一直看起来很忙。
  9. 四个 shell 陷阱，每一个都伪装成硬件故障 · pkill -f 会匹配到调用者自己的命令行（因此丢了四个 shell）；
    · timeout 5 kill -0 跑的是 /bin/kill 而非 shell 内建，语义不同；
    · kill -0 的 EPERM 被 2>/dev/null 吞掉、被读成「进程不存在」；
    · grep -c 无匹配时既打印 0 又返回退出码 1， 于是 || echo 0 会产生 "0\n0"，把后续算术全毁掉。（这条踩了两次。）

能避免其中大部分的那一条规则： 在相信任何「X 是否在工作」的信号之前，先问「有没有直接测 X 的办法」。 通常有，而且通常比搭一套间接监控更快。

这九条 ＋ 另外一批经验已经整理成一个可复用的 skill： ~/.claude/skills/gpu-kernel-campaign/，共九节， 包括「缺席不是证据」「降级 ≠ 卡死」「什么样的结果才值得信」「基础设施什么时候变成正事」。

GEMM通用矩阵乘。attention 前向 2 趟，本反向内核 7 趟。
Triton用 Python 写 GPU 内核的语言。可读可改，但只能通过有限旋钮间接控制机器码。
aiterAMD 的算子库，内含手写并预编译好的汇编内核（.co 文件）。快，但形状不匹配就用不了、也改不了。
flex_attentionPyTorch 官方的可编程 attention，编译期生成 Triton 内核。本次的对照锚点。
LSElog-sum-exp，softmax 的归一化因子。前向算完存下来给反向用，两种实现的存储布局不同，混用会静默出错。
SQNR信噪比，dB。衡量算得对不对。bf16 的理论上限约 50–55 dB，本次门限设 50。
GQA分组查询注意力。多个 query head 共享一组 key/value head，省显存。本形状 hq=32 / hkv=8，即 4 个 query 共享一组。
num_warps一个线程块用几个 wave。少 → 每 wave 寄存器多；多 → 并行度高。本反向内核 2 最好。
num_stages软件流水级数，用来预取、藏显存延迟。本前向 2 最好，反向 1 最好。
waves_per_eu每执行单元最少驻留几个 wave。0 = 不约束，让后端自选。本次值 4.2%。
AOTAutogradPyTorch 编译栈的一环。它会在编译前向时顺带追踪反向——这是本次两个 bug 的成因。
MESAMD GPU 的微引擎调度器。MES failed to respond = 卡已降级；wait for reset ack = 卡已不可恢复，只能重启。

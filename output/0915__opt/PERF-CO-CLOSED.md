# `_perf` 变体：查清了，不用再看

`hsa/gfx1250/fmha_v3_bwd/` 里有两个没有任何 campaign 文档提到过的对象：
`bwd_hd128_bf16_causal_br_a32_pssk_perf.co` 和 `bwd_hd128_bf16_a32_pssk_perf.co`。
名字带 `_perf`，看起来像"更快的那个"，所以值得查一次。**结论是不要用。**

## 观察

与 shipped 版对拍（gqa2k，b1 s2048 hq32 hkv8）：

| | dq | dk | dv |
|---|--:|--:|--:|
| shipped | 52.21 | 50.578 | 50.864 |
| `_perf` | **5.84** | 50.578 | 50.864 |

**dk/dv 逐位相同**（50.577884674072266 / 50.86431884765625，每一位），只有 dq 错。

## 排除的假设

- **不是 ABI 差异**：两个对象的 `kernarg_segment_size` 都是 704、44 个字段、
  LDS 327680、VGPR 1024、SGPR 128，完全一致，只有代码段长度不同（61688 vs 59392 字节）。
- **不是 grid 折半**：折半 5.91 dB、不折半 5.67 dB，都不对。
  对照组证明旋钮有效 —— shipped 版改成不折半，dq 从 52.21 掉到 13.96。
- **不是缺一个系数**：最佳拟合缩放 0.996，缩放后 SQNR 不变（5.67 dB）。

## 真正的现象

```
第一个出错的序列位置: 128
按序列八分位的出错比例: 0.50 1.00 1.00 1.00 1.00 1.00 1.00 1.00
```

**位置 0–127 完全正确，128 以后全错，而 128 正是 `TS_KV`。**

因果掩码下 query 0–127 只需要第一个 kv tile 的贡献，那部分对；
128 以后需要跨多个 kv tile 累加，那部分错。
最自洽的解释：**`_perf` 对 dq 是赋值而非原子累加**，每行只有最后写入的 tile 存活。
这也解释了为什么改 grid 无效 —— 跨 tile 累加这件事根本没发生。

## 为什么就此打住

**aiter 自己不用它们。** `fmha_bwd_dqdkdv.csv` 的 dispatch 表只有两行，
`co_name` 分别指向 `bwd_hd128_bf16_a32_pssk.co` 和 `bwd_hd128_bf16_causal_br_a32_pssk.co`；
整个 aiter 源码里搜不到 `pssk_perf`。它们是随目录发布但不在任何 dispatch 路径上的孤儿产物。

一个"对 dq 只赋值不累加"的 build，要么未完成，要么需要一套 host 侧 split-K 规约 ——
而那套东西在发布的 host 代码里不存在。shipped 版已经给到 2.0×，
再投 GPU 时间去补一个上游自己都不调用的对象，不划算。

**如果将来要重开这条线**：需要的是一个 split-K 的 `dq_acc`（形如 `[nsplit, b, hq, s, d]`）
加上 host 侧规约，而不是调 grid 或 kernarg。

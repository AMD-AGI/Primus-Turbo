# 一次运行的 loss 变成 nan，而我把它当成了最好的结果

日期 2026-09-16 · 运行 `fly1-fly` · **这条推翻了本日先前报出的一个数字**

## 事实

`fly1-fly` 是四次 FlyDSL wgrad 运行里最快的一次（**49,878 tps**），
我据此先后讲了两套说法："双模态"，以及后来的"一次异常的首跑"。

它的 loss 从 step 10 起**全是 `nan`**：

```
step:  9  loss:  6.13157  grad_norm: 23.9459
step: 10  loss:      nan  grad_norm:     nan   tps: 46,169  mfu: 249.23%
step: 11  loss:      nan  grad_norm:     nan   tps: 49,213
step: 12  loss:      nan  grad_norm:     nan   tps: 50,120
```

**它不是一次快的运行，它根本不是一次测量。** tps 记的是一个已经崩坏的计算跑得有多快。

十一次 e2e 运行里只有这一次出现 nan，其余（三次 fly、三次 copy、两次 32L 等）全部干净。

## 是突变，不是发散

两次运行钉了同一个种子，前九步逐位跟随；第十步一个继续、一个变成 nan：

| step | `fly1-fly` | `fly2-fly` |
|--:|---|---|
| 9 | 6.13157 | 6.13182 |
| **10** | **nan** | **9.70769** |

loss 没有先涨起来再溢出。**同种子的对照运行给出了这一步本该是什么。**

## 剔除它之后的数字

| 臂 | 运行 | 均值 | sd |
|---|---|--:|--:|
| FlyDSL wgrad | 46,622 / 46,513 / 45,986 | **46,374** | 0.60% |
| 两次拷贝 | 42,452 / 42,448 / 42,435 | **42,445** | 0.02% |

**效应 +9.26%**（8 层）。

先前写的"双模态"和"异常首跑"**两套说法都作废** —— 它们是围绕一个本该丢弃的数据点编出来的。
剔除之后 fly 臂的 sd 是 0.60%，与 copy 臂同一量级，**根本没有第二个档位**。

32 层的同会话对照（两臂均 `rc=0`、`nan_steps=0`）：

| 32L | tps | |
|---|--:|---|
| 规则 1+3+ASM | 14,050 | |
| 规则 1+2+ASM | 12,340 | 同会话对照 |
| 效应 | **+13.9%** | |

（`PROGRESS-REPORT.html` 里那个 11,608 是**另一天**的数，不能用作这里的分母。）

## kernel 本身在隔离测试下是干净的

用 NaN 预填充做覆盖检查（输出先填满 NaN 再作为 `out=` 传入，kernel 没写到的元素会留下 NaN）：
**六个形状 × 40 次 × 3 个进程 = 720 次调用，零非有限值，`maxabs = 0`**（与 `torch.mm` 逐位相同）。

所以这不是"kernel 在这些形状上算错"。故障**罕见、非确定，且在隔离条件下复现不出来**。

一个被排除的假设：我怀疑过 FlyDSL 在自己的 HIP stream 上发射、与 PyTorch 的 stream 竞争。
**不成立** —— `gemm_gfx1250_kernel.py:1198` 用的就是 `torch.cuda.current_stream(device=a.device)`。

## 离线表的门为什么没拦住

`flydsl_table.py` 的门是**平均 SQNR ≥ 50 dB**。两个问题：

1. **平均值看不见小块错误。** 一个没被写到的小区域会被平均掉；正是因为如此，
   上面那个覆盖检查用的是 NaN 预填充 + `isfinite`，而不是 SQNR。
2. **`nan < 50` 是 `False`** —— 一个全 NaN 的结果会**通过**这个门。

## 真正要修的是流程，不是这一个 bug

我跑了十一次 e2e，**每一次都只看 tps，一次都没看 loss**。
这个故障从 11:19 就躺在日志里，直到审计把它翻出来才被发现，而在那之前它已经污染了两套解释。

已落地的修改：

- **`e2e.sh` 每次运行后自己数 `loss: nan` 的步数**，打印在结果行里，出现即明确提示
  "DISCARD this run's tps, it is not a measurement"。不再依赖人记得去看。
- **`nkfix.py` 加了 `NKFIX_FLYDSL_CHECK=N`**：每 N 次规则 3 调用抽查一次输出是否有限，
  命中则打印形状与调用序号并计入 `flydsl_nonfinite`。**不回落**——回落会把事件藏起来，
  这里要的是在运行还活着的时候把它记下来。

## 当前立场

- 规则 3 **保持默认关闭**。
- 干净运行测得的 **+9.26%（8L）/ +13.9%（32L）** 成立 —— 它们来自 `nan_steps=0` 的运行。
- 在这个故障有机制解释之前，**不建议任何人打开它**，即便它更快。

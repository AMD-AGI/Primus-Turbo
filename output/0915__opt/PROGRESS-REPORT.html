背景知识（零基础可读）

这一节是给不做算子优化的同学准备的，已经熟悉的可以直接跳到下一节。

大模型训练一步在做什么

训练一个大语言模型，是反复执行"一步"（step）。每一步做三件事：

  1. 前向传播（forward）：把一批文本喂进模型，算出预测结果和误差（loss）。
  2. 反向传播（backward）：从误差倒推回去，算出每个参数应该往哪个方向调整（梯度）。 反向的计算量大约是前向的两倍，所以它通常是优化重点。
  3. 参数更新（optimizer）：按梯度把参数改一点点。

模型由很多层（layer）堆叠而成，本次测试的 llama-3.1-8B 有 32 层。每一层内部主要是两类计算： attention（注意力） 和 MLP（前馈网络），而这两类的底层几乎都是矩阵乘法。

关键术语
算子（kernel / operator）
在 GPU 上执行的一个具体计算单元，比如"一次矩阵乘"或"一次 attention 计算"。 算子优化 = 让单个这样的计算跑得更快。
GEMM
General Matrix Multiply，通用矩阵乘法。大模型训练里绝大部分算力都花在这上面。
TFLOP/s
每秒万亿次浮点运算，衡量算得多快。数字越大越好。
MFU（Model FLOPs Utilization）
实际算力 ÷ 硬件理论峰值算力。比如 65% 表示把这块卡的算力发挥出了 65%。 这是衡量训练效率最常用的单一指标。业界大模型训练能到 40–60% 就算不错。
tps（tokens per second）
每秒处理多少个词元，端到端训练速度的直接指标。
SQNR
信噪比，单位 dB，用来验证"优化后算得还对不对"。 我们的门槛是 ≥ 50 dB，低于这个值就认为精度受损、优化不能采纳。
bf16
一种 16 位浮点数格式，训练常用。比 32 位省一半显存和带宽，精度足够。
GQA（分组查询注意力）
attention 的一种省显存变体。本次形状是 32 个 query 头共享 8 个 key/value 头（比例 4:1）。

为什么"算子快了"不等于"训练快了"

这是今天最重要的一条经验。一个算子快 4.76 倍，如果它只占整步时间的 3%，那整步最多快 2.4%。 更糟的是，算子级测试和真实训练的环境不同 —— 算子测试里同一块显存反复复用，而真实训练里要和几百 GB 的其它数据抢资源。 所以算子级的收益必须用端到端实测来验证，不能外推。

今天的实例

我们的 ASM 反向算子在算子级快 1.74×，但第一次端到端测试显示它让训练慢了 6.78%。 查下来有两个算子级测不出来的开销：每次调用都重新加载 GPU 代码模块（每步 96 次），以及大量临时显存申请。 修掉之后重测，端到端既不快也不慢（n=9 下差异 −0.28%，统计上不显著）。

本次测试的硬件和它的局限

本机被限频，所有绝对数字都不代表正常水平
  • 本机 A0-c07-1 被 VR（供电模块）限频在 1100 MHz，而实测持续负载下只有 943 MHz。
  • 同一块卡 09-04 曾跑到 1699–1703 MHz；另一台 B0-a37-1 负载下稳定在 2133–2244 MHz， 驱动上限是 2400 MHz。
  • 所以本机的 tps、TFLOP/s 只能自己和自己比，不能和其它机器或 JIRA 上的数字横向对比。 本报告全程不做任何跨机器的时钟换算。
  • 另外本机是单卡，且今天大部分实验用的是 8 层模型（生产是 32 层）—— 8 层每 token 的计算量约为 32 层的四分之一，所以它的 tps 天然虚高 3–4 倍， 不能和 32 层的数字放在一起比较。用 8 层是为了让 A/B 实验跑得起来， 并避开 32 层配置 88% 显存占用的悬崖。

为什么最快的那档默认是关闭的

ASM 反向在算子级确实是最快的，但端到端测不出收益：n=9 重复实验下它与融合反向的差异是 −0.28% （分离度 0.15 倍标准误，统计上完全不显著）。而它要付出：常驻 1 GiB 临时显存、一套资格门逻辑、 三个预编译 .co 文件的维护成本。

所以默认关闭，用 PRIMUS_TURBO_ATTN_ENABLE_ASM_BWD=1 显式开启。 按模态配对分析时它有 +1.0~1.5% 的信号（与算子级预测的 +1.36% 吻合），但该分析依赖一个未验证的前提， 记为有前景的假设，不是结论。（以上为 0915 的记录，已被上方更新取代）

主线二：GEMM 后端缺陷 —— 端到端 6.21×

这条线是意外发现的，但它才是今天端到端价值最大的成果。

怎么发现的：一个对不上的数字

端到端日志报告整体算力是 117 TFLOP/s，而我测的 GEMM 微基准只有 68.74 TFLOP/s。 如果训练是 GEMM 主导的，整体速率不可能超过 GEMM 本身 —— 这说明微基准测错了东西。 于是抓了一次 torch profiler，把单步时间拆开：

单步 5.2 秒的去向（8 层配置，step 10 的 profile）
模块耗时占比
hipBLASLt GEMM（矩阵乘）4877 ms94%
attention（前向 + 反向）171 ms3.3%
其余全部（逐元素运算、optimizer、归约、softmax…）~140 ms2.7%

再往里拆，那 4877 ms 的 GEMM 里，4727 ms（97%）跑在一个叫 MT32x16x32 的 kernel 上。

什么是 macro tile（MT）

GPU 算矩阵乘时，会把大矩阵切成小块分给成千上万个线程组并行算。 MT32x16x32 表示每个线程组只负责输出矩阵里 32×16 的一小块。 块切得越小，需要的线程组就越多、重复读取的数据也越多。 这里的 grid 达到 6567 万个线程组，单次调用耗时 592–681 毫秒； 而选对 MT256x256x128（块大 128 倍）的同类调用只要 0.796 毫秒。

根因：NN 布局缺少纯 GEMM 调优库

什么是 NN / NT / TN 布局

矩阵乘 C = A × B 中，A 和 B 各自可以是"正常存放"（N）或"转置存放"（T）。 组合起来就有 NN、NT、TN 三种常见情况。它们在数学上等价，但在 GPU 上访存模式完全不同， 所以数学库要为每种组合分别做调优。PyTorch 的 Linear 层前向走 NT，而反向的梯度计算走 NN。

打开 hipBLASLt 自己的日志（HIPBLASLT_LOG_LEVEL=4 + TENSILE_DB=0x6）， 同样的矩阵尺寸、同样 76 MB 工作空间，唯一差别是布局：

NN 路径:  ProblemMap: Contraction_l_Ailk_Bljk...   sol-tag = GridBased   ← 稀疏查找表
          目标问题 key: M=4096, N=32768, K=14336
          查找表里最近的点 →  M=1024, N=1, B=1, K=512     ← N 差了三万倍！
          Considered 11 (31.43%) of entries        → 选中 sol-idx 104, MT32x16x32

TN 路径:  ProblemMap: Contraction_l_Alik_Bljk...   sol-tag = Prediction  ← 训练好的预测模型
                                                   → 选中 sol-idx 237, MT256x256x128

NN 路径没有预测模型，只有一张稀疏的查找表，而表里离目标最近的点是 N=1。 MT32x16x32 正是为 N=1 这种"细长条"矩阵设计的切法，被错误地套用到了 N=32768 上。

物证在库文件目录里。hipBLASLt 的调优数据按布局组合分文件存放：

NN (Ailk_Bljk) 的 bf16 库：        TN (Alik_Bljk) 的 bf16 库：
  BB_BB_Bias_UA_Type_BB_HPA          BB_BB_Bias_UA_Type_BB_HPA
  BB_BB_HA_Bias_Grad_UA_...          BB_BB_HA_Bias_Grad_UA_...
  BB_BB_HA_Bias_SAV_UA_...           BB_BB_HA_Bias_SAV_UA_...
  BB_BB_HA_Grad_UA_...               BB_BB_HA_Grad_UA_...
                                     BB_BB_UA_Type_BB_HPA        ← 纯 GEMM 调优库
                                     BB_BB_UA_Type_BB_HPA_CU96   ← 按 CU 数的变体
                                     BB_BB_UA_Type_BB_HPA_CU192  ← 按 CU 数的变体

BB_BB_UA_Type_BB_HPA（不带 Bias/Grad 后缀的纯 bf16 GEMM 调优库）TN 有三份，NN 一份都没有。 文件总数也不对等：TN 68 个，NN 40 个。所以纯矩阵乘一旦走 NN，只能退到带 Bias 的库上，而那些库的查找表覆盖不到大 N 区域。

这不是硬件问题，是镜像打包/覆盖缺陷

同一块卡、同一时钟下，NT 路径实测 1502 TFLOP/s —— 比我们一直当作天花板的手写 Triton GEMM（897 TFLOP/s）还快 1.67×。硬件完全没问题。 这与之前发现的 HIPBLASLT_TENSILE_LIBPATH 路径错位是同一家族的镜像问题。

变通修法与端到端验证

修法很简单：当 aten::mm 收到一个"正常存放"的 B 矩阵时，把它换成物理上转置存放的等价形式 （b.t().contiguous().t() —— 逻辑上同一个矩阵，物理主序不同）。 实现为 PyTorch 的 TorchDispatchMode，见 bin/nkfix.py。

更正：日志里的 MFU 一律不可用

torchtitan 的 get_peak_flops() 对任何不认识的 device_name 兜底为 "assume A100" = 312 TFLOP/s，而本机报的是 AMD Radeon Graphics（容器里也没有 lspci）。所以它打印的每一个 MFU 用的都是 A100 的分母 —— 这也是为什么 0916 的运行会报出 215.63% 这种不可能的值 （672.76 ÷ 312 = 2.156）。
tflops 列是对的（FLOP÷时间），mfu 列一律不要引用。 若用本 campaign 实测的 Triton GEMM roof（1002.7 TF/s @1100 MHz）作分母，640.7 是 63.9%。

0916 续：还有一半没修，而且要两个操作数一起改

修完 dgrad 后重新 profile，发现 GEMM 里还有一半跑在坏 kernel 上 —— 57 次调用、2185 ms、占 GEMM 时间的 89.8%、占整个单步的 77%，全部是 wgrad（权重梯度）。第一版规则按 b.is_contiguous() 判断，而 wgrad 的 B 恰好也是连续的， 所以被 dgrad 规则先认领走、留在了慢路径上。

这一步走通靠的是读命中统计，不是推理 —— 我连错了两次
  1. 第一版 wgrad 规则端到端零收益。读统计才发现它命中 0 次： 我的微基准把 B 构造成了非连续，而真实的 B 是连续的，判据永远不成立。
  2. 据此我又推断"dgrad 规则在把 wgrad 推进坑"。实测证伪 —— 它其实有帮助（54 → 69 TF/s），只是远远不够。

顺带解掉了测量噪声问题

今天花了大半天刻画出"本机端到端跨运行噪声约 3.9%、且呈三个离散模态"这个现象，并据此推翻了此前所有 n=1 的结论。 现在因果清楚了：三模态的源头就是 NN 路径上查找表的最近邻匹配 —— 表覆盖不到这片区域，不同进程可能落到不同的 solution 上。绕开它，散布从 3.91% 降到 0.42%，模态消失。

这也解释了一个之前没想通的现象：为什么 A/B 两个臂的方差几乎一模一样（3.88% vs 3.91%）—— 因为它们共用同一条 GEMM 路径，模态从来就不在 attention 里。

镜像层面的两个缺陷（建议上报）

  1. hipBLASLt 的 NN 组合缺少纯 GEMM 调优库（BB_BB_UA_Type_BB_HPA 及其 CU 变体）。 影响面很大：在 PyTorch 训练里，NN 就是每一个 Linear 层的梯度计算，也就是每个模型每一步的大头。
  2. hipblaslt-bench 在这个镜像里不可用：它要找 TensileLibrary_lazy_*.dat， 而镜像提供的是"非 lazy"布局（每个问题类型一个独立文件、没有总索引）。 这挡住了用户自行做 tuning 或验证 solution 的路。

另外此前已发现的 HIPBLASLT_TENSILE_LIBPATH 路径错位（加载器在 library/ 下找索引， 而 402 个文件全在 library/gfx1250/ 子目录里）—— 一行环境变量即可修正， 端到端影响 8.3×（244 → 2,027 tps，32 层配置）。这三条都建议一并上报镜像维护方。

一条需要更正的旧结论

此前文档记载"hipBLASLt 68.7 vs Triton 897 TFLOP/s，还有 13× 空间"。 那是在 NN 布局的 8192³ 方阵上测的，恰好落在本次发现的缺陷区域内。 所以 13× 在 NN 上是真的，但它的含义不是"hipBLASLt 慢"，而是"NN 没有调优库"。 同一块卡同一时钟下，NT 布局上 hipBLASLt 是 1502 TFLOP/s，比那个 Triton 数字还快 1.67×。

不会影响 MI355X 的 attention 性能

但有一处我们的改动确实影响 gfx1250 之外，必须说明

FlyDSL 后端的门被收窄了，而且它的 import 改成了可选：

Q4　优化优先级是怎么定的？评估过哪些后端？

优先级不是拍脑袋定的，是被一次对照实验逼出来的 —— 而且那次实验同时暴露了我们自己之前的方法论错误。

"gfx1250 没有 MFMA" 这一条值得单独讲

Q6　预想周会上可能被问到的问题

按提问者完全不了解算子优化来准备。每条都给可以直接说出口的答复。

可能的问题建议答复
算子快了 4.76 倍，为什么训练只快 1.89 倍？ 这两个数说的不是同一件事。4.76× 是 attention 这个算子本身，而 attention 只占单步时间的 3.3% —— 就算把它优化到零，整步也只快 3.3%。
而 1.89× 根本不是 attention 带来的，是修了一个矩阵乘库的问题。两件事要分开讲。
那 attention 这一天的工作到底有没有价值？ 有三重价值，但要诚实分级：
① JIRA 的第一条请求完成了 —— turbo attention 在 gfx1250 上被跳过的根因找到并修掉；
② 算子本身 4.76×，这是能力储备 —— 一旦 GEMM 问题解决，attention 占比会自动上升，届时它就值钱了；
③ 正是在验证 attention 的过程中，才发现了 GEMM 那个大问题。
但要直说：以今天的占比，attention 优化的端到端收益接近于零。
为什么最快的那个反而默认关掉？ 因为端到端测不出它的好处。n=9 的重复实验下，开和关的差异是 −0.28%， 统计上完全不显著；而它要付出 1 GiB 常驻显存和三个预编译文件的维护成本。 没有可测收益的复杂度不应该进默认路径。需要时一个环境变量就能打开。
你们是不是就是调了几个参数？ 不是调参，但也不是写了新 kernel，要说准：三个计算内核都是 AMD/aiter 的。 我们做的是评测选型、把 aiter 的实现移植/接通到 gfx1250、 并写了约 2300 行的分发、资格判定、参数打包和正确性验证机制。
其中 ASM 这条路 aiter 自己的接口在 gfx1250 上够不到（它的代码里写死了只认 gfx942/gfx950），是我们接出来的。
GEMM 那个问题是我们的 bug 还是 AMD 的？ 是镜像/库侧的覆盖缺陷，不是我们的代码问题，也不是硬件能力问题。 hipBLASLt 对 NN 这种矩阵布局缺少纯 GEMM 的调优数据（TN 有三份，NN 一份没有）， 于是它退回到一张覆盖不到的查找表，选中了为 N=1 细长矩阵设计的切法。
证据是同一块卡同一时钟下，NT 布局能跑到 1502 TFLOP/s。
为什么这个问题现在才发现？ 因为之前的 GEMM 微基准用错了矩阵布局。我们一直测的是 NN 方阵， 而训练里 Linear 层前向走 NT、反向走 NN。
真正戳破它的是一个对不上的数：端到端报告整体 117 TFLOP/s，而 GEMM 微基准只有 68.74 —— 如果训练是 GEMM 主导，整体不可能超过 GEMM 本身。顺着这个矛盾做 profile 才挖出来。
1.89× 能在生产的 32 层配置上拿到吗？ 还不知道，这是下一步第一件事。目前所有端到端数字都是 8 层配置。 32 层配置显存已占 88%，而这个修法的转置会增加瞬时分配，有 OOM 风险。 已经准备了一个缓存转置的变体来降低这个风险，但还没验证。
换个模型还有效吗？ 分两块：
GEMM 修法与模型无关，只要走 NN 布局的大矩阵乘就有效 —— 也就是所有模型的每个 Linear 层反向；
attention 的 ASM 路径限制较严：必须 head_dim=128、bf16、seqlen≥2048。 换 mbs 不影响资格，但换 head_dim 会立刻失效。
会不会影响 MI355X？ attention 不会 —— 两个快速路径的门第二条就是"必须是 gfx1250"， 在 MI355X 上直接拒绝，走原来的代码。我们也没有碰任何 GEMM / 量化目录。
有一处要如实说：FlyDSL 后端的门收窄了、import 改成可选。 这修的是"缺包会让整个 attention 栈无法 import"，在 gfx950 装了 flydsl 时行为不变。
数据可靠吗？听说你们今天推翻了自己好几次 应该反过来看：推翻得越多，现在留下的越可靠。
今天做的最重要的一件事，是量出了这台机器的测量噪声 —— 跨运行 3.9% 且三模态。 在此之前所有端到端结论都是单次测量，其中一条还把方向搞反了 10 个百分点。
现在的做法是：钉随机种子、交替顺序、每臂跑 9 次、报跨运行方差。 而且所有对外数字都回查过原始记录 —— 查出四处与文档不符，包括一个在任何原始记录里都不存在的数。
机器挂了两次，是我们代码的问题吗？ 一次是，一次不确定，要分开说：
第一次确定是我操作导致的 —— 为做对照实验关掉了 converter，模型退回 Flex Attention， 而它内部强制走 inductor 编译，那条路径在本机会打死 GPU。原因清楚，危险配置已删除，其余配置加了警告。
第二次未能归因 —— AC-cycle 后用更长冷却时间连跑 6 次没能复现。 既不能说修法有问题，也不能说它安全，需要补样本。
我们和 JIRA 上的目标差多少？ 这个比较做不了，原因要讲清楚：本机被限频到 1100 MHz（实测负载下 943）， 而 JIRA 机器的时钟在截图和我们仓库里都没有记载。
能说的是：JIRA 提的第一条请求（turbo attention 被跳过）已经完成； 第二条（对齐 compile + primus_turbo）受阻于本机 inductor 会打死卡。
为什么不直接用 torch.compile？ 在本机不能用 —— inductor 的 Triton 自动调优会触发 hipErrorLaunchFailure 并打死 GPU，今天验证过一次。
这也正是 JIRA 那边 MI455X 配置里 compile.enable=False 的原因。这个矛盾目前无解。
SQNR 50 dB 是什么？够吗？ 是衡量"优化后算得还对不对"的信噪比指标，越高越准。 50 dB 是这个项目定的门槛，低于它就认为精度受损、优化不采纳。
我们所有采纳的改动都在门槛之上。特别地，GEMM 那个修法精度零代价 —— 两条路径对 fp32 参考的 SQNR 逐位相同。
nkfix 这个 patch 能进产品吗？ 不建议直接进。它是绕过库缺陷的临时手段，在一个 NN 覆盖正常的镜像上 它是纯粹的损失（白白多一次转置）。
正确做法是推动镜像侧补齐调优库；在那之前可以作为一个环境变量开关的临时方案， 但必须写清适用条件。
报给 AMD 之后多久能修？在那之前怎么办？ 时间不由我们控制。在那之前有两个可用手段： HIPBLASLT_TENSILE_LIBPATH 指向正确目录（一行环境变量，端到端 8.3×，零风险）， 以及 nkfix 这个运行时 patch（1.89×，但需先在 32 层配置上验证显存）。
限频什么时候能解决？ 需要运维介入，不在我们控制范围。
要说明的是：限频不影响我们优化决策的正确性（所有对比都在同一台机器同一时钟下做）， 但它确实让所有绝对数字无法对外比较。建议后续关键结论在满频机器上复测一遍。
下一步要多久？ 上报 hipBLASLt 缺陷是本周就能做的事，且收益最大。 32 层验证大约半天（含显存风险处理）。op-evolve 需要独占一块 GPU 跑一天。
注意本机已交还给同事，需要先协调机器。

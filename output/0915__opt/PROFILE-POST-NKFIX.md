# 修 GEMM 之后的单步构成：attention 升到 6.0%，而 GEMM 里仍有一半没修好

0915 全树只有一个 profile，是**修 GEMM 之前**的（GEMM 94% / attention 3.3%），
所有"下一步优化什么"的判断都压在它上面。0916 补测了修之后的。

配置 `repro_l8b_turbo_conv_8L_prof.yaml` + `NKFIX_ENABLE=1`（nkfix v1），
step 10 的 torch profile，落在 11,489 tps 的模态上。

## 单步构成

| | 修前 | **修后** |
|---|--:|--:|
| 单步 | 5.2 s | **2.83 s** |
| hipBLASLt GEMM | 4877 ms / 94% | **2434 ms / 85.9%** |
| attention（fwd+bwd） | 171 ms / 3.3% | **171 ms / 6.0%** |
| 其余（elementwise/optimizer/归约/softmax） | ~140 ms / 2.7% | 230 ms / 8.1% |

attention 的绝对耗时不变（171 ms），占比因为分母缩小而**翻倍到 6.0%**。
事前推算是 6.1%，吻合。

**但 attention 仍然只占 6%** —— 即使再快一倍，端到端也只有 3% 的空间。GEMM 仍是唯一值得投的方向。

## 关键发现：nkfix v1 只修好了一半

| | ms | 占 GEMM | n |
|---|--:|--:|--:|
| `MT32x16x32`（坏 tile）`Alik_Bjlk` | **2185.6** | **89.8%** | 57 |
| `MT256x256x128`（好 tile）`Alik_Bljk` | 248.2 | 10.2% | 114 |

修之前是坏 tile 114 次、好 tile 57 次；修之后坏 tile 57 次、好 tile 114 次 ——
**恰好一半转过去了，还剩一半，吃掉单步的 77%。**

剩下的全是 **wgrad**，且全是 `Alik_Bjlk`（A 与 B 都是非连续的转置 view）：

| 形状 | ms | n |
|---|--:|--:|
| `[14336,32768]×[32768,4096]` | 901.9 | 16 |
| `[128256,32768]×[32768,4096]`（lm_head） | 510.7 | 1 |
| `[4096,32768]×[32768,14336]` | 454.5 | 8 |
| `[4096,32768]×[32768,4096]` | 254.3 | 16 |
| `[1024,32768]×[32768,4096]` | 64.2 | 16 |

nkfix v1 的判据是 `b.is_contiguous()`，而这些 B 是非连续 view，所以全被跳过。

## wgrad 的修法：动 A，不是 B

微基准（形状取自上表）：

| | 原 | B contiguous | **A contiguous** | 零拷贝 `(BᵀAᵀ)ᵀ` |
|---|--:|--:|--:|--:|
| mlp wgrad | 55.6 ms / 69 TF | 70.6 ms / **更慢** | **3.3 ms / 1160 TF** | 65.4 ms / 0.85× |
| lm_head | 513.6 ms / 67 TF | 689.2 ms | **23.0 ms / 1498 TF** | 618.9 ms / 0.83× |
| qkv wgrad | 15.9 ms / 69 TF | 19.6 ms | **0.68 ms / 1621 TF** | 16.6 ms / 0.95× |

- **方向与 dgrad 相反**：dgrad 要动 B，wgrad 要动 A。把 B 弄连续反而更慢。
- **零拷贝改写失败**：`(Bᵀ@Aᵀ)ᵀ` 用的是两个底层连续张量，理应最优，实测 0.83–0.95× ——
  它落进了同一个坏 solution 家族。这条路不通。
- A 很大（0.25 / 0.88 / 7.83 GiB），拷贝成本不可忽略，**但仍值得付**：
  含拷贝的净收益 8.4× / 11.2× / 9.9×。

数值零代价：两条路径对 fp32 参考的 SQNR 逐位相同（55.60 / 55.62 / 55.62 dB）。

## v2 的端到端结果：没有收益，原因未查明

`bin/nkfix.py` 已加入 rule 2（A 与 B 都非连续时 `a.contiguous()`），
微基准复现了 8–11×，但**端到端 11,539 tps vs v1 的 11,604 —— 0.994×，噪声内**。

微基准 8–11× 而端到端零收益，这个矛盾**尚未解释**。两种可能：
（a）rule 2 在真实训练里没命中（判据与实际张量布局不符）；
（b）命中了但被别的东西抵消。

诊断本身也失败了两次，两个坑都值得记：
1. `atexit` 打印的统计**没出现在日志里** —— 训练启动器的 stdout 经过捕获层会吞行，
   这与 0915 记录的 aiter banner 消失是同一个问题。改写文件即可（`NKFIX_STATS_FILE`）。
2. `rm -rf profile_traces` **静默失败** —— 那些文件是容器里 root 创建的，宿主机普通用户删不掉。
   于是"新 profile"读到的其实是上一次的旧 trace，数字一模一样正是因为它就是同一个文件。
   **凡是要重新生成的产物，先确认旧的真的删掉了。**

第三次 profile 运行（`v2prof`）启动阶段把卡搞 wedge 了，诊断未完成。

## 未决

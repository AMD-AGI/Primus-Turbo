# e2e A/B：ASM 反向在真实训练里值多少

配置 `repro_l8b_turbo_conv.yaml`（llama-3.1-8B，b=4 s=8192，单卡，converter 打开，
compile 关闭，hipBLASLt 走修正路径），20 步，唯一差别是 `PRIMUS_TURBO_ATTN_DISABLE_ASM_BWD`。

## 事前预测（在看到对照臂之前写下）

由已测量的 op 级数字推导：

```
单步时长     = 32768 tokens / 1858 tps = 17.64 s
attention    = 32 层 × 11.726 ms = 375 ms = 单步的 2.13%
ASM 反向省下 = 32 × (17.686 − 10.160) = 241 ms = 单步的 1.37%
预测 ab-off ≈ 1858 × (1 − 0.0137) ≈ 1833 tps
```

稳态离散实测 0.43%，所以 1.37% 的差异约为噪声的 3 倍，**应当可测**。
若实测显著偏离此值，说明"attention 占比"这个模型有问题，而不是优化有问题。

## ASM 反向开启（ab-on）

| | |
|---|--:|
| 步数 | 20 |
| loss | 12.326 → 4.434 |
| 稳态 tps（step≥8）中位 | **1858** |
| 稳态离散 | **0.43%**（1855–1863） |
| 稳态 mfu | 34.49% |
| 资格门 | `engaged: b=4 s=8192 hq=32 hkv=8 d=128`（读出来的，非推断） |

loss 在 20 步内从 12.326 降到 4.434 —— 比 3 步那次（停在 12）强得多的正确性信号：
梯度若有系统性错误，loss 不会这样单调下降。

## ASM 反向关闭（ab-off）

| | |
|---|--:|
| 稳态 tps 中位 | **1984** |
| 稳态 mfu | **36.84%** |
| 资格门 | `declined: disabled by PRIMUS_TURBO_ATTN_DISABLE_ASM_BWD`（读出来的） |

## 结果：预测错了，方向也错了

**关掉 ASM 反向反而快 6.81%**（1984 vs 1858 tps）。我预测的是开启快 1.37%。

op 级：ASM 反向每次省 7.526 ms × 32 层 = **241 ms/步**。
e2e：实际**慢了约 1.2 s/步**。

两者相差约 **1.4 秒/步**，这部分开销 op 级测量完全看不见。

**按当前状态，这个资格门会让真实训练变慢 6.8%。** 不能就这么发布。

### 为什么 op 级测不出来

ASM 反向每层要分配：fp32 `dq_acc` 536 MB + 按 q head 的 dk/dv 268 MB × 2 ≈ 1.07 GB，
32 层每步约 **34 GB 的分配 churn**。
op 级 harness 里同一组张量被 PyTorch 缓存分配器反复复用，这笔开销被摊掉了；
训练里每层每步都要重新申请，还要和 380 GiB 的已用显存争。

融合反向不需要 `dq_acc`（它不用原子累加），dk/dv 也是 kv head 尺寸（小 4 倍）。

### 教训

一个算子级 1.74× 的胜利，在端到端可以是 6.8% 的损失，
而且**两个数字都是对的** —— 它们测的是不同的东西。
op 级测内核，e2e 测内核加上它对分配器和显存系统的要求。
今天之前这个 campaign 的所有结论都只有 op 级证据。

## 背景：为什么差异这么小

这不是优化无效，是**测量对象占比太小**。单步 17.64 秒里 attention 只有 375 ms。
step 被 GEMM 主导，而 GEMM 目前是 hipBLASLt 68.7 TF/s，距 Triton 的 897 还有 13×。
详见 `BLAS-FINDING.md`。

## 第二轮：scratch 复用不是解法，而且把卡搞挂了

修复思路是缓存 `dq_acc` 和按 q head 的 dk/dv 以消除分配 churn。
op 级验证通过：SQNR 逐位不变（53.6197/52.2402/50.6082/50.8302），反向 10.1275（中性）。

**端到端第 3 步 SIGBUS（Signal 7）。**

```
第一轮（无缓存）  step 3 显存 380.06 GiB (87.98%)   跑完 20 步
第二轮（有缓存）  step 3 显存 381.44 GiB (88.30%)   SIGBUS
```

**这个配置本来就贴着显存上限跑，+0.32% 就够了。**
缓存把"每层分配再释放"换成了"常驻 1.07 GB"—— churn 没了，但**峰值上去了，而这里没有峰值余量**。

后果比失败本身更糟：SIGBUS 的进程**没有释放 KFD 上下文和 411 GB 显存**，
容器重启也拿不回来，卡随后建不了新上下文（`torch.cuda.init()` 挂住），
dmesg 全程 0 wedge / 0 degraded。需要人工 AC-cycle。

## 结论：资格门默认关闭

三个数字都是真的，而且互不矛盾：

| | |
|---|---|
| op 级 | ASM 反向 **1.74×**（17.686 → 10.160 ms，n=5，SQNR 一致） |
| e2e，不缓存 | **慢 6.78%**（1858 vs 1984 tps，噪声的 30 倍） |
| e2e，缓存 | **SIGBUS**，并泄漏上下文导致卡不可用 |

`PRIMUS_TURBO_ATTN_ENABLE_ASM_BWD=1` 可显式开启。
`--impl asmbwd` 等测量入口全部保留，算子级结果依然可复现。

**默认路径不带已知的端到端回归** —— 这条比"今天的主线成果"重要。

## 留给明天的问题

1. **能不能不要 `dq_acc`？** 它是 514 条 `buffer_atomic_add_f32` 的累加目标，
   fp32 且必须清零。若能让内核直接写 bf16 dq（`_perf` 变体似乎就是这么做的，
   但它缺跨 tile 累加），整个内存问题就消失了。
2. **能不能不要 4 倍大的 dk/dv？** 根因是主内核 grid `(kv_tiles, nhead_q, batch)`
   在 GQA 下让 `ratio` 个 workgroup 写同一块 tile。若能改 grid 或加同步，
   就能按 kv head 分配。但内核是预编译的，改不了。
3. **这个训练配置本身就在显存边缘**（88%）。任何多占 0.3% 的改动都会 SIGBUS。
   在这个配置上做内存敏感的优化之前，应该先把 batch 或 seqlen 降一档留出余量。

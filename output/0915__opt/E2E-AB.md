# e2e A/B：ASM 反向在真实训练里值多少

配置 `repro_l8b_turbo_conv.yaml`（llama-3.1-8B，b=4 s=8192，单卡，converter 打开，
compile 关闭，hipBLASLt 走修正路径），20 步，唯一差别是 `PRIMUS_TURBO_ATTN_DISABLE_ASM_BWD`。

## 事前预测（在看到对照臂之前写下）

由已测量的 op 级数字推导：

```
单步时长     = 32768 tokens / 1858 tps = 17.64 s
attention    = 32 层 × 11.726 ms = 375 ms = 单步的 2.13%
ASM 反向省下 = 32 × (17.686 − 10.160) = 241 ms = 单步的 1.37%
预测 ab-off ≈ 1858 × (1 − 0.0137) ≈ 1833 tps
```

稳态离散实测 0.43%，所以 1.37% 的差异约为噪声的 3 倍，**应当可测**。
若实测显著偏离此值，说明"attention 占比"这个模型有问题，而不是优化有问题。

## ASM 反向开启（ab-on）

| | |
|---|--:|
| 步数 | 20 |
| loss | 12.326 → 4.434 |
| 稳态 tps（step≥8）中位 | **1858** |
| 稳态离散 | **0.43%**（1855–1863） |
| 稳态 mfu | 34.49% |
| 资格门 | `engaged: b=4 s=8192 hq=32 hkv=8 d=128`（读出来的，非推断） |

loss 在 20 步内从 12.326 降到 4.434 —— 比 3 步那次（停在 12）强得多的正确性信号：
梯度若有系统性错误，loss 不会这样单调下降。

## ASM 反向关闭（ab-off）

| | |
|---|--:|
| 稳态 tps 中位 | **1984** |
| 稳态 mfu | **36.84%** |
| 资格门 | `declined: disabled by PRIMUS_TURBO_ATTN_DISABLE_ASM_BWD`（读出来的） |

## 结果：预测错了，方向也错了

**关掉 ASM 反向反而快 6.81%**（1984 vs 1858 tps）。我预测的是开启快 1.37%。

op 级：ASM 反向每次省 7.526 ms × 32 层 = **241 ms/步**。
e2e：实际**慢了约 1.2 s/步**。

两者相差约 **1.4 秒/步**，这部分开销 op 级测量完全看不见。

**按当前状态，这个资格门会让真实训练变慢 6.8%。** 不能就这么发布。

### 为什么 op 级测不出来

ASM 反向每层要分配：fp32 `dq_acc` 536 MB + 按 q head 的 dk/dv 268 MB × 2 ≈ 1.07 GB，
32 层每步约 **34 GB 的分配 churn**。
op 级 harness 里同一组张量被 PyTorch 缓存分配器反复复用，这笔开销被摊掉了；
训练里每层每步都要重新申请，还要和 380 GiB 的已用显存争。

融合反向不需要 `dq_acc`（它不用原子累加），dk/dv 也是 kv head 尺寸（小 4 倍）。

### 教训

一个算子级 1.74× 的胜利，在端到端可以是 6.8% 的损失，
而且**两个数字都是对的** —— 它们测的是不同的东西。
op 级测内核，e2e 测内核加上它对分配器和显存系统的要求。
今天之前这个 campaign 的所有结论都只有 op 级证据。

## 背景：为什么差异这么小

这不是优化无效，是**测量对象占比太小**。单步 17.64 秒里 attention 只有 375 ms。
step 被 GEMM 主导，而 GEMM 目前是 hipBLASLt 68.7 TF/s，距 Triton 的 897 还有 13×。
详见 `BLAS-FINDING.md`。

## 第二轮：scratch 复用不是解法，而且把卡搞挂了

修复思路是缓存 `dq_acc` 和按 q head 的 dk/dv 以消除分配 churn。
op 级验证通过：SQNR 逐位不变（53.6197/52.2402/50.6082/50.8302），反向 10.1275（中性）。

**端到端第 3 步 SIGBUS（Signal 7）。**

```
第一轮（无缓存）  step 3 显存 380.06 GiB (87.98%)   跑完 20 步
第二轮（有缓存）  step 3 显存 381.44 GiB (88.30%)   SIGBUS
```

**这个配置本来就贴着显存上限跑，+0.32% 就够了。**
缓存把"每层分配再释放"换成了"常驻 1.07 GB"—— churn 没了，但**峰值上去了，而这里没有峰值余量**。

后果比失败本身更糟：SIGBUS 的进程**没有释放 KFD 上下文和 411 GB 显存**，
容器重启也拿不回来，卡随后建不了新上下文（`torch.cuda.init()` 挂住），
dmesg 全程 0 wedge / 0 degraded。需要人工 AC-cycle。

## 结论：资格门默认关闭

三个数字都是真的，而且互不矛盾：

| | |
|---|---|
| op 级 | ASM 反向 **1.74×**（17.686 → 10.160 ms，n=5，SQNR 一致） |
| e2e，不缓存 | **慢 6.78%**（1858 vs 1984 tps，噪声的 30 倍） |
| e2e，缓存 | **SIGBUS**，并泄漏上下文导致卡不可用 |

`PRIMUS_TURBO_ATTN_ENABLE_ASM_BWD=1` 可显式开启。
`--impl asmbwd` 等测量入口全部保留，算子级结果依然可复现。

**默认路径不带已知的端到端回归** —— 这条比"今天的主线成果"重要。

## 事后：代码审查找到了第二个成因，而且它可能更大

并行跑的产品代码审查（四视角 + 对抗性证伪，47 条原始发现）点出一条我完全没看到的：

> **`asm_dense_backward` 没有传 `HipModule`**，而 `asm_backward` 里是 `hip = hip or HipModule()` ——
> 于是每次反向都新建一个实例，实例内的模块缓存永远是空的，
> **三个 `.co` 每次都重新 `hipModuleLoad`**，而且从不 `hipModuleUnload`。

每步 32 层 × 3 = **96 次模块加载，逐步累积泄漏**。

**这解释了为什么 scratch 修复没效果** —— 存在**两个独立的每次调用开销**，我只修了较小的那个：

| 成因 | 量级 | 发现方式 |
|---|---|---|
| 模块重载 | 每步 96 次 `hipModuleLoad`，不卸载 | 代码审查 |
| 分配 churn | 每层 1.07 GB，每步约 34 GB | 我的假设 |

两者被 op 级 harness 以**同样的方式**掩盖：20 次迭代重载同样三个模块 20 次、复用分配器同一批块，
在 32 层的训练步面前都不算什么。

**"scratch 修复没能恢复回归"这件事本身就是证据**，说明模块重载是两者中较大的那个 ——
我当时把它读成了"分配假设错了"，其实是"分配假设不完整"。

两个修复都已实现（进程级 `HipModule` 单例、scratch 复用并补上清零），
但**都没有硬件验证** —— 卡在等重启。明天第一件事就是带这两个修复重跑 e2e A/B。

## 留给明天的问题

1. **能不能不要 `dq_acc`？** 它是 514 条 `buffer_atomic_add_f32` 的累加目标，
   fp32 且必须清零。若能让内核直接写 bf16 dq（`_perf` 变体似乎就是这么做的，
   但它缺跨 tile 累加），整个内存问题就消失了。
2. **能不能不要 4 倍大的 dk/dv？** 根因是主内核 grid `(kv_tiles, nhead_q, batch)`
   在 GQA 下让 `ratio` 个 workgroup 写同一块 tile。若能改 grid 或加同步，
   就能按 kv head 分配。但内核是预编译的，改不了。
3. **这个训练配置本身就在显存边缘**（88%）。任何多占 0.3% 的改动都会 SIGBUS。
   在这个配置上做内存敏感的优化之前，应该先把 batch 或 seqlen 降一档留出余量。

## 第三轮：降显存，把上一轮变成可控实验

上一轮 SIGBUS 的根因是这个配置在 **88% 显存**上跑，没有峰值余量。
正确的应对不是放弃这个测量，而是**给它留出余量再测** ——
`local_batch_size` 4 → 2，seqlen 保持 8192（生产相关，且资格门 `seqlen>=2048` 仍触发），
激活显存大致减半。配置：`repro_l8b_turbo_conv_b2.yaml`。

这样上一轮的失败就变成了一个**判别实验**：

| 第三轮结果 | 含义 |
|---|---|
| ON 不再落后 OFF | **内存压力确实是 6.78% 回归的成因**。资格门可以按"显存余量"而非一刀切来定 |
| ON 仍落后约 6.8% | 内存压力**不是**成因，真因另在。默认关闭的决定不变，但机制需要重查 |
| ON 落后但幅度变小 | 内存压力是部分成因，还有别的因素 |

op 级在 b=2 上 ASM 反向仍然赢 **1.467×**（9.007 → 6.141 ms），所以 op 级预期不变。

巡检加了**显存 75% 硬阈值**：超过就停这一轮。这一轮的全部意义就是留余量，
在它身上再撞一次 OOM 会毁掉实验本身，也会再挂一次卡。

## 先说第一次测量为什么不能用

第一对（`fix2-on` / `fix2-off`）给出 ON **+3.42%**，我差点把它当成翻盘。它不成立：

| 缺陷 | 证据 |
|---|---|
| **没有播种** | `set_determinism` 在 `world_size==1` 且 `debug.seed is None` 时直接 return 而不播种（`torchtitan/distributed/utils.py:92`），而 8L 配置没设 seed。五次运行五个不同的 step-1 loss：12.12861 / 12.31076 / 12.32626 / 12.33148 / 12.29155。**两臂的模型初始化本来就不是同一个。** |

| **冷热/顺序混杂** | ON 先跑（冷，step 1 耗 247 s），OFF 在其末步后 43 s 起跑，在已经热的 VR 限频 1100 MHz 卡上。 |

### 逐模态配对：与 op 级预测吻合的信号

| | ON | OFF | 差 |
|---|--:|--:|--:|
| 高模态 | 6420 | 6327 | **+1.5%** |
| 中模态 | 6011 | 5936 | **+1.3%** |

op 级预测：8 层 × 9.556 ms / 5.6 s 单步 = **+1.36%**。逐模态差落在 1.0–1.5%，**吻合**。

## 判定：资格门维持默认关闭

理由**不是**原来写的"6.78% 显存足迹回归"（已证伪，见下），**也不是**我一度写的
"ON 不可重复"（同样证伪 —— 两臂一样多模态）。

真实理由：**端到端收益在 n=9 下不可测（−0.28%，0.15× sem）**，
而这条路径要付出 1 GiB 常驻显存、一套 ASM 资格门和三个 `.co` 的维护成本。
逐模态的 +1.2% 若能坐实，值得重新考虑 —— 但那需要上面 (a) 或 (b)。

## 更正：原来"6.78% 来自显存足迹"的归因是错的

`_SCRATCH` 的 key 是 `("dq_acc", b, hq, s, d, dev)` —— **不含层索引**。
本模型所有层形状相同，8 层（或 32 层）全部塌缩成**同一个** buffer：
dq_acc fp32 0.500 GiB + dk/dv bf16 0.250×2 = **进程级常数 1.000 GiB，不随层数增长**。

32 层的日志早就测过这件事：

| | 显存 |
|---|--:|
| `ab-on` / `ab-off`（无 scratch 缓存） | 380.06 GiB，**逐位相同** —— ASM 路径零额外 reserved |
| `fix-on`（有 scratch 缓存） | 381.44 GiB，delta **+1.38 GiB** |

决定性的一点：delta 在 8 层（15.65 GiB）比 32 层（1.38 GiB）**更大** ——
凡是随层数缩放的东西都不可能这样。step 行里的 `memory:` 是
`reserved_bytes.all.peak`（`torchtitan/components/metrics.py:71-73`，每次 log 后
`reset_peak_stats`），即**分配器池高水位，不是 live bytes**；低显存压力（36%）下
分配器自由扩张而非复用，高压力（88%）下复用。

所以第二轮那次 SIGBUS 是 **1.38 GiB 贴着 88.30% 上限**的问题，不是 62 GiB 的问题。

## 附带发现：全部四个 op 级测量入口与产品路径已分叉

只有产品路径传 `hip=` 和 `scratch=`：

| 调用点 | `hip=` / `scratch=` |
|---|---|
| `attention_asm_bwd_impl.py:282`（产品） | ✅ |
| `tools/gfx1250/tune_attention.py:529` | ❌ |
| `tools/gfx1250/t2_bringup.py:224,266` | ❌ |
| `output/0915__opt/bin/perfdq_diag.py:18` | ❌ |

两个推论，**都还没有硬件验证**：

1. campaign 全部 op 级 ASM 反向数字（含 10.118 ms 和"1.74×"这个主线成果）
   测的都是**没有这两个修复**的版本。重测是 8.13–8.68 ms，即 op 级比值实际上比记录的
   **更好**（约 2.18×，非 1.74×）。
2. 更要紧：资格门 `seqlen >= 2048` 是从"ASM 反向有约 0.85 ms 固定地板"推出来的，
   而那个地板里**有一部分就是每次调用的 `hipModuleLoad`**。修复后地板应当下降，
   **门槛可能定高了**。支撑门槛的那 9 个测量点需要重测。

这是本 campaign 反复踩的"参照臂/测量入口与被测对象分叉"那个坑的又一个变体
（前两次：参照臂自己变成 ASM 反向；`TORCH_BLAS_PREFER_HIPBLASLT=0` 让 op 级免疫）。

## 事故：关掉 converter 会打死这张卡（0915 晚，第二次 AC-cycle）

为了验证"三模态是否与 turbo attention 有关"，我把 `converters: []` 跑了一次对照臂。
**卡直接 wedge，需要第二次人工 AC-cycle。** 一步训练都没跑出来。

日志停在 inductor 的 `AUTOTUNE flex_decoding`（正在 benchmark 6 个 `triton_flex_decoding`
候选），dmesg 是：

```
MES(6,0) / MES(7,0) failed to respond to msg=REMOVE_QUEUE   反复约 30 秒
failed to unmap legacy queue
Suspending ip block ih_v7_0
wait for reset ack                                          <- 停住
```

**机制**：`converters: []` 不只是"换掉 attention 实现"。它让模型退回 torchtitan 原生
Flex Attention，而 `FlexAttentionWrapper` 内部**必须** `torch.compile(flex_attention)` ——
配置里的 `compile.enable: false` 管不住它，那个开关管的是 TransformerBlock 的编译。

也就是说：**converter 一直在顺带保护这张卡不进 inductor 路径。**
在这台机器上，关掉 converter 等价于打开 inductor，而配置注释早就记着
inductor 的 triton autotune 会 `hipErrorLaunchFailure` 并打死 GPU。
我读过那条注释，但把它理解成"不要开 compile"，没想到还有第二个入口。

处置：`repro_l8b_noconv_8L_fast.yaml` 已删除（留着就是陷阱），
三个带 converter 的配置在 `converters:` 那一行上方都加了警告。

**这条对"想测无 turbo attention 基线"的人是硬约束**：在这台机器上做不到 ——
至少不能靠关 converter，那条路必经 flex，而 flex 必经 inductor。

## 三模态定位：排除了两项，第三项未证实

| 假设 | 做法 | 结果 |
|---|---|---|
| **GEMM 层** | 9 个独立进程跑同样的 GEMM（方阵 8192³ / mlp / qkv） | **已排除。** 跨进程 0.19% / 1.2% / 0.36%，完全稳定 |
| **与 turbo attention 有关** | 关掉 converter 跑对照臂 | **做不了。** 见上一节的事故 —— 这条路径会打死卡 |
| **CPU 调度 / NUMA 漂移** | `taskset` 钉到单个 NUMA 节点，n=8 | **未证实**，见下 |

NUMA 假设的动机：模态在进程启动时就定死（run 内平坦 0.37%，散布全在进程之间），
而本机有 255 个 CPU、两个有内存的 NUMA 节点，`numa_balancing` 开着，GPU 的 `numa_node` 是 `-1`。

```
未钉 OFF n=9   5822×2 | 5936×2 | 6327×5      sd 3.91%   高模态 5/9
钉 node 0 n=4  5858 5916 5920 5889           sd 0.49%
钉 node 1 n=4  5909 5905 6323 5914           sd 3.44%
钉定合并 n=8                                  sd 2.53%   高模态 1/8
```

**有效应，但没有消除。** `numa1_3` 跑出 6323，与未钉时的高模态 6327 是同一个。
sd 从 3.91% 降到 2.53%、高模态命中从 5/9 降到 1/8，但这个样本量下 sd 差异本身不可靠。

**记一笔：我在 n=6 时（还没抽到 numa1_3）一度写下"方差降低 10 倍、模态消失"。
这是今天第三次用不足的 n 下结论 —— 而且是在调查这个问题本身的过程中犯的。**
前两次见上文表格。这个错误模式比它导致的任何单个错误结论都重要。

## 附带成果：每次 e2e 可以省 53%

时间分解（8 层配置）：进程启动 → training start 2 s，→ step 1 再 7 s，
step 2–20 共 93–102 s，总计 109–120 s。**初始化只占 9 秒，步数是唯一杠杆。**

对 18 次运行逐一比较不同窗口的中位：

| 窗口 | 与 step 8–20 中位的最大偏差 | 均值偏差 |
|---|--:|--:|
| step 8–12 (n=5) | 0.29% | 0.06% |
| step 5–9 (n=5) | 0.22% | 0.08% |
| **step 4–8 (n=5)** | **0.22%** | 0.09% |

全部远低于 3.9% 的跨运行地板，所以 **steps 可以从 20 砍到 10**，每次运行 110 s → ~52 s。
`repro_l8b_turbo_conv_8L_fast.yaml` 即此配置。

# `MES ring buffer is full`：三次故障，归因仍未成立

三次都需要人工 AC-cycle。

| # | 日期 | 配置 | nkfix | 连续第几次 | 挂在哪 | 证据是否干净 |
|---|---|---|---|--:|---|---|
| 1 | 0915 | 8L fast | 开 | 4 | step 1 刚开始 | 是 |
| 2 | 0916 早 | 8L prof | 开 | 3 | 启动阶段，185 行 | 是 |
| 3 | 0916 | 32L | 关 | 2 | 启动阶段，0 步 | **否 —— 被抢卡污染** |

## 第 3 次的证据不能用，原因是我自己的编排失误

我一度把第 3 次当成决定性证据："它发生在无 patch 的运行上，所以排除 nkfix"。
`e2e.32-base.log` 里 `nkfix` 确实是 0 次，那部分没错。

**但当时卡上还有别的东西。** 我在启动 32L 队列的同时开了一个并行的分析 workflow，
以为它只做 CPU 侧工作 —— 实际上它的 agent 自己写了 GPU 探针并跑了起来
（`output/0916__attn_sweep/warps16.py`，两个实例，各占 385 MB 显存，CU 占用 0）。
其中 `num_warps=16` 那个候选**挂起**（不是编译失败：日志 0 字节，跑了 11 与 8 CPU-分钟零输出），
把卡占死。32-base 起不来，很可能就是这个原因，而不是一次独立的卡故障。

**所以"无 patch 也会挂"这个结论不成立，nkfix 没有被排除。**

这正是本项目 skill §4 记录过的坑 —— *"抢卡的测量不会报错，它记录一个错的数字"* ——
我自己踩了。教训是：**并行编排时必须假定 agent 会用 GPU，除非明确禁止**。

另外一条值得单独记：**`gpu_health.sh` 在这个状态下报 `HEALTHY degraded=0 wedged=0`**，
而卡实际上已经不能执行工作（随后一个简单的 GEMM 也挂住，`kfd_holders` 从 2 涨到 3）。
健康探针的判据不覆盖这种"被挂起进程占死"的状态。

## 被排除的两个假说

**假说 A：nkfix 是原因**（它把吞吐提高数倍，从而提高命令提交速率，而 ring-buffer-full 是
提交速率类的失败）。

**未排除。** 本想用第 3 次来排除它，但那次证据被抢卡污染（见上）。
唯一还站得住的反向证据是：0915 事后补的 6 次连续 nkfix 运行、0916 的 5 次连续 nkfix 运行，
全部干净、零 MES 行。**11 次干净 vs 2 次故障，倾向于否，但不构成排除。**

**假说 B：第 4 次连续运行是临界点。**

**大概率不成立**，但同样依赖第 3 次那个被污染的数据点。
可靠的部分是：0915/0916 各有 6 次和 5 次连续运行完好无损，所以"第 4 次必挂"肯定是错的。

## 前两次（证据干净的那两次）的共同点

**都挂在训练刚启动、首批 kernel 提交的阶段** —— 没有一次是跑到中途才挂的：

- 第 1 次停在 `Training starts at step 1` 之后，未产出任何 step 行；
- 第 2 次日志 185 行，停在启动；
- 第 3 次 0 步。

这把嫌疑指向**模型构建到首批 kernel 提交之间**的某种竞态，而不是稳态运行时的负载。
故障时 `rocm-smi` 显示 GPU 100% 占用、显存 37–39% —— **有东西在跑但不推进**。

## 与另外两次挂卡的区别（不要混为一谈）

- **converters:[] → Flex Attention → inductor** 那次是**已归因**的，机制完全不同：
  进程停在 `AUTOTUNE flex_decoding`，是 inductor 的自动调优打死了卡。
- **88% 显存 + scratch 常驻 → SIGBUS** 那次也已归因，且签名不同（SIGBUS 而非 MES）。

## 能定性它的实验

当前样本：3 次故障 / 约 20 次干净运行，且三次的配置、patch 状态、连续次数都不同。
共同点只有"启动阶段"这一条。要定性，应当：

1. **压启动，不压稳态**：连续启动-中止训练进程（跑到 step 1 就杀），重复 30 次。
   若故障率显著高于正常跑完 30 次，则定位到启动阶段。成本约 15 分钟 GPU。
2. **记录每次启动的 KFD 队列数**：`/sys/class/kfd/kfd/proc/*/queues`（纯目录读，卡异常时安全），
   看故障前是否有队列泄漏累积。
3. 若 1 证实，再二分启动阶段：模型构建、optimizer 构建、首次 forward、首次 backward。

## 在定性之前的操作规则

- **每次 e2e 之间保持 `E2E_COOLDOWN=25` 以上**（当前默认 20，故障那次用的就是 25，
  所以冷却时间不是充分条件，但也没有理由缩短）。
- **无人值守的长队列，每个 run 之间检查 dmesg 故障计数**，一旦增加立即中止整个队列 ——
  `bin/run32.sh` 已实现，本次正是它把损失限制在一个 run 上。
- **不要在卡不健康时做驱动级操作。** 0915 的 `modprobe -r` 把整机 SSH 打掉了，
  下界不是"没改善"而是"失联"。正确动作是报告并等 AC-cycle。

# 原始记录回查：四处与文档不符，两处在我今天写的材料里

在给周会准备材料时，把 attention 的每一个数字都回查了原始 ledger（B0 的
`output/0914__campaign/ledgers/`，A0 的 `output/0915__opt/ledger.jsonl` 与 `ledgers/`）。
结论：**机器归属全部正确，没有把 B0 的数字混进 A0**；但有四处数值与文档不一致。

## 1. B0 的 `12.412 ms / 620.5 TF/s` 在任何 ledger 里都不存在

`X|w2+wpe0|1..3` 三次原始记录：

```
fwd    2.576 / 2.579 / 2.582      中位 2.579   ← 与文档一致
bwd    9.841 / 9.875 / 9.872      中位 9.872   ← 文档记 9.867
total  12.418 / 12.455 / 12.454   中位 12.454  ← 文档记 12.412
```

全库搜索没有任何 `total_ms = 12.412`（最接近的是 12.4148 / 12.4176 / 12.4241 / …）。
该值已传播到 `RESULTS.md:17`、`HANDOFF.md:16`、`HANDOFF.md:347`，
且 `RESULTS.md:355` 进一步用它推导「32 层 × 12.412 = 0.397 s → attention 占 turbo step 的 16.9%」——
**那一整行是 DERIVED，且推导自一个不存在于原始记录的数**。

xlsx 中已改用可溯源的 **12.454 / 618.0**，并在备注注明差异。

## 2. A0 的 `11.687 ms（n=7）` 不可重构

事故前 ASM-fwd + ASM-bwd 的记录池共 11 行。穷举全部 C(11,7) = 330 个子集：
**只有 4 个**能同时命中 fwd 1.568 与 bwd 10.118，而这 4 个的 total **全部是 11.685**，
从来不是 11.687。

因此本次所有材料一律采用 AC-cycle 后 n=5 的 **11.726**（原始五次
11.688 / 11.726 / 11.749 / 11.754 / 11.697，取中位）。

## 3. 「四个阶梯行都是 AC-cycle 后 n=5」是错的

实际逐行不同：

| 档位 | n | 时段 |
|---|--:|---|
| 出厂 `1cb2e183` | 3 | 事故**前**，且来自另一个 worktree（`wt-bakeoff`） |
| 强制 Triton 前向 + 融合反向 | 2 | 事故**前** |
| ASM 前向 + 融合反向 | 5 | AC-cycle 后 |
| ASM 前向 + ASM 反向 | 5 | AC-cycle 后 |

这个错误出现在三处：`JIRA-BASELINE.html`、`RESULTS.md:20`，
以及**我今天写的 `WEEKLY-EN.md`**。三处均已改为逐行标注。

顺带一提，ASM 前向行事故后测得 19.239，与事故前的 19.233 只差 0.03% ——
这是机器 AC-cycle 后回到同一状态的证据，值得保留。

## 4. `11.687` 与 `11.726` 在同一份文档里自相矛盾

`JIRA-BASELINE.html` 第 195 行（导语）写 11.687，第 388 行（条形图）写 11.726。已统一。

## 其它值得记录的

- **`1.549` 不是 `champ|asm` 的中位数**（那是 1.5474），而是 `ledgers/anchor.json` 的 n=1 值。
  同一配置在树里有三个值：19.285（n=4）、19.233（n=3）、19.2415（n=1）。
- **ledger 的 `impl_note` 字段不可信**：它是按 `--impl` 在运行前就写死的字符串。
  ASM 反向的那些行，`impl_note` 写的是「turbo forward + vendored fused backward」。
  可审计的字段是 `asm_fwd`，而真正能证明 ASM 反向跑了的是 SQNR 指纹（dk 50.608 / dv 50.830，
  融合反向是 52.31 / 52.71）。
- **B0 那次「竞争污染」的第一次重复不是空值，是正确性失败**：out 47.63 dB（门槛 50）、
  dq 38.69、dk 39.40、`correct=false`。这比「抢卡只是变慢」更强 ——
  **抢卡会让 SQNR 假性不达标**。
- **一个没有任何文档引用的异常行**（`ledger.jsonl:50`）：tag 标着 ASM 反向 **OFF**，
  但 SQNR 指纹是 ASM 反向的（dk 50.608 / dv 50.830），且 bwd 8.948 ms 远低于融合反向的 17.7 ms。
  **那个「关闭」臂并没有拿到融合反向**，与已记录的参照臂污染是同一类问题。
- B0 的旋钮扫描行，ledger 的 `configs` 字段在每一行都相同、**并不记录被扫的旋钮**，
  归属完全依赖 tag 字符串。

## 做法上的一条

这次能查出来，是因为把「文档里的数」和「ledger 里的数」当成两个独立来源做了交叉核对，
而不是信任文档。**凡是要对外汇报的数字，都应当回查到原始记录。**

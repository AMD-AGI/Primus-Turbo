gfx1250 单卡 baseline 对照 JIRA

2026-09-15 · 本机 heliosr-1b114-c07-1，单卡 gfx1250，VR 限频 1100 MHz · 分支 dev/lhz/attn · 数据来自 output/0915__opt/ 的日志与 ledger， 经四路独立采集 + 对抗性交叉校验

一句话

JIRA 提的第一条请求（turbo_attention 在 gfx1250 上被 skip）已经解决， attention 算子在本机从出厂 55.785 ms 降到 11.726 ms； 但本机端到端数字不能和 JIRA 并列 —— 本机被 VR 限频到 1100 MHz， 且 GEMM 走的后端比同一块硅片能达到的慢 13–32 倍。

读这份报告前必须知道的三件事
  1. 时钟不可比。本机硬限在 1100 MHz（DPM 表只有 500 / 1100 两档，重启与 AC-cycle 都不解除）。 同一块卡 09-04 曾跑到 1699–1703 MHz；另一台 gfx1250（a37-1）负载下稳在 2133–2244 MHz、 KFD 上限 2400 MHz。JIRA 机器的时钟在 JIRA 截图和本仓库里都没有记载， 所以本报告不做任何时钟换算，两列并排放、差距标注为"未换算"。
  2. 层数不可比。本机今天大部分实验用 8 层模型（为了让 A/B 跑得起、并避开 32 层配置 88% 显存的悬崖）。 8 层每 token 的 transformer 工作量约为 32 层的四分之一，tps 因此虚高约 3–4 倍。 所有 5800–6440 的数字都是 8 层，绝不能和 JIRA 的 32 层数字放同一列。
  3. JIRA 两张图是两个配置。jira_2 是 seq=8192（与本机配置同形）， jira_1 是 seq=4096（len4k），且其 30,188 那一列还额外改了 batch size。 本报告只用 jira_2 做对照。

JIRA 自身的一处数据问题

jira_2 的 Config 行写 FP16，而同一张图里两个 trace 链接都标 BF16； 另外 jira_1 的 GEMM split-K 表给出 1024×4096×32768 NT = 19.0 ms / 924 TFLOPS， 但这两个数互相对不上约 64 倍（该形状 2·M·N·K ≈ 2.75e11 FLOP，19.0 ms 对应约 14.5 TFLOPS，不是 924）。 本报告不基于这两个 TFLOPS 数字做任何对比 —— 分母已知有问题的比值，加多少注解都不可用。

诚实的定位

本机 32 层最好成绩约 2,000 tps，JIRA 的 MI455X 参照是 19,795 tps —— 约 10 倍差距。 这 10 倍不是 gfx1250 的能力问题，而是本机环境的三个叠加因素，且这三者没有被任何测量分离过。见下节。

根因是镜像打包缺陷，不是 gfx1250 的能力上限

hipBLASLt 的加载器在 library/ 下找 TensileLibrary_lazy_gfx1250.dat， 而包括该索引在内的 402 个文件全在 library/gfx1250/ 子目录里。 不改文件、一个环境变量即可修正：

-e HIPBLASLT_TENSILE_LIBPATH=…/_rocm_sdk_libraries_gfx1250/lib/hipblaslt/library/gfx1250

端到端效果：本机 32 层 244 → 2,027 tps（8.3×） 两侧均为 3 步 n=1，非稳态。 建议上报镜像维护方 —— 一行环境变量，影响所有该镜像用户。细节见 BLAS-FINDING.md。

Attention 算子：JIRA Request 1 已经解决

JIRA 的根因第一条是 turbo_attention 在 MI455X 上被 skip、退回 Triton flex。 本机已定位并修复（enable_gqa 的 TypeError 导致 converter 被关掉），converter 现已打开并跑通。

为什么这里不给"对照 JIRA FA path 755 ms"的比值

JIRA 的 755 ms 是 32 层每步合计，来自对方机器一次 profile 采样， 其时钟未知；本机 11.726 ms 是 1100 MHz 下的单层单次算子测量。 把它乘 32 得 375 ms 再与 755 ms 相除，会同时跨越时钟、测量口径（算子 vs trace 聚合） 和层间独立性假设三道边界。三道边界里有两道已知不成立，所以这个比值本报告不给。

机制：ASM 反向耗时跨 16 倍工作量近乎常数（0.88 / 0.91 / 1.00 / 1.34 ms），固定地板约 0.85 ms， 要有足够工作量才摊得开。门槛因此定在 seqlen >= 2048。 注意：这 9 个点是用未修复的调用路径测的（见下），固定地板里有一部分就是每次调用的 hipModuleLoad，修复后地板应当下降，门槛很可能定高了，需要重测。

今天最重要的发现是关于测量本身

本机 e2e 跨运行噪声约 3.9%，且是三模态 —— 此前全部 e2e 结论都建立在 n=1 上

钉住随机种子、交替顺序、每臂跑 9 次之后，两个臂都呈现三个离散模态，且方差几乎相同 （ON 3.88% / OFF 3.91%）。每次运行 junction 温度都是 44.0 °C、sclk 都是 1100 MHz， 所以既不是热也不是降频；run 内平坦到 0.37%，散布全部在进程之间。

任何小于 3.9% 的效应，单次 A/B 都测不出来。

今天被推翻的三条结论 —— 其中两条是当天早些时候刚写下的
曾经的结论当时 n实际
ASM 反向「慢 6.78%，是噪声的 30 倍」1 那个「噪声」是组内 step 抖动，不是跨运行方差。6.78% 落在模态间距之内
带修复后「快 3.42%，翻盘」1 未播种（两臂模型初始化就不同）+ 冷热顺序混杂
「ON 不可重复 sd 4.53%，OFF 稳定 0.06%」3 那三次 OFF 碰巧落在同一模态。n=9 下 OFF 的 sd 是 3.91%

未播种这一条是配置缺陷，已修：torchtitan 的 set_determinism 在 world_size==1 且 debug.seed is None 时直接 return 而不播种， 五次运行给出五个不同的 step-1 loss。现已在配置中钉死 debug.seed: 1234 （只钉种子，不开 deterministic —— 后者会启用确定性算法并降速，反而污染被测量的对象）。

模态成因：已排除两项，第三项未证实

附带发现：四个算子级测量入口已与产品路径分叉

只有产品调用点（attention_asm_bwd_impl.py:282）传 hip= 和 scratch=； tune_attention.py:529、t2_bringup.py:224/266、perfdq_diag.py:18 都不传， 测的仍是未修复的路径。

两个推论，均未经硬件验证：记录在案的 1.74× 低估了修复后的内核（重测约 2.18×）； 资格门门槛可能定高了（见上表脚注）。

建议的下一步

优先级动作理由
1把 hipBLASLt 路径错位上报镜像维护方 一行环境变量，影响所有使用该镜像的用户；本机端到端 8.3×。 今天唯一被证明有端到端价值的方向
2所有后续 e2e A/B 改用 n≥9 + 钉种子 + 交替顺序 否则测不出小于 3.9% 的效应。已提供 bin/ab_replicate.sh 与 bin/ab_summary.py（后者报跨运行方差）。 另已验证步数可从 20 砍到 10（偏差 ≤0.22%），每次运行省 53%
3修好四个算子级入口并重测资格门 9 个点 当前门槛建立在含 hipModuleLoad 的固定地板上，很可能定高
4把 GEMM 钉到 Triton 剩余 13× 全在这里，且 e2e 是 GEMM-bound。 需要 torch.compile，而本机 inductor 会打死 GPU —— 这个矛盾未解
5争取解除本机 VR 限频，或换台全速机器复测 时钟是三个成因里唯一无法在本机内部量化的一项

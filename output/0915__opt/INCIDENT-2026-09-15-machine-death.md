# 事故：我把整台机器搞挂了，最后靠人工 AC-cycle 救回

**结论先行**：机器彻底死掉（SSH 都连不上），是**操作者 AC-cycle 重启**恢复的。
**不是**我的驱动重载修好的 —— 我一度这么记录，那是错的，见文末"我判断错在哪"。

约一小时 GPU 时间 + 约两小时机器完全不可用。

## 触发链

### 1. 起点：两次 e2e 之间没等卡安静

armD 在 04:46:15 报 "Training completed"，我在 **04:47:20**（65 秒后）启动了下一轮。
当时仍有 3 个进程持有 KFD —— 上一轮的 `torchrun` 和一个 `pt_elastic` 还没退。

`output/0914__campaign/bin/closing.sh` 专门做"轮询等卡安静 + 冷却 150 秒"，
我写顺序执行的 runner 时**没有沿用**。

### 2. 第一臂挂在第一次前向里 24 分钟

100% GPU 占用、dmesg 零故障、反向 gate 的 trace 文件从未写入 —— 卡在前向。
内层 `timeout` 按设计在 1440 秒触发。

### 3. `timeout` 只杀了它 spawn 的进程

`torchrun` 是那个进程的**子进程**，活了下来：27 分钟 `Dl` 态，
旁边一个僵尸 worker 和一个 `pt_elastic`，三者都还持有 KFD。

`bin/e2e_loop.sh` 早就给每次运行分配独立 `MASTER_PORT`，注释写明
"孤儿 pt_elastic 占着 1234 端口杀死了 12 次运行"。**我读到过这条，没有应用。**

### 4. 第二臂连端口都绑不上

`DistNetworkError: server socket failed to listen ... port: 1234`。

### 5. 我开始反复探测，每探一次多留一个卡死进程

分段探针定位到具体事实：`torch.cuda.init()` 从约 1 秒变成 **45.2 秒**（两次可复现），
之后第一次真实分配永不返回。这些探针进程 SIGKILL 不死（R 态自旋在驱动里）。

### 6. 致命一步：在这种状态下动驱动

为了腾出 `amdgpu` refcount，我 `docker kill` 掉容器，然后执行

```
sudo modprobe -r amdgpu && sudo modprobe amdgpu
```

**此后 SSH 断开，机器完全不可达。**

`PROGRESS.md` 早有记载：wedge 时**驱动自己的 reset 从来没完成过**。
在一块已经不能执行工作的卡上卸载驱动模块，是把"卡不能用"升级成"机器不能用"。

## 我判断错在哪

会话中断后我在 07:18 重连，看到 `amdgpu loaded / /dev/kfd 存在 / kfd nodes 3 / sclk 1100`，
就判定"`modprobe` 成功了，恢复阶梯第 3 步有效"。

**那是操作者 AC-cycle 之后的全新状态**，与我的 modprobe 无关。
我把别人的重启当成了自己的修复，还写进了文档和提交。

这个错误的形态和今天其他几次同源：**看到期望的状态就认定是自己的操作造成的，没有独立证据。**
正确的做法是先问"我有什么证据表明是我的动作导致了这个状态"，
而当时唯一能区分两者的证据（会话中断期间发生了什么）我恰恰拿不到。

## 应该怎么做

1. **两次 GPU 作业之间必须等卡安静**，不是可选项。已加进 `bin/e2e.sh`（轮询 KFD + 冷却）。
2. **杀进程组，不是杀进程**。`timeout --foreground`，已加。
3. **每次运行独立的 rendezvous 端口**。已加。
4. **卡已经不能执行工作时，不要动驱动**。恢复阶梯的第 3 步应该改成
   "**报告并等人工 AC-cycle**"，而不是 `modprobe -r`。
   驱动重载只适用于卡还能工作、只是想清状态的场合 —— 而那种场合本来也不需要它。
5. **不要反复探测一块已判定不能工作的卡**。每次探测多留一个不可杀进程，
   把可恢复的状态推向不可恢复。第一次确认"init 完成但分配不返回"就该停手上报。

## 给恢复阶梯的修订

| 原 | 改为 |
|---|---|
| 1. 收割容器内进程 | 不变 |
| 2. 重建容器 | 不变 |
| 3. `modprobe -r amdgpu && modprobe amdgpu` | **删除**。改为：推送通知，报告需要 AC-cycle，切 CPU 轨 |
| 4. 通知 + CPU 轨 | 并入第 3 步 |

授权"可以做驱动级重置"不等于"在任何状态下做都安全"。
本次的具体教训是：**卡不能执行工作时，驱动级操作的下界不是"没改善"，而是"整台机器失联"。**
